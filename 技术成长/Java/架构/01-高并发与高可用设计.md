# 01 · 高并发与高可用设计

> **预计阅读**：90 min

---

## 1. 设计目标澄清

高并发设计不是「堆机器」，而是先对齐指标：

| 维度 | 典型问题 |
|------|----------|
| QPS / TPS | 峰值多少？读写比？ |
| 延迟 | P99 要求？可接受抖动？ |
| 一致性 | 强一致还是最终一致？ |
| 可用性 | 几个 9？允许降级吗？ |
| 成本 | 预算与人力运维上限 |

**7 年工程师**：能给出数量级估算，而不是只说「加 Redis」。

---

## 2. 高并发三板斧

```
读多写少 → 缓存
峰值突发 → 异步削峰
资源昂贵 → 池化复用
```

### 2.1 缓存

| 层级 | 适用 | 注意 |
|------|------|------|
| 本地缓存（Caffeine） | 热点、变更少 | 多实例不一致 |
| 分布式缓存（Redis） | 共享、跨节点 | 穿透/击穿/雪崩 |
| CDN | 静态资源 | 缓存失效策略 |

**缓存一致性**（常考）：

1. **Cache Aside**：读 miss 加载；写先更 DB 再删缓存
2. **延迟双删**：删缓存 → 写 DB → sleep → 再删
3. **订阅 binlog**（Canal）：DB 变更驱动缓存失效

### 2.2 异步

- **MQ 削峰**：秒杀下单先入队，异步落库
- **CompletableFuture**：并行聚合多下游
- **事件驱动**：领域事件解耦，提升吞吐

### 2.3 池化

- 数据库连接池（HikariCP）
- 线程池（按 IO/CPU 密集型区分）
- HTTP 连接池（Feign/OkHttp）

**原则**：池大小有上限，配合监控与拒绝策略。

---

## 3. 水平扩展与无状态

```
有状态 Session → 粘性会话 / Redis Session / JWT
本地文件上传 → OSS
单机锁 → 分布式锁（Redis/ZK）
```

服务设计为 **无状态**，通过负载均衡水平扩容；状态外置到 Redis/DB。

---

## 4. 限流 · 熔断 · 降级

| 手段 | 目的 | 实现 |
|------|------|------|
| 限流 | 保护自身 | 令牌桶、漏桶、Sentinel |
| 熔断 | 快速失败 | 错误率/慢调用比例 |
| 降级 | 保核心 | 开关、返回默认值 |

**组合使用**：网关层全局限流 + 服务层熔断 + 业务降级开关。

---

## 5. 数据层扩展

| 手段 | 场景 |
|------|------|
| 读写分离 | 读压力大，可接受主从延迟 |
| 分库分表 | 单表数据/连接数瓶颈 |
| 冷热分离 | 历史订单归档 |
| ES 搜索 | 复杂检索与聚合 |

**注意**：分片键选择影响跨分片查询；避免分布式事务滥用。

---

## 6. 高可用架构

### 6.1 冗余与故障转移

```
多实例部署 + 健康检查 + 自动摘除
主备 / 主主（需冲突解决）
异地容灾（同城双活 / 两地三中心）
```

### 6.2 RPO / RTO

| 指标 | 含义 |
|------|------|
| RPO | 最多丢多少数据 |
| RTO | 多久恢复服务 |

备份策略、MQ 持久化、多活同步都影响 RPO。

### 6.3 混沌工程

- 随机杀 Pod、注入延迟、断网
- 验证：熔断是否生效、降级是否可用、告警是否及时

---

## 7. 可观测性（HA 基础）

```
Metrics：QPS、延迟、错误率、池使用率
Logging：traceId 贯穿链路
Tracing：Jaeger / SkyWalking
告警：SLO 驱动，避免告警疲劳
```

没有监控的高可用是「自我感觉良好」。

---

## 8. 生产案例摘要

| 现象 | 根因 | 改进 |
|------|------|------|
| 大促 DB 打满 | 无缓存 + 慢 SQL | 多级缓存 + 索引 |
| Redis 热点 key | 单 key 流量过大 | 本地缓存 + key 拆分 |
| 连接池耗尽 | 慢调用占满 | 超时 + 熔断 + 池监控 |
