# 01 · 压测理论与指标

> **预计阅读**：90 min

---

## 1. 为什么压测

```
验证容量 → 发现瓶颈 → 支撑扩容决策 → 保障大促 SLA
```

**7 年工程师**：能设计压测方案、读报告、定位瓶颈，不是只会点 JMeter Run。

---

## 2. 核心指标

### 2.1 吞吐

- **QPS**（Queries Per Second）：查询类
- **TPS**（Transactions Per Second）：完整事务（如下单）

### 2.2 延迟

| 分位 | 含义 |
|------|------|
| P50 | 中位数 |
| P95 | 95% 请求低于此值 |
| P99 | 长尾，SLA 常看此值 |
| Max | 极端值，参考 |

**不要只看平均 RT**：平均值会被多数快请求掩盖。

### 2.3 并发

**Little 定律**（稳定系统）：

```
并发用户数 N ≈ 吞吐量 λ × 平均响应时间 W
```

例：QPS=1000，RT=100ms → 并发约 100。

### 2.4 错误率

- HTTP 5xx/4xx
- 业务错误码
- 超时视为失败

### 2.5 资源饱和度

- CPU（应用、DB）
- 内存、GC 频率
- 磁盘 I/O、网络带宽
- 连接池、线程池队列

**瓶颈**：最先打满的资源。

---

## 3. 压测类型

| 类型 | 说明 | 场景 |
|------|------|------|
| 基准测试 | 单接口、固定并发找上限 | 新服务摸底 |
| 负载测试 | 目标负载持续运行 | 验证 SLA |
| 压力测试 | 逐步加压至崩溃 | 找 breaking point |
| 浸泡测试 | 中等负载数小时/天 | 内存泄漏 |
| 浪涌测试 | 突发流量 | 秒杀模拟 |

---

## 4. 场景设计

1. **明确目标**：大促峰值 5000 QPS，P99 < 200ms
2. **混合场景**：80% 读 + 20% 写（贴近真实）
3. **思考时间**：用户操作间隔（JMeter Timer）
4. **数据参数化**：避免同一 ID 打缓存假象
5. **预热**：JVM 热身 5～10 min 再统计

---

## 5. 环境要求

| 要求 | 说明 |
|------|------|
| 生产同构 | 硬件、JVM、配置比例 |
| 数据规模 | 数据量接近生产（索引行为） |
| 依赖隔离 | Mock 不可控第三方，或 shadow |
| 监控就绪 | APM、GC log、DB 慢查询 |

**避免**：压测机与被测机同机；测试库只有 100 条数据。

---

## 6. 瓶颈分析思路

```
1. 错误率突增 → 看超时、连接池、下游
2. RT 飙升、QPS 不涨 → 串行阻塞、锁、DB
3. CPU 100% → 热点代码、GC、加密
4. CPU 低 QPS 低 → 等 IO、连接池过小
5. DB 瓶颈 → 慢 SQL、锁、连接数
```

工具：Arthas、async-profiler、Prometheus、慢查询日志。

---

## 7. 性能基线与回归

- 每次发版跑**基准场景**，对比 P99/QPS
- CI 轻量压测（冒烟级）
- 大版本/full 压测在预发
