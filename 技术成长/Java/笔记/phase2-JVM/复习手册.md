## 一、运行时数据区

```
┌─────────────────────────────────────────┐
│  线程私有                                │
│  ├─ 程序计数器 PC（唯一不会 OOM）         │
│  ├─ 虚拟机栈（栈帧：局部变量表/操作数栈）  │  StackOverflowError / OOM
│  └─ 本地方法栈                           │
├─────────────────────────────────────────┤
│  线程共享                                │
│  ├─ 堆 Heap（对象实例、数组）             │  -Xms / -Xmx
│  ├─ 方法区 Method Area（JDK8+ Metaspace）│  类元信息、常量、静态变量
│  └─ 直接内存 Direct Memory（NIO）         │  -XX:MaxDirectMemorySize
└─────────────────────────────────────────┘
```

| 区域 | 存什么 | 异常 |
|------|--------|------|
| 堆 | 对象、数组 | `java.lang.OutOfMemoryError: Java heap space` |
| Metaspace | 类元数据 | `Metaspace` OOM（类加载过多） |
| 栈 | 局部变量、方法调用 | `StackOverflowError`（递归过深） |
| 直接内存 | DirectByteBuffer | 堆外 OOM |

**JDK8 变化**：永久代 PermGen 移除 → **Metaspace**（本地内存，默认无限（受 OS 限制））。

## 三、垃圾回收

### 3.1 如何判断可回收

- **引用计数**：循环引用解决不了（Java 不用）
- **可达性分析**：从 GC Roots 不可达 → 可回收

**GC Roots**：栈中引用、静态变量、JNI 引用、同步锁持有对象等。

### 3.2 算法

| 算法 | 做法 | 缺点 |
|------|------|------|
| 标记-清除 | 标活 → 清死 | 碎片 |
| 复制 | 分两块，复制存活 | 浪费一半空间（新生代用） |
| 标记-整理 | 标活 → 移动压缩 | 移动成本高（老年代用） |

### 3.3 分代模型

```
新生代（Young）          老年代（Old）
Eden | S0 | S1    →    长期存活对象
     Minor GC              Major GC / Full GC
```

- **Minor GC**：Eden 满，存活对象复制到 Survivor，年龄 +1，达阈值进 Old
- **Full GC**：整堆 + 方法区；STW 长，要尽量避免频繁

### 3.4 收集器对比（面试必背）

| 收集器 | 区域 | 特点 | 适用 |
|--------|------|------|------|
| Serial | 新生代 | 单线程 STW | 客户端小堆 |
| Parallel Scavenge | 新生代 | 多线程，**吞吐量** | 后台计算 |
| ParNew | 新生代 | 配合 CMS | 老系统 |
| **CMS** | 老年代 | 并发标记清除，低停顿；**碎片、浮动垃圾** | 已逐步淘汰 |
| **G1** | 全堆分区 | 可设 `-XX:MaxGCPauseMillis`；Region、Mixed GC | **JDK9+ 默认，生产首选** |
| **ZGC** | 全堆 | 超低延迟（<10ms 级），染色指针 | 大堆、延迟敏感 |
| Shenandoah | 全堆 | 类似 ZGC | OpenJDK |

**选型口诀**：
- 通用 Web / 微服务 → **G1**
- 超大堆 + 极低延迟 → **ZGC**
- 批处理要吞吐 → Parallel

### 3.5 常用 GC 参数

```bash
-Xms4g -Xmx4g                    # 堆初始=最大，避免动态扩缩
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200         # G1 目标停顿
-XX:MetaspaceSize=256m
-XX:MaxMetaspaceSize=512m
-Xlog:gc*:file=gc.log            # JDK9+ GC 日志
```

## 四、类加载

### 4.1 生命周期

```
加载 → 验证 → 准备 → 解析 → 初始化 → 使用 → 卸载
```

| 阶段 | 做什么 |
|------|--------|
| 加载 | 读 class 字节码，生成 Class 对象 |
| 准备 | 静态变量赋**零值**（非代码里的初始值） |
| 解析 | 符号引用 → 直接引用 |
| 初始化 | `<clinit>()` 执行静态块、静态赋值 |

**触发初始化**：new、反射、子类初始化触发父类、main 所在类、MethodHandle 等。

### 4.2 双亲委派

```
自定义 ClassLoader
    ↓ 先委派
Application ClassLoader
    ↓
Extension ClassLoader
    ↓
Bootstrap ClassLoader（C++，加载 rt.jar 等）
```

**好处**：`java.lang.String` 不会被用户自定义类替换，保证核心类安全。

**打破双亲委派**：
- **SPI**（JDBC）：`Thread.contextClassLoader` 由应用层加载实现类
- **Tomcat**：Web 应用隔离，不同 WebApp 不同 ClassLoader
- **热部署 / 字节码增强**：OSGi、Spring Boot DevTools

## 五、排查工具箱

| 工具 | 用途 | 常用命令 |
|------|------|----------|
| jps | 列 Java 进程 | `jps -l` |
| jstat | GC/类加载统计 | `jstat -gcutil <pid> 1000` |
| jmap | 堆 dump | `jmap -dump:live,format=b,file=heap.hprof <pid>` |
| jstack | 线程栈 | `jstack <pid>` → 死锁、阻塞 |
| **MAT** | 分析 hprof | Dominator Tree、GC Roots、Leak Suspects |
| **Arthas** | 在线诊断 | `dashboard`、`thread`、`watch`、`trace` |
| async-profiler | CPU/内存火焰图 | 找热点方法 |

### OOM 排查流程

```
1. 确认哪种 OOM（heap / metaspace / direct / unable to create thread）
2. -XX:+HeapDumpOnOutOfMemoryError 或 jmap dump
3. MAT：看 Leak Suspects、谁占最多 retained heap
4. 找 GC Roots 引用链 → 代码里谁持有
5. 修复：缓存无界、静态集合、监听器未注销、大对象
```

### Full GC 频繁

```
1. jstat 看 Old 区是否快满、GC 频率
2. 是否内存泄漏 or 堆太小 or 大对象直接进老年代
3. 调大堆 / 优化代码 / 调 G1 参数
4. MAT 对比两次 dump 看增长对象
```

## 七、面试速答

| 问 | 答 |
|----|-----|
| 堆和栈区别？ | 堆存对象共享；栈存局部变量、方法帧，线程私有 |
| Minor GC 和 Full GC？ | Minor 只收新生代；Full 整堆+元空间，停顿长 |
| G1 和 CMS？ | G1 分区、可预测停顿、无碎片问题；CMS 并发但有碎片和浮动垃圾 |
| 什么时候用 ZGC？ | 超大堆、对 P99 延迟极敏感 |
| 双亲委派好处？ | 核心类安全、避免重复加载 |
| 如何排查内存泄漏？ | dump → MAT Dominator → GC Roots 链 → 代码修复 |

## 八、易错点

- [ ] `-Xms` 和 `-Xmx` 设不一样会导致堆动态调整，有性能开销
- [ ] `System.gc()` 可能触发 Full GC，生产别乱用
- [ ] 大数组、长生命周期对象容易进老年代，引发 Full GC
- [ ] Metaspace 默认可能无限涨，要设 `MaxMetaspaceSize`
- [ ] dump 文件要 `live` 才排除已死对象，否则文件巨大
