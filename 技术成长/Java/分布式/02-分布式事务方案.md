# 02 · 分布式事务方案

> **目标读者**：7 年 Java 后端，能对比 2PC/TCC/Saga/本地消息表/Seata AT，并在项目中说明「为何不用强一致 2PC」。
> **预计阅读**：60 min · **难度**：★★★★★

---

## 1. 问题从哪来

微服务 **一服务一库**，单次业务可能跨：

```
订单服务(库A) ──扣库存──► 库存服务(库B)
              ──扣款────► 支付服务(库C)
```

单机 `@Transactional` 无法跨库；需要 **分布式事务** 或 **最终一致** 方案。

**第一原则**：能拆成 **本地事务 + 异步** 就不用分布式事务。

---

## 2. 两阶段提交（2PC / XA）

```
协调者 TM                    参与者 RM1 / RM2
    │ prepare ──────────────►  执行但不提交，锁资源
    │ ◄─────────── vote OK
    │ commit ───────────────►  全部提交
    │ 或 rollback ──────────►  全部回滚
```

| 优点 | 缺点 |
|------|------|
| 强一致 | **同步阻塞**，资源锁到 commit |
| 理论清晰 | 协调者 **单点** |
| | 参与者宕机导致 **悬挂、不确定** |
| | 性能差，互联网少用 |

**Java**：JTA、`Atomikos`；数据库 XA 支持有限，高并发不推荐。

---

## 3. TCC（Try-Confirm-Cancel）

业务侵入式三阶段：

| 阶段 | 含义 |
|------|------|
| **Try** | 预留资源（冻结库存、冻结余额） |
| **Confirm** | 确认扣减 |
| **Cancel** | 释放预留 |

```java
// 库存服务
void tryReserve(Long skuId, int qty);   // 可用- qty, 冻结+ qty
void confirm(Long skuId, int qty);     // 冻结- qty
void cancel(Long skuId, int qty);      // 可用+ qty, 冻结- qty
```

| 优点 | 缺点 |
|------|------|
| 无全局行锁到 commit | **三套接口**，开发成本高 |
| 性能优于 2PC | 空回滚、悬挂、幂等须自行处理 |

框架：Seata TCC 模式、Hmily（了解）。

---

## 4. Saga

长事务拆成 **本地事务链** + **补偿**：

```
T1 创建订单 → T2 扣库存 → T3 扣款
         失败 ◄── 补偿 C2 回库存 ← 补偿 C1 关单
```

| 类型 | 说明 |
|------|------|
| 编排 Orchestration | 中心协调器发命令 |
| 协同 Choreography | 各服务监听事件自行补偿 |

**优点**：无长时间锁，适合长流程。  
**缺点**：**最终一致**；补偿逻辑复杂；可见中间状态。

---

## 5. 本地消息表

```
同一 DB 事务：
  INSERT 订单
  INSERT 本地消息表(status=待发送)

定时任务扫描消息表 → 发 MQ → 成功改 status=已发送
```

消费者处理成功 → 回调或再发消息确认。

| 优点 | 缺点 |
|------|------|
| 与业务同库，**可靠投递** | 表维护、定时扫描 |
| 不依赖 MQ 事务 | 消息可能重复，消费者须幂等 |

**变体**：RocketMQ **事务消息**（半消息 + 回查），见 [消息队列/02-RocketMQ](../../数据与中间件/消息队列/02-RocketMQ核心原理.md)。

## 6. Seata AT 模式（常用）

```
TM @GlobalTransactional
  → RM 执行业务 SQL + 自动记录 undo_log（前后镜像）
  → TC 协调：全成功 commit 删 undo；失败用 undo 回滚
```

```java
@GlobalTransactional(rollbackFor = Exception.class)
public void createOrder(OrderCmd cmd) {
    orderService.create(cmd);
    inventoryClient.deduct(cmd);  // Feign 跨服务
}
```

**前提**：每服务独立库、undo_log 表、Seata Server（TC）。

| 优点 | 缺点 |
|------|------|
| 对业务 **无侵入**（无 TCC 三接口） | 依赖 Seata 部署 |
| 自动回滚 | 全局锁、undo 存储开销 |
| | 仍属 **最终一致** 范畴的 AT |

实战详见 [SpringCloud/06-Sentinel与Seata](../SpringCloud/06-Sentinel与Seata.md)。

## 7. 方案对比表

| 方案 | 一致性 | 性能 | 侵入 | 典型场景 |
|------|--------|------|------|----------|
| 2PC/XA | 强 | 低 | 低 | 传统金融、少 |
| TCC | 最终 | 中 | 高 | 库存、账户冻结 |
| Saga | 最终 | 高 | 中 | 长流程、旅游订票 |
| 本地消息表 | 最终 | 高 | 中 | **电商下单**（推荐） |
| Seata AT | 最终 | 中 | 低 | 快速落地跨库回滚 |

---

## 8. 选型决策树

```
能否只改一个库？
  └─ 是 → 本地事务
  └─ 否 → 能否异步接受延迟？
           └─ 是 → 本地消息表 / MQ 事务消息 + 幂等
           └─ 否 → TCC / Seata AT（评估性能）
                   强一致？→ 2PC（极少）
```

---

## 9. 与 MQ 配合（跳转）

跨服务最终一致 **主流**：

1. 本地事务写业务 + 发 MQ（或消息表）
2. 消费者幂等处理
3. 失败重试 + 死信 + 人工补偿

详见 [消息队列/03-可靠性与幂等](../../数据与中间件/消息队列/03-可靠性与幂等.md)。

---

## 10. 面试题精选

**Q：Seata AT 和 TCC 怎么选？**  
A：要快落地、SQL 可解析用 AT；要精细控制资源预留、性能敏感用 TCC。

**Q：Saga 补偿和 MQ 重试区别？**  
A：补偿是业务语义回滚（加回库存）；MQ 重试是再次执行正向逻辑，须幂等。

**Q：为什么说分布式事务是反模式？**  
A：强一致代价高；多数场景 **最终一致 + 业务补偿** 更简单可靠。

---

## 11. 本章小结

- **默认避免** 分布式事务；用 **消息驱动最终一致**。
- 必须跨库原子感：优先 **本地消息表 / Seata AT**；金融级预留用 **TCC**。
- 2PC 知道原理即可，生产 **慎用**。
