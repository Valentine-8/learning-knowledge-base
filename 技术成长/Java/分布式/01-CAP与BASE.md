# 01 · CAP 与 BASE

> **目标读者**：7 年 Java 后端，能讲清 CAP 定理含义、CP/AP 代表系统，并在架构讨论中正确表述「权衡」而非「三选二」。
> **预计阅读**：45 min · **难度**：★★★★

---

## 1. 分布式系统的前提

单机应用不存在 **网络分区**；一旦多节点 + 网络，就必须考虑：

- 节点宕机、网络延迟、丢包
- 副本同步滞后
- 时钟不一致

CAP 与 BASE 是描述这些约束下 **设计取舍** 的理论框架。

---

## 2. CAP 三个字母

| 字母 | 英文 | 含义 |
|------|------|------|
| **C** | Consistency | **线性一致**：所有节点同一时刻看到相同数据（强一致） |
| **A** | Availability | 每个请求都能收到 **非错误** 响应（不要求最新） |
| **P** | Partition tolerance | 网络分区时系统 **仍能继续工作**（不要求全节点互通） |

---

## 3. CAP 定理（正确理解）

**在网络分区发生时，C 和 A 不可兼得** — 必须二选一：

- 选 **C**：拒绝部分写入或阻塞，直到副本同步（牺牲可用性）
- 选 **A**：各分区独立响应，可能读到旧数据（牺牲强一致）

**P 不是可选项**：分布式系统 **必须接受分区容错**，否则网络一断全停。

```
         发生 Partition
              │
    ┌─────────┴─────────┐
    ▼                   ▼
  保 C                  保 A
  拒绝写/等同步          各分区独立服务
  (ZK 选举期)           (可能脏读)
```

**面试纠正**：不是「平时三选二」，而是 **分区时** C 与 A 冲突。

---

## 4. CP 系统代表

| 系统 | 行为 |
|------|------|
| **ZooKeeper / etcd** | 写入经 Leader；少数派分区不可写；选举期间短暂不可用 |
| **HBase** | 强一致，Region 不可用时不服务 |
| **MySQL 同步复制（严格）** | 主从同步失败则阻塞写 |

**特点**：元数据、锁、选主、配置 — **宁可不可用，不要错数据**。

---

## 5. AP 系统代表

| 系统 | 行为 |
|------|------|
| **Eureka** | 节点间异步复制注册表；可能短暂看到过期实例 |
| **Cassandra** | 可调一致级别；默认 AP 倾向 |
| **Dynamo 系** | 最终一致，向量时钟/版本合并 |

**特点**：高可用优先，**接受短暂不一致**，靠版本号、TTL、补偿修正。

---

## 6. 实际系统并非纯 CP/AP

| 系统 | 实际 |
|------|------|
| **Nacos** | 可 AP（Distro）或 CP（Raft）模式切换 |
| **Redis Cluster** | 多数 AP 倾向；主从切换可能丢写 |
| **MySQL** | 默认异步复制偏 AP；半同步/组复制偏 CP |

架构师应问：**业务能否接受脏读/重复？RTO/RPO 多少？**

---

## 7. BASE 理论

CAP 的实用延伸，互联网 **高可用 + 最终一致** 哲学：

| 字母 | 含义 |
|------|------|
| **BA** | Basically Available — 降级仍可用（返回默认值、关非核心） |
| **S** | Soft state — 允许中间状态（副本未同步） |
| **E** | Eventually consistent — 最终达到一致 |

**典型路径**：主库写 → 异步 MQ/binlog → 从库/缓存/ES 追上。

---

## 8. 一致性级别（扩展）

| 级别 | 说明 |
|------|------|
| 强一致 | 读 always 最新写 |
| 单调读 | 不会读到更旧 |
| 会话一致 | 同会话内一致 |
| 最终一致 | 延迟后一致 |

业务常选 **最终一致 + 幂等 + 补偿**，而非全局 2PC。

---

## 9. PACELC 扩展（了解）

**Else**（无分区时）：Latency vs Consistency 权衡。

- Dynamo/Cassandra：低延迟，可能弱一致
- Spanner：TrueTime，高一致 + 全球部署（成本高）

7 年面试 **提到 PACELC 加分**，不必深钻。

---

## 10. 面试题精选

**Q：注册中心选 Eureka 还是 Nacos？**  
A：Eureka AP，自我保护，适合允许短暂脏实例；Nacos 可 CP，配置+注册一体，国内主流。

**Q：为什么 ZK 是 CP？**  
A：写必须 Leader 同步 ZAB；分区时少数派停止服务，保证一致。

**Q：BASE 和 ACID 矛盾吗？**  
A：不矛盾。ACID 是单库事务；BASE 是跨服务最终一致的工程妥协。

---

## 11. 本章小结

- **P 必接受**；分区时在 **C 与 A** 间选。
- 业务数据多用 **BASE + 最终一致**；元数据/锁用 **CP**。
- 避免 absolutist「我们系统完全 CAP 某一项」— 说清 **场景与边界**。
