## 1. 生产故障案例

### 案例 1：分片键热点导致单 Shard CPU 100%

| 项 | 内容 |
|----|------|
| 现象 | 写入 QPS 高时只有一个 shard 负载飙高 |
| 根因 | 分片键 `{ createdAt: 1 }`，新数据全写同一 chunk |
| 修复 | 改为 `{ userId: "hashed" }` 或 `{ userId: 1, createdAt: 1 }` |
| 预防 | 上线前压测写入分布；避免单调递增单字段分片键 |

### 案例 2：Oplog 窗口过小导致 Secondary 全量同步

| 项 | 内容 |
|----|------|
| 现象 | 从节点频繁 Initial Sync，复制延迟小时级 |
| 根因 | oplog 仅 1GB，大批量导入占满窗口 |
| 修复 | `db.adminCommand({ replSetResizeOplog: 1, size: 10240 })`（GB） |
| 预防 | 监控 `Replication Lag` 和 oplog 窗口小时数 |

### 案例 3：未建索引导致全表 COLLSCAN

| 项 | 内容 |
|----|------|
| 现象 | 某 API P99 从 50ms 涨到 8s |
| 根因 | 新查询 `{ status, createdAt }` 无复合索引 |
| 修复 | `createIndex({ status: 1, createdAt: -1 })` background |
| 预防 | 慢查询日志 + explain 门禁 |

### 案例 4：$lookup 拖垮聚合报表

| 项 | 内容 |
|----|------|
| 现象 | 日报聚合任务 30min 超时 |
| 根因 | 千万级 orders `$lookup` users |
| 修复 | 冗余 userName 到 orders；定时 `$merge` 预聚合 |
| 预防 | 按访问模式嵌入/冗余，限制 lookup 数据量 |

### 案例 5：writeConcern w:1 主节点宕机丢单

| 项 | 内容 |
|----|------|
| 现象 | 故障切换后部分订单找不到 |
| 根因 | 默认 w:1，写未复制到 Secondary 即宕机 |
| 修复 | 关键写改为 `writeConcern: { w: "majority" }` |
| 预防 | 连接串加 `w=majority`；监控 rollback 事件 |

## 3. 高频追问参考答案

**Q：MongoDB 能保证 ACID 吗？**

4.0+ 多文档事务支持 ACID，但有性能开销和 16MB 等限制。单文档操作始终原子。大多数场景通过文档设计避免跨文档事务。

**Q：为什么很多公司 MongoDB 用得少？**

国内 MySQL 生态成熟、DBA 多；MongoDB 分片键设计门槛高；复杂关联报表不如 SQL 方便；早期版本缺事务印象深。

**Q：如何设计日志存储？**

按天/月分集合或 TTL 索引自动过期；写入用 `{ createdAt: 1 }` TTL；查询按时间范围 + 业务 ID 复合索引；冷热分离归档到对象存储。
