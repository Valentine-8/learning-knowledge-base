## 一、生产故障案例（8+）

以下案例均来自 **典型线上场景**，按「现象 → 根因 → 排查 → 修复 → 预防」结构整理，可直接用于面试讲述。

---

### 案例 1：慢 SQL 拖垮整库（无索引全表扫描）

**现象**  
晚高峰订单列表接口 RT 从 50ms 飙到 30s，MySQL CPU 100%，连接池排队，上游 Tomcat 线程打满。

**根因**  
新上线查询 `WHERE status=1 AND create_time > '2026-01-01' ORDER BY create_time DESC LIMIT 20`，表 800 万行。  
`status` Cardinality 极低（仅 3 个值），优化器选 `idx_status` → **扫描 200 万+ 行** + filesort。

**排查**

```sql
-- 从 APM 拿 trace 对应 SQL
EXPLAIN SELECT ...;
-- type=range, key=idx_status, rows=2000000, Extra=Using filesort

SHOW PROCESSLIST;
-- 大量 Sending data 状态

SELECT * FROM sys.schema_table_statistics
WHERE table_schema='order_db' ORDER BY rows_read DESC LIMIT 5;
```

**修复**  
建立联合索引 `(create_time, status, id)`，改写为 **延迟关联** 或 **游标分页**：

```sql
SELECT o.* FROM order o
INNER JOIN (
  SELECT id FROM order
  WHERE create_time > '2026-01-01' AND status = 1
  ORDER BY create_time DESC LIMIT 20
) t ON o.id = t.id;
```

**预防**  
- 上线前 **EXPLAIN 强制 review**，rows > 1 万需审批  
- 开启 **slow_query_log**，`long_query_time=0.5`  
- Prometheus 监控 `mysql_global_status_slow_queries`

### 案例 2：深分页 OFFSET 导致 DB 超时

**现象**  
后台导出「第 5000 页订单」任务超时；`LIMIT 100000, 20` 执行 40s。

**根因**  
InnoDB 需扫描并丢弃前 100020 行，即使走索引也要读大量页。

**修复**

```sql
-- 游标分页（记住上一页最后 id）
SELECT * FROM order
WHERE id < #{lastId} AND status = 1
ORDER BY id DESC LIMIT 20;
```

Java 侧 **禁止** 前端传 pageNo > 100 的深分页；大数据导出走 **Canal + ES** 或 **批任务扫主键范围**。

**预防**  
- API 规范：分页用 cursor，不用大 offset  
- 代码审查拦截 `LIMIT #{largeOffset}`

### 案例 3：死锁频发（反向加锁顺序）

**现象**  
库存扣减接口间歇性 `Deadlock found when trying to get lock; try restarting transaction`，每天 200+ 次。

**根因**  
事务 A：`UPDATE stock SET qty=qty-1 WHERE sku_id=1` → `UPDATE sku SET version=... WHERE id=1`  
事务 B：先锁 sku 再锁 stock → **加锁顺序相反**，形成环路等待。

**排查**

```sql
SHOW ENGINE INNODB STATUS\G
-- LATEST DETECTED DEADLOCK 段查看两个事务的 lock mode 与 waiting lock

SELECT * FROM performance_schema.data_locks;
SELECT * FROM performance_schema.data_lock_waits;
```

**修复**  
- 统一 **加锁顺序**：先 sku 后 stock  
- 缩小事务：单条 `UPDATE stock SET qty=qty-1 WHERE sku_id=? AND qty>=1`  
- 高并发热点 SKU 用 **Redis 预扣 + 异步落库**

**预防**  
- 事务内多表更新必须文档化加锁顺序  
- 监控 `Innodb_deadlocks` 指标

### 案例 4：主从延迟导致「下单成功查不到」

**现象**  
用户支付成功跳转订单详情，偶发 404；日志显示读从库 `order_id` 不存在，500ms 后重试成功。

**根因**  
主库写入后立即读从库，**Seconds_Behind_Master** 平均 3s，大促峰值 15s。  
Spring `@Transactional(readOnly=true)` 默认路由从库。

**排查**

```sql
-- 从库
SHOW SLAVE STATUS\G
-- Seconds_Behind_Master: 12
-- Retrieved_Gtid_Set 领先 Executed_Gtid_Set
```

**修复**  
- 订单详情接口 **写后读主库**（HintManager / `@Master`）  
- 写后 **Redis 缓存** 订单摘要 30s  
- 从库开 **并行复制** `slave_parallel_workers=8`

**预防**  
- 梳理「读己之写」场景清单  
- 监控复制延迟告警 > 5s P1

### 案例 5：连接池打满（连接泄漏 + 慢 SQL）

**现象**  
应用报 `Could not get JDBC Connection`，MySQL `Threads_connected` 接近 `max_connections=500`，但 QPS 不高。

**根因**  
1. 某定时任务大查询未设 **query timeout**，单连接占用 10 分钟  
2. 代码分支异常未 `close` Connection（未用 try-with-resources）  
3. HikariCP `maximumPoolSize=200`，10 个实例 = 2000 需求远超 DB 上限

**排查**

```sql
SHOW PROCESSLIST;
SHOW STATUS LIKE 'Threads_%';
SHOW VARIABLES LIKE 'max_connections';

SELECT user, host, db, command, time, state, info
FROM information_schema.processlist
WHERE command != 'Sleep' ORDER BY time DESC;
```

**修复**  
- 修复泄漏代码；HikariCP 设 `leakDetectionThreshold=60000`  
- 单实例 pool 上限 20，总连接 < max_connections × 0.7  
- 慢 SQL 加 `max_execution_time`（8.0.13+）

**预防**  
- 连接池大小公式：`connections = (core_count * 2) + effective_spindle_count`，多实例要除实例数  
- 强制使用 DataSource，禁止手动 `DriverManager.getConnection`

### 案例 6：磁盘满导致 MySQL 只读

**现象**  
凌晨告警磁盘 100%，所有写接口 500，错误 `The table 'xxx' is full` 或 `No space left on device`。

**根因**  
- Binlog 未过期，积压 800GB  
- 临时表 + sort buffer 打满 `/tmp`  
- 大表 DELETE 未分批，Undo 膨胀

**排查**

```bash
du -sh /var/lib/mysql/*
du -sh /var/lib/mysql/binlog.*
```

```sql
SHOW BINARY LOGS;
SHOW GLOBAL STATUS LIKE 'Created_tmp%';
```

**修复**  
- 紧急 `PURGE BINARY LOGS BEFORE '2026-06-01'`  
- 配置 `binlog_expire_logs_seconds=604800`  
- 扩容磁盘；大 DELETE 改分批 + pt-archiver

**预防**  
- 磁盘使用率告警 75%/85%  
- Binlog 与数据分盘  
- 定期演练 purge 与备份恢复

### 案例 7：误删数据（DROP TABLE 无备份）

**现象**  
运维在从库误执行 `DROP TABLE user`，主从复制导致 **从库表也被删**（SQL 线程重放 DDL）。

**根因**  
在 **从库** 执行写操作（未设 read_only）；或主库误删 + 无延迟从库。

**修复**  
- 若有 **延迟从库**（MASTER_DELAY=3600）：立即 `STOP SLAVE`，从延迟从库 mysqldump 恢复  
- 若无：从 **全量备份 + binlog flashback**（binlog2sql）恢复到事故前秒  
- 8.0 **Clone Plugin** 从其他从库重建

**预防**  
- 从库 `read_only=1` + `super_read_only=1`  
- 生产 DDL 走 gh-ost，禁止手工 DROP  
- 至少一个延迟从库 + 每日全备 + binlog 异地归档

### 案例 8：热点行更新（单行库存秒杀）

**现象**  
秒杀开始瞬间 TPS 3000，单行 `UPDATE stock SET qty=qty-1 WHERE id=1` 串行化，RT 99 线 8s。

**根因**  
InnoDB 对同一行 **排他锁** 串行；单行成为全局热点。

**修复**  
- **库存分桶**：`stock_0`～`stock_7` 各 100 件，随机扣减  
- Redis `DECR` + 异步 MQ 落库  
- 乐观锁 `UPDATE ... SET qty=qty-1, version=version+1 WHERE id=? AND version=?` 减少锁持有时间（但不能解决热点本身）

**预防**  
- 秒杀架构评审：前置缓存、队列削峰、分桶设计  
- 压测验证单行上限（通常 < 1000 TPS）

---

### 案例 9：Metadata Lock 阻塞全库（长事务 + DDL）

**现象**  
执行 `ALTER TABLE order ADD COLUMN ...` 卡住 2 小时，所有对该表的读写排队。

**根因**  
某未提交事务 `SELECT * FROM order WHERE id=1`（RC 下 MDL 读锁），阻塞 DDL 的 MDL 写锁；DDL 又阻塞后续所有访问。

**排查**

```sql
SELECT * FROM performance_schema.metadata_locks;
SELECT * FROM sys.schema_table_lock_waits;

SHOW PROCESSLIST;
-- 找 state=Waiting for table metadata lock
```

**修复**  
- `KILL` 长事务连接  
- DDL 改用 **gh-ost / pt-osc** 在线变更

**预防**  
- 变更窗口 + 长事务监控（`information_schema.innodb_trx` trx_started > 60s 告警）  
- 禁止高峰期 DDL

---

### 案例 10：Buffer Pool 命中率低导致 IO 飙升

**现象**  
数据库 iowait 90%，QPS 仅 2000，但磁盘读 500MB/s。

**根因**  
- 热数据 200GB，Buffer Pool 仅 32GB  
- 新上线报表 SQL 全表扫描 **冷数据**，冲刷热页  
- `innodb_buffer_pool_instances` 过小锁竞争

**排查**

```sql
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%';
-- hit rate = 1 - (reads / read_requests)，低于 99% 需关注

SELECT * FROM sys.innodb_buffer_stats_by_table
ORDER BY pages DESC LIMIT 10;
```

**修复**  
- Buffer Pool 调至物理内存 **60～70%**（专机）  
- 报表迁 **只读从库 / ClickHouse**  
- 预热 `innodb_buffer_pool_dump_at_shutdown` + load at startup

**预防**  
- 监控 buffer pool hit rate  
- OLTP 与 OLAP 物理隔离

## 二、面试题库（60+ 题 · 精简答案）

按主题分类，适合 7 年工程师 **快速过一遍** 或 **模拟面试**。

---

### A. InnoDB 架构与日志（8 题）

**A1. InnoDB 和 MyISAM 区别？**  
InnoDB 聚簇索引、行锁、事务、MVCC、崩溃恢复（Redo）；MyISAM 表锁、无事务、非崩溃安全。

**A2. Redo Log 和 Binlog 区别？**  
Redo InnoDB 物理页日志，循环写，崩溃恢复；Binlog Server 层逻辑日志，归档与主从；两阶段提交保证一致。

**A3. 为什么需要两阶段提交？**  
防 redo 已 commit 但 binlog 未写（无法复制）或 binlog 已写 redo 未 commit（恢复不一致）。

**A4. Buffer Pool 是什么？**  
内存缓存数据页和索引页；读先缓存，写改脏页后异步刷盘。

**A5. 脏页什么时候刷盘？**  
Redo log 写满、Buffer Pool 不足、后台线程、shutdown、长时间未刷。

**A6. Undo Log 作用？**  
事务回滚 + MVCC 版本链；长事务会导致 Undo 无法 purge 膨胀。

**A7. change buffer 是什么？**  
二级索引变更缓冲，合并时再写盘；仅非唯一二级索引。

**A8. 一条 UPDATE 语句的执行过程？**  
解析→优化→执行器调引擎→load 页到 Buffer Pool→写 Undo→写 Redo→更新内存→commit 写 Binlog→两阶段提交→返回。

---

### B. 索引与 B+ 树（10 题）

**B1. 为什么用 B+ 树不用 B 树？**  
B+ 树非叶只存键、叶链表便于范围扫；单页扇出大，IO 次数少。

**B2. 聚簇索引和二级索引？**  
聚簇叶存整行；二级索引叶存主键，需 **回表**。

**B3. 什么是覆盖索引？**  
查询列全在索引中，Extra `Using index`，无需回表。

**B4. 最左前缀原则？**  
联合索引 (a,b,c) 可用 a、ab、abc；跳过左列无法用后续列。

**B5. 索引下推 ICP？**  
5.6+ 存储引擎层在索引上过滤条件，减少回表。

**B6. 索引什么时候失效？**  
对列函数/运算、隐式类型转换、like '%x'、or 一侧无索引、违反最左前缀、优化器判全表更快。

**B7. 前缀索引？**  
长字符串取前 N 字符建索引，省空间但无法覆盖排序/group。

**B8. 联合索引列顺序怎么定？**  
等值查询列放前、区分度高放前、范围查询列放后。

**B9. 主键为什么推荐自增或趋势递增？**  
顺序插入减少 B+ 树页分裂；随机主键（UUID）导致频繁分裂。

**B10. MRR 是什么？**  
Multi-Range Read，二级索引回表前先排序主键，变随机 IO 为顺序 IO。

### C. 事务、MVCC 与锁（12 题）

**C1. 事务 ACID 在 InnoDB 如何实现？**  
A 原子 Undo；C 隔离 MVCC+锁；I 隔离级别；D Redo+binlog。

**C2. 四种隔离级别区别？**  
RU 脏读；RC 不可重复读；RR 快照读无幻读；Serializable 串行。

**C3. InnoDB 默认隔离级别？**  
RR（可重复读），快照读靠 MVCC，当前读靠 Next-Key Lock。

**C4. MVCC 原理？**  
隐藏列 trx_id、roll_pointer 构成版本链；Read View 判断可见性。

**C5. 快照读和当前读？**  
快照读普通 SELECT；当前读 FOR UPDATE/UPDATE/DELETE 读最新并加锁。

**C6. RR 能解决幻读吗？**  
快照读可以；当前读靠间隙锁，不完全等同 SQL 标准意义。

**C7. 记录锁、间隙锁、Next-Key Lock？**  
记录锁锁行；间隙锁锁区间；Next-Key = 记录+左间隙。

**C8. 什么情况下间隙锁会加？**  
RR + 当前读 + 非唯一索引或范围条件。

**C9. 死锁怎么产生？怎么解决？**  
两事务互相等对方锁；InnoDB 检测后回滚代价小的一方；应用重试。

**C10. 如何减少死锁？**  
固定加锁顺序、缩短事务、低隔离级别（RC）、热点拆分。

**C11. 乐观锁和悲观锁？**  
乐观 version 字段 CAS；悲观 SELECT FOR UPDATE 加锁。

**C12. 长事务危害？**  
Undo 膨胀、锁持有久、复制延迟、MDL 阻塞 DDL。

### D. SQL 优化与 EXPLAIN（8 题）

**D1. explain 重点看哪些列？**  
type、key、rows、Extra；避免 ALL、filesort、temporary。

**D2. type 常见值优劣？**  
system>const>eq_ref>ref>range>index>ALL。

**D3. 小表驱动大表？**  
Nested Loop 外层小则循环少；优化器可能自动调整。

**D4. 如何优化 COUNT(*)?**  
大表用近似值、缓存、汇总表；或 `WHERE id>0` 走索引覆盖。

**D5. JOIN 优化注意？**  
关联字段建索引、同类型、控制驱动表大小。

**D6. 子查询 vs JOIN？**  
多数 JOIN 更可控；相关子查询易慢，改 JOIN 或 EXISTS。

**D7. 如何发现慢 SQL？**  
slow log、Performance Schema、APM（SkyWalking/Pinpoint）。

**D8. 8.0 索引优化新特性？**  
隐藏索引、索引合并优化、hash join（8.0.18+）。

### E. 主从复制与高可用（8 题）

**E1. 复制三线程？**  
Dump 发 binlog；IO 写 relay；SQL 重放。

**E2. ROW 和 STATEMENT binlog？**  
ROW 行变更一致性好；STATEMENT 体积小但可能不一致。

**E3. 半同步复制？**  
等从库 ack 再返回；超时降级异步。

**E4. GTID 好处？**  
Failover 自动定位，无需 file+pos。

**E5. 复制延迟原因？**  
单 SQL 线程、大事务、从库硬件差、并行度低。

**E6. 读己之写？**  
写后读从库可能旧；关键读主库或位点等待。

**E7. MGR 了解？**  
组复制 Paxos，certification，自动选主。

**E8. 主从切换注意？**  
数据追平、防脑裂、连接池刷新、改从库指向。

### F. 分库分表与分布式（8 题）

**F1. 垂直 vs 水平拆分？**  
垂直业务/列；水平同结构分片。

**F2. 分片键选择？**  
高基数、查询常带、不变、本地性。

**F3. 绑定表？**  
同分片键表同片 Join。

**F4. 跨库分页问题？**  
各片取再归并，深分页代价大；用游标。

**F5. 雪花 bit 分配？**  
41 时间 + 10 机器 + 12 序列。

**F6. 时钟回拨？**  
等待/报错/Leaf 号段方案。

**F7. 跨库事务？**  
Seata/TCC/本地消息表；架构上尽量避免。

**F8. 扩容 rebalance？**  
双倍扩容、一致性 Hash、逻辑 slot。

---

### G. 缓存、连接池与架构（6 题）

**G1. 缓存穿透/击穿/雪崩？**  
穿透布隆/空值；击穿互斥锁；雪崩 TTL 随机/多级缓存。

**G2. 先删缓存还是先写 DB？**  
Cache Aside：写 DB 后删缓存；延迟双删应对极端不一致。

**G3. HikariCP 连接数怎么配？**  
单实例不宜过大；多实例总和 < MySQL max_connections×0.7。

**G4. 数据库和缓存一致性？**  
最终一致；订阅 Canal 删缓存；重要读走 DB。

**G5. 分库后全局 ID？**  
雪花、号段、Redis INCR。

**G6. 如何设计订单表？**  
分片键 user_id/order_id；状态机；索引 (user_id, create_time)；冷热分离。

---

### H. 运维与故障（6 题）

**H1. 如何安全做 DDL？**  
gh-ost/pt-osc；低峰；避免 MDL 阻塞。

**H2. 备份策略？**  
全量 + binlog 增量；定期恢复演练。

**H3. 如何估算表大小？**  
行数 × 平均行宽 + 索引；`information_schema.tables`。

**H4. max_connections 满了怎么办？**  
查 processlist、kill 异常连接、扩连接、降 pool、读写分离。

**H5. 磁盘满应急？**  
purge binlog、删临时文件、扩容；勿盲目 DELETE 大表。

**H6. 从库延迟应急？**  
非关键读切主、停大 job、开 MTS、kill 从库慢查询。

## 三、上线前 Checklist（Go-Live）

### 3.1 Schema 与索引

- [ ] 所有生产 SQL 有 **EXPLAIN 记录**，无 type=ALL 的核心路径
- [ ] 主键存在且 **趋势递增**（自增/雪花）
- [ ] 联合索引符合 **最左前缀**，无冗余重复索引
- [ ] 字段类型合理（避免 INT 存手机号导致隐式转换）
- [ ] 大表有 **归档/分片** 预案，单表预估 1 年数据量
- [ ] 禁止使用 `SELECT *` 于核心高频接口
- [ ] 字符集 **utf8mb4**，排序规则统一

### 3.2 事务与 SQL 规范

- [ ] 事务尽量短，无外部 RPC/HTTP 在事务内
- [ ] 多表更新 **加锁顺序** 文档化
- [ ] 无 `UPDATE/DELETE` 无 WHERE 或全表扫
- [ ] 批量操作 **分批**（如 500 条/commit）
- [ ] 深分页改 **游标**；导出走离线任务
- [ ] 热点 SQL 设置 **timeout**（8.0 `max_execution_time`）

### 3.3 连接与资源

- [ ] HikariCP `maximumPoolSize` × 实例数 < `max_connections` × 0.7
- [ ] 开启 **leakDetectionThreshold**（测试/预发）
- [ ] `wait_timeout` / `interactive_timeout` 合理（如 600s）
- [ ] Buffer Pool ≥ 物理内存 50%（专机 60～70%）
- [ ] `innodb_log_file_size` 足够（避免频繁 checkpoint）
- [ ] 磁盘独立、IOPS 满足压测峰值；binlog 与 datadir 可分盘

### 3.4 复制与高可用

- [ ] 生产 **ROW binlog** + `sync_binlog=1`（核心库）
- [ ] **GTID** 开启，server-id 唯一
- [ ] 从库 `read_only=1`，至少 2 个从库
- [ ] 复制延迟监控告警（>5s P1）
- [ ] Failover 方案演练（MHA/Orchestrator/云 RDS）
- [ ] **读己之写** 场景已路由主库或缓存
- [ ] 延迟从库或跨区备份用于误删恢复

### 3.5 安全与权限

- [ ] 应用账号 **最小权限**（无 DROP/ALTER/SUPER）
- [ ] 禁止 root 远程；运维走堡垒机
- [ ] 敏感字段 **加密/脱敏**（手机号、身份证）
- [ ] SQL 注入：全量 **PreparedStatement** / MyBatis `#{}`

### 3.6 监控与告警

- [ ] QPS/TPS、慢查询、连接数、Threads_running
- [ ] 复制延迟、IO thread/SQL thread 状态
- [ ] 磁盘使用率 75%/85% 分级告警
- [ ] Buffer Pool 命中率、Innodb_row_lock_waits
- [ ] 死锁次数、长事务（>60s）
- [ ] 备份成功性与 **恢复演练** 记录（季度）

### 3.7 压测与预案

- [ ] 全链路压测达预期 QPS 的 **1.5～2 倍**
- [ ] 核心接口 RT P99 达标
- [ ] 限流/熔断/降级开关就绪
- [ ] 回滚方案：应用版本 + DB 变更（可逆 DDL）
- [ ] On-call  runbook：慢 SQL、连接满、磁盘满、主从切换

### 3.8 分库分表（如适用）

- [ ] 分片键 **不可变** 已评审
- [ ] 无分片键查询有 **兜底**（ES/禁止/全路由评估）
- [ ] 绑定表/广播表配置正确
- [ ] 分布式 ID workerId 分配方案（ZK/Redis）
- [ ] 扩容 rebalance 方案与 **双写演练**

## 四、模拟面试：综合题（5 道）

**Q1. 设计一个日订单 500 万的订单系统存储方案。**  
垂直订单库；按 user_id 分 16 库 64 表；雪花 order_id；绑定 order_item；列表走 ES 或 (user_id, create_time) 索引；读写分离 + 写后读主；Seata 避免跨片事务；归档 6 个月前冷数据。

**Q2. 线上 CPU 100% 你如何排查？**  
top/processlist 找慢 SQL → EXPLAIN → 有无全表扫/锁等待 → Performance Schema → 临时索引或 kill → 根因修复 → 补监控。

**Q3. 如何保证主从数据一致？**  
异步最终一致；半同步/MGR 强一致；监控 GTID 差集；业务接受读延迟或读主；数据校验 job。

**Q4. 大表加字段怎么做？**  
gh-ost/pt-osc 在线 DDL；低峰；监控 MDL；禁止原生 ALGORITHM=INPLACE 盲用在大表。

**Q5. InnoDB 一页 16KB，主键 bigint，估算 2000 万行表多大？**  
约 200B/行 × 2000 万 ≈ 4GB 数据 + 索引（二级索引另算）+ 页空洞；实际以 `information_schema` 为准。
