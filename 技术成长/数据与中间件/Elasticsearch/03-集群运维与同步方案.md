# 03 · 集群运维与同步方案

> **目标**：掌握 ES 集群架构、分片与容量规划、监控运维、脑裂与故障处理，以及 MySQL → ES 的主流同步方案。

---

## 一、集群架构

### 1.1 最小生产集群

```
┌─────────────────────────────────────────────────┐
│  Master Node × 3（专用，仅集群管理，不存数据）    │
├─────────────────────────────────────────────────┤
│  Data Node × N（存储分片，按磁盘/CPU 扩展）        │
├─────────────────────────────────────────────────┤
│  Coordinating（可选，大查询合并，默认各节点兼任）   │
├─────────────────────────────────────────────────┤
│  Ingest Node（可选，Pipeline 预处理）            │
└─────────────────────────────────────────────────┘
```

### 1.2 Master 选举

- **Master-eligible** 节点参与选举
- 7.x 默认：**单节点也可当 Master**（开发）；生产 **≥ 3 Master-eligible**
- **discovery.seed_hosts**：发现其他节点
- **cluster.initial_master_nodes**：首次 bootstrap 指定

**原则**：Master 节点 **不承载 heavy 查询/写入**，避免 GC 影响集群状态。

### 1.3 分片分配

| 概念 | 说明 |
|------|------|
| **Primary** | 写入口，每 Index 每分片 1 个 |
| **Replica** | 副本，可在不同 Node |
| **Allocation** | Master 负责分片分配到 Data Node |
| **Awareness** | 跨机架/机房分配副本 |

```json
PUT /_cluster/settings
{
  "persistent": {
    "cluster.routing.allocation.awareness.attributes": "rack_id"
  }
}
```

## 二、分片规划

### 2.1 分片数量公式（经验）

```
主分片数 ≈ 预期数据量 / 单分片目标大小（20GB~50GB）
节点数 ≤ 主分片数 × (1 + replica) / 每节点分片密度
```

**示例**：
- 数据 200GB，单分片 40GB → 5 主分片
- replica=1 → 共 10 分片
- 4 Data 节点 → 每节点约 2~3 分片

### 2.2 分片过多问题

| 问题 | 影响 |
|------|------|
| 每个分片 Lucene 索引开销 | 内存、文件句柄 |
| 查询 fan-out | Coordinating 合并 N 个分片结果 |
| 集群状态变大 | Master 更新慢 |

**Elastic 建议**：单节点分片数 < 20（视 heap 而定）；单集群总分片 < 数千。

### 2.3 分片过少问题

- 无法利用多节点并行
- 单分片过大 → 迁移/Reindex 慢

### 2.4 扩容策略

| 场景 | 方案 |
|------|------|
| 磁盘不够 | 加 Data 节点 + 均衡分片 |
| 数据增长超预期 | Reindex 到新 Index（更多分片）+ 别名切换 |
| 读压力大 | 增加 replica |

**注意**：主分片数 **创建后不可改**，只能 Reindex。

### 2.5 Reindex 零停机

```
1. 创建 products_v2（更多分片 / 新 Mapping）
2. POST _reindex：products → products_v2
3. 双写短暂期（可选）
4. 别名切换：products → products_v2
5. 删除 products_v1
```

## 三、硬件与 JVM

### 3.1 硬件建议

| 资源 | 建议 |
|------|------|
| **内存** | 64GB 机器 → ES heap **31GB**（压缩指针阈值） |
| **磁盘** | SSD；日志/冷数据可混合 |
| **CPU** | 8 核+，Merge 与聚合吃 CPU |
| **网络** | 万兆内网，跨 AZ 复制延迟 |

### 3.2 Heap 配置

```yaml
# jvm.options
-Xms31g
-Xmx31g
```

**原则**：
- Xms = Xmx，避免 resize
- **不超过 32GB**（Compressed Oops）
- **不超过物理内存 50%**（另一半给 OS Cache，Lucene 依赖）

### 3.3 禁止

- 不要 swap（bootstrap.memory_lock=true）
- 不要把 ES 当主库大量随机写

## 四、关键集群设置

### 4.1 副本与可用性

```json
PUT /my_index/_settings
{
  "number_of_replicas": 1
}
```

- replica=0：无 HA，Master 故障可能丢数据
- 生产至少 replica=1

### 4.2 刷新与合并

| 设置 | 默认 | 调优 |
|------|------|------|
| `refresh_interval` | 1s | 批量导入设 -1 |
| `index.translog.durability` | async/request | 高可靠用 request |
| `merge policy` | 自动 | 导入期增大 segment |

### 4.3 熔断器（Circuit Breaker）

防止 OOM：
- **parent circuit breaker**：总 heap 限制
- **fielddata / request / in-flight requests**

监控：`GET /_nodes/stats/breaker`

## 五、监控指标

### 5.1 集群健康

```bash
GET /_cluster/health
```

| 状态 | 含义 |
|------|------|
| **green** | 全部分片 active |
| **yellow** | 主分片全 active，部分副本未分配 |
| **red** | 部分主分片未分配，**数据不可用** |

### 5.2 关键指标

| 指标 | 告警阈值思路 |
|------|--------------|
| JVM heap 使用率 | > 75% 持续 |
| CPU | > 80% 持续 |
| 磁盘 | > 85% |
| Search/Index latency P99 | 业务 SLA |
| rejected executions | 线程池拒绝 |
| unassigned shards | > 0 且持续 |
| GC 时间 | Old GC 频繁 |

### 5.3 工具

| 工具 | 用途 |
|------|------|
| Kibana Stack Monitoring | 官方监控 |
| Prometheus + elasticsearch-exporter | 指标 |
| Elastic Alerting | 告警 |
| Slowlog | 慢查询分析 |

## 六、故障处理

### 6.1 脑裂（Split Brain）

**原因**：网络分区导致两个 Master 认为自己是主。

**防护**（7.x）：
- `discovery.seed_hosts` 正确配置
- Master 节点 **奇数**（3 或 5）
- **minimum_master_nodes**（6.x）→ 7.x 由选举机制改进

**现象**：集群状态不一致、写入冲突。

**处理**：恢复网络，关停错误 Master 侧，以多数派为准。

### 6.2 节点宕机

| 影响 | 处理 |
|------|------|
| Data 节点 | 副本提升，自动恢复 |
| Master 节点 | 重新选举 |
| 无副本 Primary | **red**，需快照恢复 |

### 6.3 磁盘满

- 只读模式：ES 自动 block 写入
- 删旧 Index、扩容磁盘、ILM 清理

### 6.4 分片未分配

```bash
GET /_cluster/allocation/explain
```

常见原因：磁盘不足、awareness 约束、节点数不够。

### 6.5 快照与恢复

```json
PUT /_snapshot/my_repo/snapshot_1
GET /_snapshot/my_repo/snapshot_1/_restore
```

**生产必须**：定期快照到 OSS/S3，演练恢复。

## 七、ILM 索引生命周期

```
Hot（热写）→ Warm（只读查询）→ Cold（冷存储）→ Delete
```

```json
PUT _ilm/policy/my_policy
{
  "policy": {
    "phases": {
      "hot": {
        "actions": {
          "rollover": { "max_size": "50GB", "max_age": "7d" }
        }
      },
      "delete": {
        "min_age": "90d",
        "actions": { "delete": {} }
      }
    }
  }
}
```

**适用**：日志、时序数据自动滚动与清理。

## 八、ES 与 MySQL 分工

| 维度 | MySQL | Elasticsearch |
|------|-------|---------------|
| 事务 | ACID | 无跨文档事务 |
| 一致性 | 强一致 | 近实时最终一致 |
| 查询 | 精确、JOIN | 全文、聚合、模糊 |
| 写入 | 频繁更新 | 追加为主 |
| 场景 | 订单、账户 | 商品搜索、日志 |

**原则**：**MySQL 为 Source of Truth，ES 为读模型（CQRS）**。

## 九、同步方案概览

### 9.1 方案对比

| 方案 | 一致性 | 复杂度 | 推荐度 |
|------|--------|--------|--------|
| **Canal + MQ + ES** | 最终一致 | 中 | ⭐⭐⭐⭐⭐ |
| **Debezium + Kafka** | 最终一致 | 中 | ⭐⭐⭐⭐⭐ |
| 双写 | 难保证 | 低 | ⭐ 不推荐 |
| 定时全量 | 延迟大 | 低 | 补充 |
| Logstash JDBC | 增量 polling | 低 | 小数据量 |

### 9.2 Canal + MQ + ES（国内主流）

```
┌────────┐    binlog    ┌───────┐    MQ    ┌──────────┐    Bulk   ┌────┐
│ MySQL  │ ───────────► │ Canal │ ───────► │ Consumer │ ────────► │ ES │
└────────┘              └───────┘          └──────────┘           └────┘
```

**流程**：
1. Canal 伪装 MySQL Slave，接收 binlog
2. 解析 INSERT/UPDATE/DELETE 事件
3. 发 Kafka/RocketMQ
4. ES Consumer 消费，转 ES Bulk API 写入

**优点**：
- 业务无侵入
- 解耦（MQ 缓冲）
- 可回放

### 9.3 Canal 配置要点

| 配置 | 说明 |
|------|------|
| binlog_format=ROW | 必须 ROW 模式 |
| canal.instance.filter.regex | 订阅表 |
| GTID / position | 断点续传 |

### 9.4 ES Consumer 设计

```java
// 伪代码
void onMessage(CanalEntry entry) {
    switch (entry.getEventType()) {
        case INSERT:
        case UPDATE:
            bulkIndex(entry.getTable(), entry.getPk(), toJson(entry));
            break;
        case DELETE:
            bulkDelete(entry.getTable(), entry.getPk());
            break;
    }
}
```

**要点**：
- **_id = 主键**，幂等
- **Bulk 批量**写入
- **失败重试** + DLQ
- **顺序**：同主键进同 MQ 分区（可选）

### 9.5 全量 + 增量

```
1. 首次：DataX / mysqldump → ES 全量导入
2. 记录 binlog position
3. 启动 Canal 增量
4. 定期对账（可选）
```

**避免**：全量期间增量丢失 → 全量完成后接增量 position。

### 9.6 Debezium（Kafka Connect）

```
MySQL → Debezium Connector → Kafka Topic → ES Sink Connector
```

**优点**：Kafka 生态统一；**Schema Registry** 支持。

### 9.7 双写的问题

```
Service → MySQL
Service → ES（同步）
```

| 问题 | 说明 |
|------|------|
| 部分成功 | MySQL 成功 ES 失败 → 不一致 |
| 事务边界 | 无法跨系统事务 |
| 耦合 | 业务代码复杂 |

**仅适合**：极简场景或过渡期。

## 十、数据一致性保障

### 10.1 延迟

| 环节 | 延迟 |
|------|------|
| Canal 解析 | ms 级 |
| MQ | ms~s |
| ES refresh | 默认 1s |
| **总** | 通常 1~3s |

### 10.2 对账

```
定时任务：
  MySQL COUNT / MAX(updated_at) vs ES
  抽样比对主键字段
  差异 → 补偿写入 ES
```

### 10.3 删除同步

- 物理删除：Canal DELETE 事件 → ES delete
- 逻辑删除：UPDATE status=deleted → ES 过滤或 delete

### 10.4 字段变更

Mapping 变更需 Reindex；CDC Consumer 需兼容新旧字段。

## 十一、深分页与 Scroll

### 11.1 from/size 限制

默认 `max_result_window=10000`，超过报错。

### 11.2 search_after

```json
{
  "size": 10,
  "sort": [{ "created_at": "asc" }, { "_id": "asc" }],
  "search_after": [1625097600000, "doc_100"]
}
```

**适用**：实时深分页、用户翻页。

### 11.3 Scroll

```json
POST /index/_search?scroll=5m
GET /_search/scroll
```

**适用**：离线导出、Reindex；**不适合**实时用户分页（快照占用资源）。

### 11.4 PIT（Point In Time）

7.10+ 结合 search_after，一致性快照读。

## 十四、案例：电商商品搜索同步

### 14.1 架构

```
MySQL product 表
  → Canal（HA 双节点）
  → Kafka topic: product-sync
  → ES Consumer × 4（Bulk 500 条/批）
  → ES Index: products（5 主分片，1 副本）
  → 别名 products 供搜索服务查询
```

### 14.2 关键参数

| 组件 | 配置 |
|------|------|
| ES | refresh_interval=1s，bulk 5MB |
| Kafka | 按 product_id 分区，保顺序可选 |
| Consumer | _id=product_id，失败 3 次进 DLQ |

### 14.3 故障

| 故障 | 处理 |
|------|------|
| ES yellow | 检查副本分配、磁盘 |
| 同步延迟 5min | Kafka Lag，扩容 Consumer |
| Mapping 变更 | 新建 Index Reindex + 别名 |
