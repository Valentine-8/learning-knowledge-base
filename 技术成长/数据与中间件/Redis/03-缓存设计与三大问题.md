# 03 · 缓存设计与三大问题

> **目标读者**：7 年 Java 后端工程师，需能设计 Cache Aside / 多级缓存方案，处理穿透/击穿/雪崩，并在缓存与 DB 一致性之间做工程权衡。
> **预计阅读**：50 min · **难度**：★★★★

---

## 1. 总览：缓存架构在系统中的位置

```
┌──────────┐     ┌─────────────┐     ┌─────────┐     ┌──────────┐
│  Client  │────→│  App Server │────→│  Redis  │     │   MySQL  │
└──────────┘     └──────┬──────┘     └────┬────┘     └────▲─────┘
                        │                 │               │
                        │    未命中 ──────┴───────────────┘
                        │
                        └── 本地缓存 (Caffeine) 可选
```

| 角色 | 说明 |
|------|------|
| 缓存 | 挡在 DB 前，降低延迟与 DB QPS |
| 代价 | 一致性、穿透/击穿/雪崩、内存成本 |
| 原则 | 缓存是**衍生数据**，应能重建；核心账务不以缓存为准 |

---

## 2. 经典模式：Cache Aside（旁路缓存）

### 2.1 读路径

```
1. 读 Redis key
2. 命中 → 返回
3. 未命中 → 读 DB → 写 Redis → 返回
```

```java
// 伪代码
public User getUser(Long id) {
    String key = "user:" + id;
    User u = redis.get(key);
    if (u != null) return u;
    u = userDao.selectById(id);
    if (u != null) {
        redis.setex(key, 3600 + random(300), u);
    }
    return u;
}
```

### 2.2 写路径（推荐）

```
写 DB 成功 → 删除缓存（而非更新缓存）
```

| 写缓存 vs 删缓存 | 结论 |
|------------------|------|
| 更新缓存 | 并发写可能乱序，脏数据 |
| **删除缓存** | 下次读回填，简单可靠 |

**为何先写 DB 再删缓存**（常见方案）：

```
若先删缓存再写 DB：
  线程 A 删缓存 → 线程 B 读未命中 → B 读旧 DB → B 写旧值入缓存 → A 写 DB
  → 缓存长期脏数据

先写 DB 再删缓存：仍可能极短窗口不一致，但概率更低；可接受最终一致
```

### 2.3 延迟双删

```
1. 删缓存
2. 写 DB
3. sleep 500ms（大于一次读 DB 耗时）
4. 再删缓存
```

适用于删缓存失败或主从延迟导致从库旧读回填。**缺点**：sleep 阻塞、时间难估。

## 3. 缓存穿透

### 3.1 现象

查询**不存在**的数据（如 id=-1、恶意随机 id），缓存无、DB 也无，每次打穿 DB。

```
攻击流量: GET /user?id=random_uuid
           ↓
        Redis miss
           ↓
        MySQL 全表/索引扫（高 QPS 压垮 DB）
```

### 3.2 解法对比

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **缓存空值** | miss 后 `SET key "" EX 60` | 实现简单 | 占内存、需短 TTL |
| **布隆过滤器** | 先判「一定不存在」则直接拒 | 省 DB | 有误杀、无删除（需重建） |
| **参数校验** | id 范围、格式校验 | 挡非法请求 | 业务相关 |
| **接口限流** | 网关/令牌桶 | 防刷 | 不解决合法不存在 |

### 3.3 布隆过滤器

```
hash1(key) ──→ bit array ──→ 全 1 则「可能存在」
hash2(key) ──→
hash3(key) ──→ 有 0 则「一定不存在」
```

```bash
# Redis 4.0+ RedisBloom 模块（云厂商常内置）
redis-cli BF.ADD users:bf "user:1001"
redis-cli BF.EXISTS users:bf "user:999999"
# (integer) 0  → 一定不存在，别查 DB
```

**生产组合**：布隆 + 空值缓存（防布隆误判）+ 接口校验。

### 3.4 案例

**电商 SKU 爬虫**：随机 skuId 查详情，DB QPS 暴涨。上线布隆（全量 sku 预热）+ 空值 TTL 120s，DB 压力降 95%。

## 4. 缓存击穿

### 4.1 现象

**单个热点 key** 过期瞬间，大量并发同时 miss，齐刷刷打 DB。

```
热点 key: product:hot:iphone  TTL 到期
  10万并发同时 GET → 全部 miss → 10万次 DB 查询
```

### 4.2 解法

| 方案 | 实现 | 适用 |
|------|------|------|
| **互斥锁重建** | miss 后仅一线程查 DB，其余等待或重试 | 通用 |
| **逻辑过期** | 不设 TTL，value 内带 expireTime，异步线程更新 | 热点、允许短暂旧值 |
| **永不过期 + 后台刷新** | 定时任务提前更新 | 配置类、榜单 |
| **热点探测** | 自动识别 hot key 加长 TTL / 本地缓存 | 大促 |

### 4.3 互斥锁（Redis SET NX）

```java
public Product getProduct(String id) {
    String key = "product:" + id;
    String json = redis.get(key);
    if (json != null) return parse(json);

    String lockKey = "lock:product:" + id;
    if (redis.set(lockKey, "1", "NX", "EX", 10)) {
        try {
            json = redis.get(key);  // double check
            if (json != null) return parse(json);
            Product p = productDao.load(id);
            redis.setex(key, 3600, serialize(p));
            return p;
        } finally {
            redis.del(lockKey);
        }
    } else {
        Thread.sleep(50);
        return getProduct(id);  // 或直接返回降级数据
    }
}
```

### 4.4 逻辑过期

```
value = { data: {...}, expireAt: 1735689600000 }

读时:
  if now < expireAt → 直接返回 data（可能旧）
  else → 尝试获取锁，单线程异步刷新，其他线程仍返回旧 data
```

**对比**：互斥锁第一次等待；逻辑过期无等待但可能读旧值。

## 5. 缓存雪崩

### 5.1 现象

| 类型 | 原因 |
|------|------|
| 过期雪崩 | 大量 key **同一时刻** TTL 到期 |
| 故障雪崩 | Redis **集群宕机**，流量全打 DB |
| 温数据集体失效 | 批量重启、flush、版本发布删 key |

### 5.2 解法

```
过期时间 + random(0, 300)     # 打散 TTL
多级缓存 + 限流降级            # Redis 挂仍可用
Redis 高可用 Sentinel/Cluster
本地缓存短 TTL 挡一层
熔断：DB 超时返回默认值
```

```java
int ttl = 3600 + ThreadLocalRandom.current().nextInt(600);
redis.setex(key, ttl, value);
```

### 5.3 限流与降级

```
Redis 不可用检测 ──→ 开关打开 ──→ 读降级（静态页/旧本地缓存）
                              ──→ 写直接 DB + 异步重建
```

**Hystrix / Sentinel**：DB 线程池隔离，超时快速失败。

## 6. 缓存与 DB 一致性

### 6.1 一致性级别

| 级别 | 说明 | 手段 |
|------|------|------|
| 强一致 | 读始终最新 | 不用缓存或读写都走 DB |
| 最终一致 | 短暂不一致可接受 | Cache Aside + 删缓存 |
| 准实时 | 秒级同步 | Canal + MQ 删缓存 |

### 6.2 先删缓存 vs 先写 DB（再论）

| 顺序 | 风险 |
|------|------|
| 先删后写 | 旧值回填（见 2.2） |
| **先写后删** | 删缓存失败 → 脏读；需重试/订阅 binlog |
| 先写后更新 | 并发写顺序问题 |

**删缓存失败**：写 DB 后发 MQ，消费者重试 DEL；或 Canal 监听 binlog 删缓存。

### 6.3 订阅 Binlog（Canal）

```
MySQL Binlog ──→ Canal ──→ MQ ──→ 消费者 DEL redis key
```

| 优点 | 缺点 |
|------|------|
| 解耦、最终一致 | 链路长、延迟、运维成本 |
| 删缓存失败可重试 | 需处理乱序、幂等 |

**幂等**：DEL 天然幂等；UPDATE 缓存需 version 字段。

### 6.4 主从延迟与缓存

```
写主库 → 删缓存 → 读从库（旧）→ 回填旧缓存
```

解决：关键读走主库；延迟双删；Canal 按 binlog 顺序删。

## 7. 多级缓存

### 7.1 架构

```
L1: 本地缓存 (Caffeine)  TTL 30s~5min  命中率 90%+
L2: Redis 集群           TTL 30min~24h
L3: MySQL
```

```
请求 → L1 hit? → return
     → L2 hit? → 回填 L1 → return
     → DB → 写 L2 + L1 → return
```

### 7.2 本地缓存注意

| 问题 | 方案 |
|------|------|
| 多实例不一致 | 短 TTL + Redis Pub/Sub 广播失效 |
| 内存占用 | maximumSize + W-TinyLFU 淘汰 |
| 热 key | 本地缓存极有效 |

```java
@Cacheable(value = "product", cacheManager = "caffeineCacheManager")
public Product getById(Long id) { ... }
```

### 7.3 更新策略

```
写 DB → 删 Redis → 发 LocalCacheInvalidate 消息 → 各节点删 L1
```

**不要**只删 Redis 忽略 L1，否则 L1 脏读最长 = L1 TTL。

## 8. 缓存设计 Checklist

| 项 | 问题 |
|----|------|
| Key 设计 | 业务前缀、版本号 `v2:user:{id}`、避免过大 |
| TTL | 必设；加随机；热点单独策略 |
| 值大小 | 单 value < 10KB 为宜；大对象拆分 |
| 穿透 | 布隆 / 空值 / 校验 |
| 击穿 | 互斥锁 / 逻辑过期 |
| 雪崩 | 随机 TTL / 高可用 / 限流 |
| 一致性 | 写 DB 删缓存；Canal 兜底 |
| 监控 | 命中率、miss QPS、慢查询 |

```bash
redis-cli INFO stats | grep keyspace
# keyspace_hits:...
# keyspace_misses:...
# 命中率 = hits / (hits + misses)
```

## 9. 其他缓存模式（了解）

| 模式 | 读 | 写 |
|------|----|----|
| Cache Aside | 应用管缓存 | 应用写 DB 删缓存 |
| Read Through | 缓存层代查 DB | — |
| Write Through | — | 同步写缓存+DB |
| Write Behind | — | 先写缓存，异步刷 DB |

Redis 场景 **99% Cache Aside**；Write Behind 用于写多读少、可丢部分写（计数近似）。

## 10. 面试 Q&A

| 问 | 答 |
|----|-----|
| 穿透/击穿/雪崩区别？ | 穿透：不存在；击穿：热点过期；雪崩：大量同时失效或 Redis 挂 |
| 为何删缓存不更新？ | 并发写乱序、双写复杂；删+懒加载简单 |
| 布隆误判？ | 不存在可能判存在 → 查 DB；不存在不会误判 |
| 互斥锁用什么？ | SET NX EX + finally DEL；或 Redisson |
| 逻辑过期缺点？ | 可能返回旧数据，需异步刷新 |
| 多级缓存一致性？ | 写删 Redis + 广播删本地缓存 |
| 缓存命中率多少合适？ | 视业务，核心读接口 95%+；低需查 key/TTL/穿透 |

## 11. 生产案例

**案例 1：大促击穿**

秒杀商品 key 1s 过期，DB 瞬时 5000 QPS。改逻辑过期 + 预热 + 永不过期后台刷新。

**案例 2：Canal 延迟 3s**

用户改昵称后 3s 内看到旧名。产品接受；支付余额改走 DB 主库读。

**案例 3：Caffeine 未同步**

只删 Redis，L1 脏 5 分钟。加 Redis Pub/Sub topic `cache:invalidate`。

**案例 4：空值攻击**

恶意 id 灌满 Redis。空值 TTL 60s + 布隆 + 单 IP 限流 100/s。

## 13. 本章小结

```
穿透 → 不存在的数据     → 布隆 + 空值 + 校验
击穿 → 热点 key 过期     → 互斥锁 / 逻辑过期
雪崩 → 集体失效 / 宕机   → 随机 TTL + HA + 限流降级
一致性 → 无银弹          → Cache Aside 先写 DB 删缓存 + Canal 兜底
```

## 14. 缓存预热与降级

### 14.1 预热

```
上线前 / 大促前:
  1. 从 DB 批量加载热 key 写入 Redis
  2. 本地缓存同步预热
  3. 布隆过滤器加载全量合法 id
```

```bash
# 批量导入示例（pipeline）
redis-cli --pipe <<EOF
SET product:1001 "{...}" EX 3600
SET product:1002 "{...}" EX 3600
EOF
```

### 14.2 降级策略

| 级别 | 触发 | 行为 |
|------|------|------|
| L1 | Redis 超时 | 重试 1 次 |
| L2 | 仍失败 | 读本地缓存旧值 |
| L3 | 无本地 | 读 DB + 限流 |
| L4 | DB 超时 | 返回默认值 / 静态页 |

**开关**：配置中心 `cache.degrade=true`，运维一键打开。

## 15. 与 Spring Cache 集成

```java
@Cacheable(value = "users", key = "#id", unless = "#result == null")
public User findById(Long id) {
    return userDao.selectById(id);
}

@CacheEvict(value = "users", key = "#user.id")
public void updateUser(User user) {
    userDao.update(user);
}
```

| 注意点 | 说明 |
|--------|------|
| 默认序列化 | JSON 注意类型；或 Kryo |
| 事务 | `@CacheEvict` 默认 after，需与 DB 事务协调 |
| 多实例 | 需 Redis 作 L2，本地 Caffeine 作 L1 并同步失效 |
