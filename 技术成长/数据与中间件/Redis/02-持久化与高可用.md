# 02 · 持久化与高可用

> **目标读者**：7 年 Java 后端工程师，需能讲清 RDB/AOF/混合持久化、主从复制、Sentinel 故障转移、Cluster 槽位路由，并能在 RPO/RTO 权衡中做架构选型。
> **预计阅读**：60 min · **难度**：★★★★

## 1. 总览：数据安全与可用性

```
                    ┌─────────────────────────────────────┐
                    │           持久化（防进程崩溃丢数据）    │
                    │   RDB 快照 │ AOF 日志 │ 混合持久化    │
                    └──────────────────┬──────────────────┘
                                       │
                    ┌──────────────────▼──────────────────┐
                    │           高可用（防节点宕机）         │
                    │   主从复制 │ Sentinel │ Cluster      │
                    └─────────────────────────────────────┘
```

| 维度 | 持久化 | 高可用 |
|------|--------|--------|
| 解决 | 进程重启后数据恢复 | 节点故障后服务连续 |
| 指标 | RPO（可丢多少数据） | RTO（恢复时间） |
| 组合 | 单机也要开 AOF/RDB | 生产至少主从 + 哨兵 |

## 2. RDB（Redis Database）

### 2.1 原理

RDB 是某一时刻内存数据的**二进制快照**（compact），适合备份与快速冷启动。

```
主线程 ──fork──→ 子进程
  │                  │
  │ 继续处理写        │ 遍历内存写 temp.rdb
  │ (Copy-On-Write)  │
  └──────────────────┴──→ 完成后 rename dump.rdb
```

**COW**：fork 后父子共享物理页，写时复制；快照期间内存可能**翻倍**（写密集时）。

### 2.2 触发方式

| 方式 | 配置/命令 |
|------|-----------|
| 自动 | `save 900 1` / `save 300 10` / `save 60 10000` |
| 手动 | `SAVE`（阻塞）、`BGSAVE`（后台） |
| 关闭 | `SHUTDOWN SAVE` |
| 主从全量 | 从库首次同步触发主库 BGSAVE |

```bash
redis-cli CONFIG GET save
redis-cli BGSAVE
redis-cli LASTSAVE
# 上次成功 RDB 时间戳

redis-cli INFO persistence | grep rdb
# rdb_bgsave_in_progress:0
# rdb_last_save_time:...
```

### 2.3 优缺点

| 优点 | 缺点 |
|------|------|
| 文件紧凑，恢复极快 | 两次快照间崩溃会丢数据 |
| 适合冷备、灾备 | fork 时大内存实例可能卡顿 |
| 对读性能影响小 | 写频繁时 COW 内存压力 |

**RPO 估算**：若 `save 900 1`，最坏丢 15 分钟数据（若未配合 AOF）。

## 3. AOF（Append Only File）

### 3.1 原理

每条**写命令**追加到 AOF 文件；重启时 **replay** 命令恢复状态。

```
客户端 SET k v ──→ 执行内存 ──→ 追加 AOF buffer ──→ 刷盘 (fsync 策略)
```

### 3.2 刷盘策略

| appendfsync | 行为 | RPO | 性能 |
|-------------|------|-----|------|
| always | 每条写 fsync | 几乎 0 | 最慢 |
| **everysec** | 每秒 fsync（默认） | 最多丢 1s | 推荐 |
| no | 由 OS 决定 | 可能丢较多 | 最快 |

```bash
redis-cli CONFIG GET appendfsync
# 1) "appendfsync"
# 2) "everysec"

redis-cli CONFIG SET appendfsync everysec
```

### 3.3 AOF 重写（Rewrite）

AOF 会膨胀（如 INCR 100 万次 → 一条 SET）。**BGREWRITEAOF** 子进程根据**当前内存**生成最小命令集。

```
旧 AOF: INCR cnt × 1000000  →  新 AOF: SET cnt 1000000
```

```bash
redis-cli CONFIG GET auto-aof-rewrite-percentage
redis-cli CONFIG GET auto-aof-rewrite-min-size
redis-cli BGREWRITEAOF
```

**重写期间**：新写进 **AOF rewrite buffer**，子进程完成后合并。

### 3.4 AOF 优缺点

| 优点 | 缺点 |
|------|------|
| 耐久性更好（everysec） | 文件通常比 RDB 大 |
| 可读、易审计 | 恢复比 RDB 慢 |
| 可配置 fsync 级别 | 极端写负载 + always 性能差 |

## 4. 混合持久化（Redis 4.0+）

```
AOF 文件结构（混合开启）:
┌────────────────────┬─────────────────────────┐
│  RDB 二进制快照头   │  快照后的 AOF 增量命令    │
└────────────────────┴─────────────────────────┘
```

```conf
aof-use-rdb-preamble yes
```

| 效果 | 说明 |
|------|------|
| 恢复速度 | 先加载 RDB 头，快 |
| 耐久 | 增量 AOF 保证快照后写不丢 |
| 生产推荐 | 开启 AOF + 混合，兼顾 RPO 与恢复 |

```bash
redis-cli CONFIG GET aof-use-rdb-preamble
redis-cli INFO persistence | grep aof
# aof_enabled:1
# aof_rewrite_in_progress:0
```

## 5. 持久化选型决策

```
                    能丢分钟级数据？
                   /              \
                 是                否
                /                    \
           仅 RDB 或               AOF everysec
           RDB 低频备份            + 混合持久化
                \                    /
                 \   都要：混合 + 定期 RDB 冷备到 OSS
```

| 场景 | 建议 |
|------|------|
| 纯缓存、可重建 | 可关持久化 |
| 会话、计数 | AOF everysec |
| 金融级 | everysec + 主从 + 外部审计；强一致不依赖 Redis |
| 快速重启 | 混合持久化 |

**面试答法**：默认 **AOF everysec + aof-use-rdb-preamble yes**，同时定时 RDB 备份到对象存储。

##  6. 主从复制（Replication）

### 6.1 架构

```
        ┌─────────┐
        │ Master  │  写 + 可选读
        └────┬────┘
     ┌───────┼───────┐
     ▼       ▼       ▼
  Replica Replica Replica   读扩展、备份、故障晋升候选
```

```bash
# 从节点
redis-cli REPLICAOF 192.168.1.10 6379
redis-cli CONFIG SET replica-read-only yes

# Redis 5+ 推荐
redis-cli REPLICAOF NO ONE   # 提升为主
```

### 6.2 全量同步 vs 增量同步

```
首次 / 断线过久:
  Master ──BGSAVE──→ RDB 文件 ──→ Replica 加载
           └── replication buffer 存期间的写

断线重连（repl_backlog）:
  Master ──offset 之后的命令流──→ Replica
```

| 概念 | 说明 |
|------|------|
| replication id | 主从复制流标识 |
| offset | 复制偏移量 |
| repl_backlog | 环形缓冲区，默认 1MB，生产调大 |

```bash
redis-cli INFO replication
# role:master
# connected_slaves:2
# master_repl_offset:...
```

### 6.3 异步复制与一致性

- 复制**异步**：主库写成功即返回，从库可能落后。
- **读从库**：可能读到旧数据（**主从延迟**）。
- **等待复制**（Redis 3.0+）：`WAIT numreplicas timeout` 阻塞直到 N 个从库确认（少用，影响延迟）。

**生产案例**：订单状态写主库后立即读从库，偶发「未支付」。方案：关键读走主库、或缓存、或 WAIT（慎用）。

## 7. Sentinel（哨兵）

### 7.1 职责

| 功能 | 说明 |
|------|------|
| 监控 | Ping 主从是否可达 |
| 通知 | 故障告警 |
| 自动故障转移 | 选举新主、通知客户端 |
| 配置提供者 | 客户端问 Sentinel 获取当前主地址 |

```
┌──────────┐  ┌──────────┐  ┌──────────┐
│ Sentinel1│  │ Sentinel2│  │ Sentinel3│   至少 3 节点，奇数
└─────┬────┘  └─────┬────┘  └─────┬────┘
      │    监控 & 投票    │
      └──────────┬─────────┘
                 ▼
           Master + Replicas
```

### 7.2 故障转移流程

```
1. 主观下线 (SDOWN): 单个 Sentinel 认为主不可用
2. 客观下线 (ODOWN): 足够数量 Sentinel 同意
3. 选举 Leader Sentinel 执行故障转移
4. 从从库选新主（优先级 > offset > runid）
5. 其他从库 REPLICAOF 新主
6. 旧主恢复后变为从库
```

```bash
# sentinel.conf
sentinel monitor mymaster 127.0.0.1 6379 2
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 60000

redis-cli -p 26379 SENTINEL masters
redis-cli -p 26379 SENTINEL get-master-addr-by-name mymaster
```

### 7.3 Java 客户端

Spring / Lettuce / Jedis 配置 **Sentinel 节点列表** + master name，自动感知新主。

**注意**：故障转移期间短暂不可写；分布式锁在切换窗口可能出问题（见第 04 章）。

## 8. Redis Cluster

### 8.1 为何需要 Cluster

| 问题 | 单主方案 | Cluster |
|------|----------|---------|
| 内存上限 | 单机 RAM | 16384 槽分片多主 |
| 写 QPS | 单线程单主 | 多主水平扩展 |
| 高可用 | Sentinel + 单主 | 每分片主从 + 自动转移 |

### 8.2 槽位（Hash Slot）

**16384 个槽**（0～16383），每个 key 映射到一槽：

```
slot = CRC16(key) & 16383
```

```
Cluster 3 主 3 从示例:
┌─────────────┬─────────────┬─────────────┐
│ Master A    │ Master B    │ Master C    │
│ slot 0-5460 │ 5461-10922  │ 10923-16383 │
│ Replica A'  │ Replica B'  │ Replica C'  │
└─────────────┴─────────────┴─────────────┘
```

**Hash Tag**：`{user}:1001` 与 `{user}:1002` 同 tag 强制同槽，便于 multi-key 事务。

```bash
redis-cli CLUSTER INFO
redis-cli CLUSTER NODES
redis-cli CLUSTER KEYSLOT user:1001
# (integer) 9189

redis-cli -c -p 7000 SET user:{shard1}:1001 alice
# -c 开启集群路由，MOVED/ASK 自动跳转
```

### 8.3 路由与重定向

| 回复 | 含义 |
|------|------|
| MOVED | 槽已永久迁移到另一节点 |
| ASK | 迁移中临时重定向 |

客户端（Lettuce Cluster）维护 **slot → node** 缓存，大部分请求直达。

### 8.4 扩容与缩容

```
添加节点 ──→ CLUSTER MEET ──→ 分配空槽 ──→ 迁移槽 (MIGRATE) ──→ 平衡
```

- 迁移期间 **ASK** 双读；业务低峰操作。
- **大 key** 迁移阻塞，需先拆 key。

### 8.5 Cluster 限制

| 限制 | 说明 |
|------|------|
| 多 key 操作 | 同槽才行；Lua 同理 |
| 事务 | 同槽 |
| 数据库号 | 仅 db 0 |
| 强一致 | 无；仍异步复制 |

## 9. 架构选型对比

| 架构 | 节点数 | 数据分片 | 自动故障转移 | 适用 |
|------|--------|----------|--------------|------|
| 单机 | 1 | 否 | 否 | 开发/小流量 |
| 主从 | 1 主 N 从 | 否 | 否（需 Sentinel） | 读多写少 |
| Sentinel + 主从 | 3+ Sentinel + 主从 | 否 | 是 | 数据量 < 单机 RAM |
| Cluster | 6+（3 主 3 从起） | 是 | 是 | 大内存、高写 QPS |

```
数据量 > 单机 80% 内存 或 写 QPS 顶满 ──→ 规划 Cluster
否则 Sentinel + 主从 更简单
```

## 10. 面试 Q&A

| 问 | 答 |
|----|-----|
| RDB 和 AOF 区别？ | RDB 快照、恢复快、可能丢区间数据；AOF 日志、更耐久、文件大 |
| 混合持久化？ | AOF 重写时用 RDB 格式写前缀 + 增量命令 |
| fork 为何阻塞？ | 内存大时页表复制耗 CPU；写密集 COW 内存涨 |
| 主从复制原理？ | 全量 RDB + 增量命令流；backlog 断线重连 |
| 主从延迟原因？ | 异步复制、从库单线程、网络、大 key 同步 |
| Sentinel 如何选新主？ | 过滤下线/断连过久；replica-priority；复制 offset 最大 |
| 为何 16384 槽？ | CRC16 结果 16bit，过多槽心跳大；过少迁移粒度粗 |
| Cluster 同 multi key？ | 需 hash tag 同槽 |

## 11. 生产案例

**案例 1：AOF 文件 80GB 重启 6 小时**

未开混合、未 rewrite。解决：BGREWRITEAOF、开混合、降 maxmemory、拆大 key。

**案例 2：BGSAVE 导致 latency spike**

32GB 实例 fork 卡顿 300ms。解决：`save ""` 关自动 RDB 改低峰 cron BGSAVE、升级内核透明大页 THP 关闭、用 AOF 混合。

**案例 3：Sentinel 脑裂误切主**

网络分区导致双主写入。解决：合理 `min-replicas-to-write`、应用层校验、Cluster 或强一致存储。

**案例 4：Cluster 扩容抖动**

批量 MIGRATE 大 Hash。解决：低峰、限速、`redis-cli --cluster rebalance`、提前 `--bigkeys` 治理。
