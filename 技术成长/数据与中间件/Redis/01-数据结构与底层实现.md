# 01 · 数据结构与底层实现

> **目标读者**：7 年 Java 后端工程师，需能讲清 Redis 五种基本类型、高级类型、底层编码及时间复杂度，并在面试与架构选型中快速匹配场景。
> **预计阅读**：60 min · **难度**：★★★★

## 1. 总览：Redis 对象模型

```
┌─────────────────────────────────────────────────────────────────┐
│                     Redis Server (单线程命令执行)                 │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────────────┐  │
│  │ 客户端连接   │  │ 事件循环     │  │ 内存数据库               │  │
│  │ (epoll/kqueue)│  │ aeEventLoop │  │ key → redisObject       │  │
│  └─────────────┘  └─────────────┘  └─────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘

redisObject 结构（逻辑视图）：
┌──────────┬──────────┬──────────┬────────────────────────────┐
│  type    │ encoding │  lru     │  ptr → 具体底层结构          │
│ (5/8种)  │ (编码)   │  24bit   │  SDS / dict / skiplist ... │
└──────────┴──────────┴──────────┴────────────────────────────┘
```

Redis 对外暴露的是**键值对**；每个 value 是一个 `redisObject`，通过 `type` 决定语义、通过 `encoding` 决定底层实现。同一逻辑类型在不同数据规模下会**编码转换**（如 Hash 小对象用 listpack，大对象用 hashtable）。

**查看对象编码**：

```bash
redis-cli SET user:1001 "alice"
redis-cli OBJECT ENCODING user:1001
# "embstr" 或 "raw"（取决于字符串长度）

redis-cli HSET profile:1001 name bob age 25
redis-cli OBJECT ENCODING profile:1001
# "listpack" 或 "hashtable"
```

## 2. SDS（Simple Dynamic String）

C 语言原生字符串以 `\0` 结尾，无法 O(1) 取长度，且拼接易溢出。Redis 自研 **SDS** 作为 String 类型的底层（及 key 的底层）。

### 2.1 SDS 结构

```
┌──────┬──────┬─────────────────────────┬───┐
│ len  │ alloc│  char buf[]             │\0 │
│ 已用  │ 分配  │  实际字符               │   │
└──────┴──────┴─────────────────────────┴───┘
```

| 字段 | 作用 |
|------|------|
| len | 已使用长度，O(1) 获取 `STRLEN` |
| alloc | 预分配容量，减少扩容次数 |
| buf | 字节数组，兼容部分 C 函数 |
| 二进制安全 | 可存 `\0`、图片、序列化 blob |

### 2.2 编码：embstr vs raw

| 编码 | 条件 | 特点 |
|------|------|------|
| embstr | 字符串 ≤ 44 字节（Redis 7 约 44） | redisObject 与 SDS **一次分配**，释放一次，只读优化 |
| raw | 更长字符串 | object 与 SDS **分开分配**，可修改 append |

```bash
redis-cli SET short "hello"
redis-cli OBJECT ENCODING short
# "embstr"

redis-cli SET long_key "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
redis-cli OBJECT ENCODING long_key
# "raw"
```

### 2.3 int 编码

整数值可用 `int` 编码存储，节省内存：

```bash
redis-cli SET counter 10086
redis-cli OBJECT ENCODING counter
# "int"

redis-cli APPEND counter x
redis-cli OBJECT ENCODING counter
# "embstr"  — 修改后降级
```

### 2.4 应用场景与复杂度

| 操作 | 命令 | 时间复杂度 |
|------|------|------------|
| 读/写 | GET / SET | O(1) |
| 自增 | INCR / INCRBY | O(1) |
| 追加 | APPEND | O(N) N=追加长度 |
| 位操作 | SETBIT / GETBIT | O(1) |
| 批量 | MGET / MSET | O(N) |

**典型场景**：缓存 JSON、分布式 ID 计数、Session、Bitmap 签到、分布式锁 value。

## 3. dict（哈希表）

Hash、Set 的底层之一；整个 Redis 的 **keyspace** 也是一张大 dict。

### 3.1 结构

```
dict
├── ht[2]          # 两个哈希表，用于 rehash
│   ├── ht[0]      # 主表
│   └── ht[1]      # rehash 时的新表
├── rehashidx      # -1 表示未 rehash
└── type / privdata
```

**渐进式 rehash**：扩容时不一次性迁移，每次增删改查顺带迁移若干 bucket，避免长时间阻塞。

```
rehash 前:  ht[0] ████████████
            ht[1] (空)

rehash 中:  ht[0] ████░░░░░░░░  ← 已迁移部分
            ht[1] ████░░░░░░░░  ← 新表同步增长
            rehashidx 指向当前迁移位置

rehash 后:  ht[0] = ht[1], ht[1] 清空, rehashidx = -1
```

### 3.2 哈希冲突与负载因子

- 负载因子 = 已用节点数 / bucket 数
- 默认：`resize 阈值 1`，`force resize 5`（无 rehash 时强制）
- 冲突解决：**链地址法**（每个 bucket 链表）

### 3.3 Hash 类型编码

| 编码 | 条件（Redis 7 大致） | 说明 |
|------|----------------------|------|
| listpack | 字段数 ≤ 512 且 单值 ≤ 64B | 紧凑连续内存 |
| hashtable | 超出阈值 | dict 实现 |

```bash
redis-cli HSET user:1 name "张三" age "28" city "上海"
redis-cli OBJECT ENCODING user:1
# "listpack"

redis-cli HINCRBY user:1 age 1
redis-cli HGET user:1 age
# "29"
```

**应用**：对象字段缓存（用户信息、商品属性），比 String 存 JSON 更省内存、可单字段更新。

| 操作 | 复杂度 |
|------|--------|
| HGET / HSET 单字段 | O(1) |
| HGETALL | O(N) N=字段数 |
| HLEN | O(1) |

## 4. skiplist（跳表）+ dict

**ZSet（有序集合）** 底层：`skiplist` 按 score 排序 + `dict` 按 member 查 score，两者共享 member 指针。

### 4.1 跳表结构

```
level 3:  head ──────────────────────────────→ node7
level 2:  head ──────────→ node3 ────────────→ node7
level 1:  head → node1 → node3 → node5 → node7 → NULL
level 0:  head → node1 → node3 → node5 → node7 → NULL
          (score: 1)   (3)      (5)      (7)
```

| 特性 | 说明 |
|------|------|
| 平均查找 | O(log N) |
| 插入/删除 | O(log N) |
| 范围查询 | O(log N + M) M 为结果数 |
| 层级 | 随机 1～32 层，概率 p=0.25 |

**为何不用红黑树**：实现更简单、范围查询友好（链表式 level 0）、与 dict 组合灵活。

### 4.2 ZSet 编码

| 编码 | 条件 |
|------|------|
| listpack | 元素少且 member/score 短 |
| skiplist | 超出阈值 |

```bash
redis-cli ZADD rank:game 9500 "player_a" 8800 "player_b" 9200 "player_c"
redis-cli ZREVRANGE rank:game 0 2 WITHSCORES
# 1) "player_a" 2) "9500" ...

redis-cli ZRANK rank:game "player_b"
# (integer) 2
```

### 4.3 应用场景

| 场景 | 命令 |
|------|------|
| 排行榜 | ZADD / ZREVRANGE |
| 延迟队列 | ZADD score=执行时间戳，ZRANGEBYSCORE 轮询 |
| 限流滑动窗口 | ZADD + ZREMRANGEBYSCORE |
| GEO | 底层基于 ZSet |

| 操作 | 复杂度 |
|------|--------|
| ZADD | O(log N) |
| ZSCORE | O(1)（dict） |
| ZRANGE | O(log N + M) |

## 5. ziplist / listpack 与 quicklist

### 5.1 历史：ziplist

ziplist 是**连续内存**紧凑结构，存 entry 序列，节省指针开销。问题：连锁更新（某 entry 变大导致后续全搬）、实现复杂。

```
ziplist: [zlbytes|zltail|zllen|entry1|entry2|...|zlend]
```

Redis 6.2+ 逐步用 **listpack** 替代 ziplist 作为 Hash/ZSet/List 的小对象编码。

### 5.2 listpack

```
listpack: [total_bytes|num_elements|element1|element2|...|end]
```

每个 element 带 **backlen** 反向长度，避免 ziplist 的级联更新问题。

### 5.3 List：quicklist

List 底层为 **quicklist** = 双向链表 + 每个节点内嵌 **listpack**（Redis 7 默认）。

```
quicklist
  head ──→ [ listpack: a,b,c ] ←→ [ listpack: d,e ] ←→ ...
```

| 优点 | 说明 |
|------|------|
| 折中 | 链表 O(1) 头尾插入 + listpack 节点内紧凑 |
| 配置 | `list-max-listpack-size` 控制单节点大小 |

```bash
redis-cli LPUSH queue:task "job1" "job2" "job3"
redis-cli RPOP queue:task
# "job1"

redis-cli LRANGE queue:task 0 -1
```

**生产建议**：简单队列可用 List；需要 ACK、消费组、持久化追溯用 **Stream**。

| 操作 | 复杂度 |
|------|--------|
| LPUSH / RPOP | O(1) |
| LINDEX | O(N) |
| LRANGE | O(S+N) S=start 偏移 |

## 6. intset（整数集合）

Set 在**全为整数**且元素 ≤ 512（可配置）时用 intset，否则 hashtable。

```bash
redis-cli SADD tags:1 1 2 3 100
redis-cli OBJECT ENCODING tags:1
# "intset"

redis-cli SADD tags:1 "hello"
redis-cli OBJECT ENCODING tags:1
# "hashtable"
```

| 操作 | intset | hashtable |
|------|--------|-----------|
| SADD | O(N) 有序数组插入 | O(1) |
| SISMEMBER | O(log N) 二分 | O(1) |
| SMEMBERS | O(N) | O(N) |

**应用**：标签去重、共同好友（SINTER）、抽奖池（SPOP）。

## 7. 高级类型概览

### 7.1 Stream

```
Stream: radix tree 存 listpack 链，支持 Consumer Group
```

```bash
redis-cli XADD orders * user_id 1001 amount 99.9
redis-cli XREAD COUNT 10 STREAMS orders 0
redis-cli XGROUP CREATE orders grp1 $ MKSTREAM
redis-cli XREADGROUP GROUP grp1 consumer1 COUNT 1 STREAMS orders >
```

**场景**：轻量 MQ、日志采集；高吞吐、复杂路由仍选 Kafka/RocketMQ。

### 7.2 Bitmap / HyperLogLog / GEO

| 类型 | 底层 | 场景 |
|------|------|------|
| Bitmap | String (SDS) 位操作 | 签到、在线状态 |
| HyperLogLog | 特殊结构 | UV 近似统计，误差 ~0.81% |
| GEO | ZSet (geohash) | 附近的人、距离计算 |

```bash
redis-cli SETBIT sign:202507:u1001 15 1
redis-cli GETBIT sign:202507:u1001 15
# (integer) 1

redis-cli PFADD uv:page:home user_a user_b user_a
redis-cli PFCOUNT uv:page:home
# (integer) 2

redis-cli GEOADD stores 121.47 31.23 "store_sh"
redis-cli GEORADIUS stores 121.48 31.24 5 km WITHDIST
```

## 8. 编码转换与内存优化

### 8.1 转换触发（只升不降，除特殊情况）

| 类型 | 触发条件 |
|------|----------|
| String | int → embstr/raw（APPEND 等） |
| Hash | listpack → hashtable（字段/值过大） |
| Set | intset → hashtable（非整数元素） |
| ZSet | listpack → skiplist |
| List | 始终 quicklist |

### 8.2 内存优化配置

```conf
# redis.conf
hash-max-listpack-entries 512
hash-max-listpack-value 64
set-max-intset-entries 512
zset-max-listpack-entries 128
zset-max-listpack-value 64
```

**生产案例**：商品 SKU 属性 Hash 字段多、值长，大量 key 从 listpack 升为 hashtable，内存涨 30%。优化：拆字段、缩短 value、或改用 String + 压缩。

## 9. 单线程与命令原子性

```
客户端 A ──┐
客户端 B ──┼──→ 事件循环 ──→ 命令队列（串行执行）
客户端 C ──┘
```

- 单条命令原子；`MULTI/EXEC` 事务批量（非回滚，某条失败其余仍执行）。
- **Lua 脚本**：整段脚本原子执行，分布式锁释放常用。
- 避免：`KEYS *`、`FLUSHALL`、大 key `HGETALL`、`SMEMBERS` 阻塞。

## 10. 面试 Q&A

| 问 | 答 |
|----|-----|
| Redis 为什么快？ | 内存、高效数据结构、单线程无锁、IO 多路复用、近似 O(1) 操作多 |
| String 底层？ | SDS；短串 embstr，长串 raw，整数 int |
| Hash 为何用 ziplist/listpack？ | 小对象紧凑存储，省内存；超阈值转 dict |
| 跳表 vs 红黑树？ | 跳表实现简单、范围查询好；ZSet 需 dict 配合 O(1) 查 member |
| ZSet 如何实现 O(1) ZSCORE？ | skiplist 排序 + dict member→score |
| List 现在底层？ | quicklist（链表 + listpack 节点） |
| 渐进式 rehash 目的？ | 避免一次性 rehash 阻塞主线程 |
| Stream 和 List 队列区别？ | Stream 支持消费组、持久化 ID、ACK；List 轻量无 ACK |

## 11. 生产案例

**案例 1：排行榜热 key**

某游戏 ZSet 千万 member，ZADD 延迟升高。根因：skiplist +log N 在大 N 下仍慢 + 单 key 过大。方案：按赛季/区分 key、TopN 单独 ZSet、冷数据归档 DB。

**案例 2：Hash 存大 JSON 字段**

HSET 单 field 存 10KB JSON，触发 hashtable + 网络传输慢。改：大 blob 放 String，Hash 只存元数据。

**案例 3：误用 KEYS 导致 P99 飙升**

运维脚本 `KEYS user:*` 在生产执行，阻塞 2s。改：`SCAN` 游标迭代 + 从库执行。

|------|-------------|----------|
