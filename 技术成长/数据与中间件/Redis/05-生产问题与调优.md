## 2. 大 Key 问题

### 2.1 什么是大 Key

| 类型 | 经验阈值（参考） |
|------|------------------|
| String value | > 10 KB（日志/配置可更大需评估） |
| Hash/List/Set/ZSet | 元素 > 5000 或 总大小 > 10 MB |
| 单 key 内存 | 占实例 1% 以上需关注 |

**危害**：

```
删除大 key     → DEL 阻塞主线程（同步释放）
序列化/网络    → 主从同步、Cluster 迁移超时
RDB/AOF 重写   → fork + COW 内存暴涨
HGETALL/SMEMBERS → 慢查询，带宽打满
```

### 2.2 发现大 Key

```bash
# 离线扫描（从库执行，避免影响主库）
redis-cli --bigkeys -i 0.1

# 内存采样
redis-cli --memkeys --memkeys-samples 10000

# 单 key 内存
redis-cli MEMORY USAGE user:big:hash

# 元素个数
redis-cli HLEN user:big:hash
redis-cli LLEN big:list
```

**Redis 4.0+ 异步删**：

```bash
redis-cli UNLINK big:key    # 后台线程释放，推荐
redis-cli DEL big:key       # 同步，大 key 慎用
```

### 2.3 治理方案

| 方案 | 适用 |
|------|------|
| **拆分** | Hash 按 field 分片 `user:1001:profile` + `user:1001:orders` |
| **压缩** | String 存 gzip/snappy 后 base64 |
| **归档** | 冷数据迁 DB / OSS，Redis 只留热数据 |
| **换结构** | 大 List 改 Stream 分段 |
| **异步删** | UNLINK + 低峰执行 |

**案例**：某用户行为 List 500 万元素，RPOP 正常但 `LRANGE 0 -1` 超时。拆成 `behavior:{userId}:{yyyyMMdd}` 按日分 key，单 key < 1 万元素。

## 3. 热 Key 问题

### 3.1 现象

```
单 key QPS 10万+  →  单 Redis 节点 CPU 100%
                   →  Cluster 单 slot 热点
                   →  网卡打满
```

### 3.2 发现

```bash
# Redis 4.0.3+ 需配置 hotkeys 采样（生产慎用，有开销）
redis-cli --hotkeys

# 监控：按 key 前缀聚合 QPS（应用埋点 / 代理层统计）
# 云 Redis 控制台常带热 key 分析
```

### 3.3 治理

| 方案 | 说明 |
|------|------|
| **本地缓存** | Caffeine 挡 90% 读，极热商品必备 |
| **多副本 key** | `hot:item:1001:{0..9}` 随机读，合并写 |
| **读写分离** | 热读走 Replica（接受延迟） |
| **拆分** | 热 key 业务拆分 |
| **MQ 削峰** | 写热 key 改异步聚合 |

```
多副本读扩散:
  readKey = "product:1001:" + random(0, N-1)
  write   → 更新所有分片 or 删全部 + 懒加载
```

**案例**：秒杀商品 `seckill:sku:1` QPS 50 万。本地缓存 2s + 10 个 Redis 副本 key + 静态页 CDN，Redis QPS 降到 3 万。

## 4. 内存管理与淘汰策略

### 4.1 内存构成

```bash
redis-cli INFO memory
# used_memory_human:2.50G
# used_memory_rss_human:2.80G    # 进程 RSS，含碎片
# mem_fragmentation_ratio:1.12   # >1.5 关注碎片
# maxmemory:4gb
# maxmemory_policy:allkeys-lru
```

```
used_memory 组成:
├── 数据 key/value
├── 过期字典
├── 复制 backlog
├── AOF buffer
└── 客户端 buffer（输出队列过大）
```

### 4.2 maxmemory-policy

| 策略 | 行为 |
|------|------|
| **noeviction** | 写满返回 OOM 错误（默认无 maxmemory 时） |
| **allkeys-lru** | 所有 key LRU 淘汰（**缓存常用**） |
| **allkeys-lfu** | 所有 key LFU（Redis 4.0+，热点友好） |
| **volatile-lru** | 仅带 TTL 的 key LRU |
| **volatile-lfu** | 仅带 TTL 的 key LFU |
| **volatile-ttl** | 淘汰 TTL 最短的 |
| **allkeys-random** | 随机 |
| **volatile-random** | 随机带 TTL |

**LRU vs LFU**：

| | LRU | LFU |
|---|-----|-----|
| 依据 | 最近访问时间 | 访问频率 |
| 适合 | 一般缓存 | 热点稳定、防一次性 key 挤掉热 key |

```conf
maxmemory 8gb
maxmemory-policy allkeys-lfu
```

### 4.3 内存优化

| 手段 | 说明 |
|------|------|
| 设 TTL | 避免 key 永久堆积 |
| 压缩结构 | Hash/ZSet 小对象 listpack |
| 共享对象 | Redis 内部整数 0～9999 等 |
| 主动碎片整理 | `activedefrag yes`（Redis 4.0+） |
| 换实例 | 内存碎片极高时导出迁移 |

```bash
redis-cli CONFIG SET activedefrag yes
redis-cli MEMORY PURGE   # 部分版本支持
redis-cli MEMORY DOCTOR
```

## 5. 慢查询

### 5.1 原理

Redis **单线程**执行命令，一条慢命令阻塞所有请求。

```conf
slowlog-log-slower-than 10000   # 微秒，10ms
slowlog-max-len 128
```

```bash
redis-cli SLOWLOG GET 20
redis-cli SLOWLOG LEN
redis-cli SLOWLOG RESET
```

### 5.2 常见慢命令

| 命令 | 原因 |
|------|------|
| KEYS * | O(N) 全库扫描 |
| FLUSHALL | 清空 |
| SUNION/SORT 大集合 | O(N) |
| HGETALL / SMEMBERS 大 key | 返回体巨大 |
| LRANGE 0 -1 大 List | 全量拉取 |
| ZRANGE 大范围 | 元素多 |

**替代**：

```bash
# KEYS → SCAN
redis-cli SCAN 0 MATCH user:* COUNT 100

# 大 Hash → HSCAN
redis-cli HSCAN big:hash 0 COUNT 100
```

### 5.3 latency 诊断

```bash
redis-cli --latency
redis-cli --latency-history
redis-cli LATENCY DOCTOR
redis-cli LATENCY LATEST
```

**延迟来源**：慢命令、fork（RDB/AOF）、AOF fsync、网络、内存 swap（**禁止 Redis swap**）。

## 6. 连接与网络

### 6.1 连接数

```bash
redis-cli INFO clients
# connected_clients:500
# blocked_clients:0

redis-cli CONFIG GET maxclients
# 默认 10000
```

| 问题 | 方案 |
|------|------|
| 连接泄漏 | 连接池（Lettuce/Jedis pool）、超时回收 |
| 连接过多 | 调大 maxclients、proxy 聚合连接 |
| 输出缓冲过大 | 客户端慢消费 → `client-output-buffer-limit` |

```conf
client-output-buffer-limit normal 0 0 0
client-output-buffer-limit replica 256mb 64mb 60
client-output-buffer-limit pubsub 32mb 8mb 60
```

### 6.2 带宽

大 value 读写在 10G 网卡上仍可能成为瓶颈。压缩 value、pipeline 批量、就近部署。

```bash
# Pipeline 示例（减少 RTT）
echo -e "GET k1\nGET k2\nGET k3" | redis-cli --pipe
```

## 7. 持久化与 fork 调优

| 现象 | 原因 | 调优 |
|------|------|------|
| 周期性 latency 尖刺 | BGSAVE/AOF rewrite fork | 混合持久化、低峰 rewrite、降内存 |
| 内存翻倍 | COW 写密集 | 少大 key、控制 rewrite 频率 |
| fork 慢 | 大内存 + THP | `echo never > /sys/kernel/mm/transparent_hugepage/enabled` |

```bash
redis-cli INFO persistence
# rdb_last_bgsave_time_sec:3
# aof_last_rewrite_time_sec:120
```

## 8. 主从与 Cluster 运维

### 8.1 复制延迟

```bash
redis-cli INFO replication
# master_repl_offset:1000000
# slave_repl_offset:998000   # 差 2000 字节延迟
```

| 原因 | 处理 |
|------|------|
| 从库单线程追不上 | 增从库机器规格、减从库读压力 |
| 大 key 全量同步 | 拆大 key |
| 网络 | 同 AZ 部署 |

### 8.2 Cluster 运维命令

```bash
redis-cli --cluster check 127.0.0.1:7000
redis-cli --cluster rebalance 127.0.0.1:7000
redis-cli CLUSTER FAILOVER   # 手动故障转移
```

## 9. 监控指标与告警

| 指标 | 告警阈值（参考） |
|------|------------------|
| used_memory / maxmemory | > 85% |
| mem_fragmentation_ratio | > 1.5 |
| connected_clients | > 80% maxclients |
| blocked_clients | > 0 持续 |
| latest_fork_usec | 突然升高 |
| master_link_status | down |
| keyspace_misses 突增 | 缓存击穿/雪崩 |
| ops/sec 突降 | 阻塞/故障 |

**Prometheus + redis_exporter**：

```
redis_memory_used_bytes
redis_connected_clients
redis_commands_processed_total
redis_slowlog_length
```

## 10. 安全配置

```conf
requirepass strong_password
rename-command FLUSHALL ""
rename-command FLUSHDB ""
rename-command CONFIG "CONFIG_abc123"
bind 10.0.0.1
protected-mode yes
```

**禁止**：公网暴露 6379、弱密码、无 ACL（Redis 6.0+ `ACL LIST`）。

## 11. 面试 Q&A

| 问 | 答 |
|----|-----|
| 大 key 危害？ | 阻塞删、迁移慢、fork 内存涨、网络慢 |
| 如何删大 key？ | UNLINK 异步；或 SCAN 分批 HDEL |
| 热 key 怎么办？ | 本地缓存、多副本、读写分离 |
| 内存淘汰策略选？ | 纯缓存 allkeys-lfu/lru；混合 volatile-lru |
| 慢查询怎么查？ | SLOWLOG、latency doctor、避免 KEYS |
| 碎片率高？ | activedefrag、重启迁移、控制分配 |
| Redis 为何禁 swap？ | 换页导致 latency 毫秒变秒 |
| 单线程如何利用多核？ | 多实例分片 Cluster；6.0+ IO 线程只解网络 |

## 12. 生产案例

**案例 1：mem_fragmentation_ratio 2.8**

8GB 数据 RSS 14GB，OOM killer。开启 activedefrag，低峰 `MEMORY PURGE`，仍高则新建实例迁移。

**案例 2：FLUSHDB 误操作**

运维连错库。改 ACL 分账号、`rename-command FLUSHDB ""`、生产禁 FLUSH。

**案例 3：输出缓冲撑爆内存**

Pub/Sub 慢消费者，client buffer 无限涨。设 `client-output-buffer-limit pubsub 32mb 8mb 60`，踢慢客户端。

**案例 4：AOF everysec 磁盘 IO 100%**

SSD 老化 + AOF 过大。BGREWRITEAOF、开混合、换盘、写缓冲 `no-appendfsync-on-rewrite yes`（rewrite 期间短暂风险）。

**案例 5：Cluster 单 slot 热点**

明星直播点赞 key 单 slot CPU 100%。改本地聚合 + 多 key 分片 + 异步批量写 Redis。

## 13. 调优 Checklist

```
□ maxmemory + 淘汰策略
□ 所有 key 有 TTL（除特殊）
□ 禁止 KEYS，用 SCAN
□ 大 key 治理（--bigkeys 季度扫描）
□ 热 key 本地缓存 / 分片
□ 从库跑 --bigkeys / 备份
□ 监控内存/延迟/复制/慢日志
□ THP disabled、no swap
□ 连接池 + maxclients
□ 持久化策略与 rewrite 窗口
```
