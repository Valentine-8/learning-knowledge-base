## 1. 生产故障案例

### 案例 1：ZK 集群脑裂导致 Dubbo 注册异常

| 项 | 内容 |
|----|------|
| 现象 | 服务时而可用时而 503，provider 列表为空 |
| 根因 | 5 节点跨 2 机房，网络分区后少数派仍接受写 |
| 修复 | 调整为 3 节点或 2+2+1 三地部署；旧版本升级 |
| 预防 | 奇数节点、跨 AZ 过半、监控选举耗时 |

### 案例 2：Session 超时误删临时节点

| 项 | 内容 |
|----|------|
| 现象 | 全量 GC 后服务被注册中心摘除 |
| 根因 | STW 超过 sessionTimeout，ZK 认为客户端死亡 |
| 修复 | sessionTimeout 调至 30s；优化 GC；JVM 调优 |
| 预防 | 监控 GC pause；Curator 重连机制 |

### 案例 3：Watcher 风暴

| 项 | 内容 |
|----|------|
| 现象 | ZK CPU 100%，大量客户端超时 |
| 根因 | 1000 客户端 Watch 同一节点，配置变更触发惊群 |
| 修复 | 改用 CuratorCache；配置分片；本地缓存 + 长轮询 |
| 预防 | 避免大量客户端 Watch 同一 ZNode |

### 案例 4：磁盘满导致 ZK 无法写入

| 项 | 内容 |
|----|------|
| 现象 | 所有写请求失败，Kafka 无法选 Controller |
| 根因 | 事务日志目录磁盘 100%，快照无法清理 |
| 修复 | 扩容磁盘；`autopurge.snapRetainCount` 和 `purgeInterval` |
| 预防 | 监控 dataDir 磁盘；独立磁盘 |

### 案例 5：错误使用 ZK 存业务数据

| 项 | 内容 |
|----|------|
| 现象 | 集群延迟飙升，最终不可用 |
| 根因 | 把订单状态写入 ZK，每秒数千写 |
| 修复 | 迁移到 Redis/MySQL；ZK 只存协调元数据 |
| 预防 | 明确 ZK 定位：小数据、低吞吐 |

## 3. 高频追问参考答案

**Q：3 节点和 4 节点容错一样吗？**

一样，都只能容忍 1 节点故障（都需要至少 2 节点存活才能过半）。4 节点浪费资源，所以用奇数。

**Q：ZK 挂了 Kafka 会怎样（旧架构）？**

Kafka 元数据在 ZK，Controller 选举依赖 ZK。ZK 不可用期间无法选 Controller、无法分区 Leader 切换，但已运行的 Broker 可继续服务已有分区（有限度）。

**Q：还需要学 ZK 吗？**

Kafka 去 ZK、K8s 用 etcd，但 Dubbo 老项目、HBase、面试仍常考。理解 ZAB/Watcher/锁算法对分布式协调本质有帮助。
