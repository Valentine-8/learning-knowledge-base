# ZooKeeper · 速查总览

> 10 分钟复习。深入见 [01～04 章](./README.md)。

---

## 1. 是什么

**Apache ZooKeeper** 分布式协调服务：提供 **命名**、**配置管理**、**集群选主**、**分布式锁**、**服务注册发现** 等能力。

特点：**CP 系统**（CAP），强一致，牺牲部分可用性（选举期间不可写）。

**典型使用者**：Kafka（旧版）、Dubbo、HBase、SolrCloud、ElasticJob。

---

## 2. 架构一图

```
Client（Java Curator / zkCli）
    │
    ▼
ZooKeeper Ensemble（集群，奇数节点 3/5/7）
    │
    ├── Leader    ── 处理写请求，发起投票
    ├── Follower  ── 转发写给 Leader，参与投票，处理读
    └── Observer  ── 不参与投票，只同步，扩展读（可选）
            │
            ▼
    内存 ZNode 树 + 事务日志（TxnLog）+ 快照（Snapshot）
```

---

## 3. 核心概念

| 概念 | 说明 |
|------|------|
| ZNode | 数据节点，树形结构，类似文件路径 |
| Session | 客户端会话，有心跳超时 |
| ACL | 访问控制 |
| Watcher | 一次性事件监听 |
| zxid | 64 位事务 ID，高 32 epoch + 低 32 计数 |

**数据规模**：适合 **小数据**（KB 级配置/状态），不是存储系统。

## 4. API 速查

```bash
# 连接
zkCli.sh -server localhost:2181

# 创建
create /config/app "{\"timeout\":3000}"
create -e -s /locks/job lock-data    # 临时顺序节点

# 读取
get /config/app
ls /services

# 更新
set /config/app "{\"timeout\":5000}" 1   # 最后参数是 version

# 删除
delete /config/app 1
deleteall /services/order-service       # 递归删除

# 监听
get -w /config/app
ls -w /services
```

## 5. 节点类型

| 类型 | 标志 | 生命周期 |
|------|------|----------|
| 持久 | PERSISTENT | 手动删除 |
| 临时 | EPHEMERAL | Session 断开自动删 |
| 持久顺序 | PERSISTENT_SEQUENTIAL | 持久 + 后缀序号 |
| 临时顺序 | EPHEMERAL_SEQUENTIAL | 临时 + 后缀序号 |

**顺序节点**：ZK 自动追加 10 位递增序号，如 `lock-0000000003`。

---

## 6. Watch 要点

| 特性 | 说明 |
|------|------|
| 一次性 | 触发后需重新注册 |
| 轻量 | 只通知变化，不推送数据（需再 get） |
| 顺序 | 客户端回调按顺序 |
| 类型 | NodeCreated / NodeDeleted / NodeDataChanged / NodeChildrenChanged |

---

## 7. ZAB 协议一句话

**ZAB**（ZooKeeper Atomic Broadcast）：类似 Paxos 的崩溃恢复 + 消息广播协议。

- **崩溃恢复**：选 Leader，Follower 同步到 Leader 最新状态
- **消息广播**：Leader 将写请求广播，过半 Follower ACK 后提交

## 8. 面试 5 分钟

| 问 | 答 |
|----|-----|
| ZK 是什么？ | 分布式协调，CP，小数据，树形 ZNode |
| 为何奇数节点？ | 过半机制，4 节点容错不如 3 节点且浪费 |
| 临时节点用途？ | 服务注册（Session 断则下线）、分布式锁 |
| Watch 为何一次性？ | 防大量 Watcher 导致性能问题 |
| ZK 和 etcd 区别？ | ZK Java 生态老；etcd gRPC+Raft，K8s 标配 |
