## 1. 为何用 ZooKeeper 做协调

| 能力 | 说明 |
|------|------|
| 临时顺序节点 | 公平排队 + 宕机自动释放 |
| 强一致 | 锁状态全局一致 |
| Watch | 等待锁时无需轮询 |

对比 Redis 锁：ZK 一致性更强但性能低；Redis 需 Redisson 等方案处理主从切换丢锁。

## 2. 分布式锁 — 临时顺序节点算法

**路径**：`/locks/{lockName}/lock-`

```
/locks/order/
    ├── lock-0000000001   ← 持有者
    ├── lock-0000000002   ← Watch 0001
    └── lock-0000000003   ← Watch 0002
```

### 加锁步骤

1. 创建 **临时顺序** 节点 `/locks/order/lock-`
2. 获取 `/locks/order` 下所有子节点，排序
3. 若自己的序号 **最小** → 获得锁
4. 否则 Watch **前一个** 节点（不是 Watch 最小节点）
5. 被 Watch 的节点删除 → 重新判断步骤 2
6. 解锁：删除自己的节点

**为何 Watch 前一个？** 避免羊群效应（所有人 Watch 最小节点，释放时惊群）。

## 3. Java Curator 互斥锁

```java
InterProcessMutex lock = new InterProcessMutex(client, "/locks/payment");

try {
    if (lock.acquire(10, TimeUnit.SECONDS)) {
        // 临界区
        processPayment();
    } else {
        throw new TimeoutException("获取锁超时");
    }
} finally {
    lock.release();
}
```

| 类 | 用途 |
|----|------|
| `InterProcessMutex` | 可重入互斥锁 |
| `InterProcessSemaphoreMutex` | 不可重入 |
| `InterProcessReadWriteLock` | 读写锁 |
| `InterProcessSemaphoreV2` | 信号量（限流） |

## 4. 锁的边界与坑

| 问题 | 说明 |
|------|------|
| 不可重入（原生实现） | 同线程再次加锁死锁；Curator Mutex 可重入 |
| 锁超时 | 业务未完成锁已释放 → 需 fencing token |
| Session 超时 | 临时节点删，锁释放，但客户端可能仍在执行 |
| GC Stop-The-World | 长时间 GC 导致 Session 超时误释放 |

**Fencing Token**：锁附带递增 zxid，下游存储拒绝旧 token 的写。

## 5. Leader 选举

### 临时顺序节点法

与锁类似：序号最小者为 Leader，Watch 前一个节点。

```java
LeaderSelector selector = new LeaderSelector(client, "/election/app", new LeaderSelectorListenerAdapter() {
    @Override
    public void takeLeadership(CuratorFramework client) throws Exception {
        // 成为 Leader，执行业务
        // 方法返回或抛异常 → 释放 Leader
        runAsLeader();
    }
});
selector.autoRequeue();  // 丢失 Leader 后重新排队
selector.start();
```

### 使用场景

| 场景 | 说明 |
|------|------|
| 定时任务 | 集群只跑一个 Scheduler |
| 写主节点 | 单点写入避免冲突 |
| 旧版 Kafka Controller | 控制器选举 |

## 6. 原生 ZK 锁 vs Curator vs Redis

| 方案 | 一致性 | 性能 | 复杂度 |
|------|--------|------|--------|
| ZK 原生 | 强 | 低（千级/s） | 高 |
| Curator | 强 | 低 | 低（封装好） |
| Redis Redisson | 较好 | 高 | 中 |
| 数据库行锁 | 强 | 低 | 低 |

**选型建议**：

- 协调、选主、配置 → ZK / etcd
- 高并发短锁 → Redis
- 已有 ZK（Kafka/Dubbo）→ Curator 锁
- 简单场景 → 数据库 `SELECT FOR UPDATE`

## 7. 完整选主示例（概念）

```java
public class MasterElection {
    private volatile boolean isLeader = false;

    public void start() {
        LeaderSelector listener = new LeaderSelector(zkClient, "/master", new LeaderSelectorListener() {
            @Override
            public void takeLeadership(CuratorFramework client) {
                isLeader = true;
                try {
                    while (isLeader) {
                        Thread.sleep(1000);
                        // 心跳或工作
                    }
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                } finally {
                    isLeader = false;
                }
            }
            @Override
            public void stateChanged(CuratorFramework client, ConnectionState newState) {
                if (newState == ConnectionState.LOST) {
                    isLeader = false;
                }
            }
        });
        listener.autoRequeue();
        listener.start();
    }
}
```

## 8. Dubbo 与 ZK 的关系（了解）

Dubbo 2.x 常用 ZK 作为注册中心：

```
/dubbo/com.example.OrderService/providers/
    └── dubbo://192.168.1.10:20880...  （临时节点）
```

Consumer Watch providers 子节点变化。Dubbo 3.x 推荐 Nacos，ZK 仍支持。

## 9. 小结

| 要点 | 一句话 |
|------|--------|
| 公平锁 | 临时顺序 + Watch 前一个 |
| Curator | 生产直接用，别手写 |
| 选主 | LeaderSelector + autoRequeue |
| 注意 | Session 超时、Fencing、羊群效应 |
