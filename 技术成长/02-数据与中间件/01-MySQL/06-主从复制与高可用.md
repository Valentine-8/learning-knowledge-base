## 一、为什么需要主从复制

| 诉求 | 主从如何解决 |
|------|-------------|
| **读扩展** | 写走主库，读走从库，分担 QPS |
| **高可用** | 主库故障时 promote 从库，缩短 RTO |
| **备份/归档** | 从库做逻辑备份、延迟从库防误删 |
| **异地容灾** | 跨机房/跨 AZ 异步复制 |
| **数据分析** | 从库跑报表，不影响主库 OLTP |

**核心机制**：主库把 **Binlog** 推/拉给从库，从库重放得到一致数据（最终一致，非强一致）。

```
                    ┌─────────────┐
  写请求 ──────────►│   Master    │
                    │  Binlog     │
                    └──────┬──────┘
                           │ 复制流
              ┌────────────┼────────────┐
              ▼            ▼            ▼
        ┌──────────┐ ┌──────────┐ ┌──────────┐
        │ Slave 1  │ │ Slave 2  │ │ Slave 3  │
        │ Relay Log│ │ Relay Log│ │ Relay Log│
        └──────────┘ └──────────┘ └──────────┘
              ▲
  读请求 ───────┘（读写分离）
```

## 二、复制原理：三个线程

### 2.1 整体流程

1. **主库**：事务提交 → 写 Binlog（见两阶段提交）
2. **Binlog Dump Thread**（主库）：读取 Binlog，通过网络发给从库
3. **IO Thread**（从库）：连接主库，接收 Binlog 事件，写入本地 **Relay Log**
4. **SQL Thread**（从库）：读取 Relay Log，**重放** SQL/行事件，更新从库数据

```
Master                              Slave
┌──────────────────┐               ┌──────────────────┐
│ 事务 commit       │               │                  │
│ 写 Binlog         │               │                  │
│       │           │               │                  │
│ Binlog Dump Thread├──network──────►│ IO Thread        │
│ (读 binlog 发送)  │               │ (写 relay log)   │
└──────────────────┘               │       │          │
                                   │ SQL Thread       │
                                   │ (重放 relay log) │
                                   └──────────────────┘
```

### 2.2 Binlog Dump Thread（主库）

- 每个连接的从库对应主库一个 **Binlog Dump** 线程
- 从指定 **binlog 文件名 + position** 或 **GTID** 开始发送
- 格式：`COM_BINLOG_DUMP` / `COM_BINLOG_DUMP_GTID` 协议
- 主库 `SHOW PROCESSLIST` 可见：`Binlog Dump`

**关键配置（主库）**：

```ini
# my.cnf
server-id = 1                    # 集群内唯一
log_bin = mysql-bin              # 开启 binlog
binlog_format = ROW              # 生产推荐 ROW，记录行变更
sync_binlog = 1                  # 每次 commit 刷盘 binlog（更安全，略慢）
binlog_row_image = FULL          # ROW 格式下记录完整行（MINIMAL 可减体积）
expire_logs_days = 7             # 或 binlog_expire_logs_seconds
```

### 2.3 IO Thread（从库）

- 负责与主库建立连接，拉取 Binlog 事件
- 写入 **Relay Log**（结构与 Binlog 类似，只在从库本地）
- 更新 **master.info**（或 `mysql.slave_master_info` 表，8.0+）：记录复制位点、主库连接信息
- `SHOW SLAVE STATUS\G` 中：
  - `Slave_IO_Running: Yes/No`
  - `Master_Log_File` / `Read_Master_Log_Pos`：已从主库读到哪
  - `Last_IO_Error`：IO 线程错误

**关键配置（从库）**：

```ini
server-id = 2
relay_log = relay-bin
read_only = 1                      # 从库只读，防误写
relay_log_recovery = 1             # 重启后自动修复 relay log
```

### 2.4 SQL Thread（从库）

- 单线程（传统）或多线程（**MTS**，`slave_parallel_workers > 0`）重放 Relay Log
- 更新 **relay-log.info** / `mysql.slave_relay_log_info`
- `SHOW SLAVE STATUS\G` 中：
  - `Slave_SQL_Running: Yes/No`
  - `Relay_Log_File` / `Exec_Master_Log_Pos`：已执行到哪
  - `Seconds_Behind_Master`：复制延迟秒数（估算值，见后文）
  - `Last_SQL_Error`：重放错误

### 2.5 三种 Binlog 格式对复制的影响

| 格式 | 内容 | 优缺点 |
|------|------|--------|
| **STATEMENT** | 原始 SQL | 体积小；不确定函数（UUID、NOW()）可能导致主从不一致 |
| **ROW** | 每行 before/after 镜像 | 体积大；**生产默认**，一致性最好 |
| **MIXED** | 自动选择 | 折中，仍不如 ROW 可控 |

**7 年工程师必记**：生产 OLTP 用 **ROW + FULL/MINIMAL**；Canal/Debezium 等 CDC 也依赖 Binlog ROW。

### 2.6 复制模式：传统 vs GTID（后文详述）

```sql
-- 传统：file + position
CHANGE MASTER TO
  MASTER_HOST='10.0.0.1',
  MASTER_USER='repl',
  MASTER_PASSWORD='***',
  MASTER_LOG_FILE='mysql-bin.000123',
  MASTER_LOG_POS=154;

-- GTID（推荐）
CHANGE MASTER TO
  MASTER_HOST='10.0.0.1',
  MASTER_USER='repl',
  MASTER_PASSWORD='***',
  MASTER_AUTO_POSITION=1;
```

## 三、异步 / 半同步 / 组复制（MGR）

### 3.1 异步复制（默认）

- 主库事务 **commit 成功即返回客户端**，不等待从库
- **优点**：性能最好，主库无额外等待
- **缺点**：主库 crash 时，已 commit 但未复制的数据 **丢失**（RPO > 0）
- **适用**：读扩展、对丢失少量数据可容忍的场景

```
Client ──► Master commit OK ──► 返回成功
                │
                └──► 异步推 binlog ──► Slave（可能滞后）
```

### 3.2 半同步复制（Semi-Sync）

- 主库 commit 时，等待 **至少一个从库** 收到 Binlog（写入 relay log 或 ack）再返回
- 插件：`rpl_semi_sync_master` / `rpl_semi_sync_slave`（8.0 合并进源码）
- 超时后 **自动降级** 为异步，避免主库被拖死

| 参数 | 含义 |
|------|------|
| `rpl_semi_sync_master_timeout` | 等待 ack 超时（ms），超时转异步 |
| `rpl_semi_sync_master_wait_for_slave_count` | 需要几个从库 ack（默认 1） |
| `rpl_semi_sync_master_wait_point` | AFTER_SYNC（5.7+ 默认，binlog 刷盘后等）/ AFTER_COMMIT |

**AFTER_SYNC vs AFTER_COMMIT**：

- **AFTER_SYNC**：binlog 写完后、引擎 commit 前等 ack → 主库 crash 时 binlog 有、从库也有，**无丢失**
- **AFTER_COMMIT**：引擎已 commit 再等 ack → 极端情况可能「主已提交、从未收到」

**适用**：金融、订单等要求 **RPO≈0** 但不想上 MGR 的场景。

### 3.3 组复制 MGR（MySQL Group Replication）

基于 **Paxos 协议** 的 **多主/单主** 集群，官方高可用方案（InnoDB Cluster = MGR + MySQL Shell + Router）。

| 特性 | 说明 |
|------|------|
| 一致性 | **Certification** 全局有序，冲突事务回滚 |
| 模式 | **单主**（默认，写集中）/ **多主**（写分散，冲突检测更复杂） |
| 故障转移 | 成员故障自动剔除，选新 Primary |
| 要求 | 全 ROW binlog、GTID、表必须有主键、网络低延迟 |

**工作流程（简化）**：

```
1. 事务在本地执行，生成 binlog event
2. 广播到 Group，Certification 检查冲突（同键并发写）
3. 多数派 ack 后，各节点 apply
4. 返回客户端
```

**与主从对比**：

| 维度 | 传统主从 | MGR |
|------|---------|-----|
| 一致性 | 最终一致 | 组内强一致（certification） |
| 故障切换 | 需 Orchestrator/MHA 等 | 内置自动 |
| 写扩展 | 单写 | 单主模式仍单写 |
| 运维复杂度 | 低 | 中高 |
| 延迟 | 异步可很低 | 跨节点共识有开销 |

**Java 侧**：配合 **MySQL Router** 做读写分离与自动路由；或使用 ProxySQL / 自研中间件。

## 四、复制延迟：原因与排查

### 4.1 `Seconds_Behind_Master` 的含义与陷阱

- 从库 SQL 线程重放的 **时间戳** 与主库当前时间的差值（估算）
- **为 0 不代表无延迟**：SQL 线程空闲时也显示 0
- **大事务** 时：IO 已拉完但 SQL 未执行完，SBM 可能 **虚低**
- **并行复制** 下语义更复杂，需结合 **Performance Schema** / **heartbeat**

### 4.2 延迟常见原因

| 类别 | 具体原因 |
|------|---------|
| **从库性能** | 单 SQL 线程瓶颈（大事务、DDL、缺少索引导致重放慢） |
| **主库写入** | 突发大流量、批量导入、大事务（一个 event 很大） |
| **网络** | 跨机房带宽、丢包、主从距离远 |
| **锁竞争** | 从库有慢查询占锁，SQL 线程 blocked |
| **并行度不足** | `slave_parallel_workers` 过小，依赖主库 commit 顺序 |
| **硬件** | 从库磁盘 IOPS/CPU 弱于主库 |
| **延迟从库** | 故意 `CHANGE MASTER ... MASTER_DELAY=N` |

### 4.3 排查步骤（生产 SOP）

```sql
-- 1. 从库状态
SHOW SLAVE STATUS\G
-- 关注：Slave_IO/SQL_Running, Last_IO/SQL_Error,
--       Seconds_Behind_Master, Retrieved_Gtid_Set vs Executed_Gtid_Set

-- 2. 主库 binlog 产生速度
SHOW MASTER STATUS;
SHOW BINARY LOGS;

-- 3. 从库 relay log 是否在涨（IO 正常但 SQL 慢）
SHOW RELAYLOG EVENTS IN 'relay-bin.000xxx' LIMIT 10;

-- 4. SQL 线程在干什么
SHOW PROCESSLIST;  -- 找 system user / SQL thread

-- 5. 并行复制（5.7+）
SELECT * FROM performance_schema.replication_applier_status_by_worker;
```

**Grafana/Prometheus 监控指标**：

- `mysql_slave_status_seconds_behind_master`
- `mysql_global_status_innodb_row_ops`（主从对比）
- IO/SQL thread 状态、relay log 磁盘增长

### 4.4 缓解手段

| 手段 | 说明 |
|------|------|
| **并行复制 MTS** | `slave_parallel_workers=4~16`，`slave_parallel_type=LOGICAL_CLOCK` |
| **从库硬件对齐** | 磁盘、CPU 不低于主库 |
| **避免大事务** | 批量改拆分 batch，DDL 用 gh-ost/pt-osc |
| **读写分离** | 非关键读走从库；关键读走主库 |
| **半同步/MGR** | 要一致性而非单纯降延迟 |
| **延迟从库** | 误删恢复，不是降延迟方案 |

## 五、读写分离与「读己之写」

### 5.1 读写分离架构

```
                    ┌─────────────┐
         写 ───────►│   Master    │
                    └──────┬──────┘
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
         ┌─────────┐  ┌─────────┐  ┌─────────┐
  读 ───►│ Slave 1 │  │ Slave 2 │  │ Slave 3 │
         └─────────┘  └─────────┘  └─────────┘
              ▲
         负载均衡 / 中间件
    （ShardingSphere、MyCat、ProxySQL、自研 JDBC 路由）
```

**Java 常见实现**：

1. **中间件层**：ShardingSphere-Proxy、MySQL Router
2. **客户端 SDK**：ShardingSphere-JDBC 读写分离规则
3. **双 DataSource + AbstractRoutingDataSource**：Spring `@Transactional(readOnly=true)` 路由从库
4. **注解/AOP**：`@Master` / `@Slave` 强制路由

### 5.2 读己之写（Read-Your-Writes）

**问题**：用户在主库写完，立刻读从库，复制未追上 → **读到旧数据**。

**典型场景**：

- 注册/登录后立即查 profile
- 下单后立即查订单详情
- 发帖后立即刷新列表

**解决方案**：

| 方案 | 实现 | 优缺点 |
|------|------|--------|
| **关键读走主库** | 写后 N 秒内同一用户读 master | 简单；主库压力增 |
| **会话粘滞 + 位点** | 记录写完成 GTID/pos，从库执行位点 ≥ 该值再读 | 精确；实现复杂 |
| **缓存** | 写后更新 Redis，读先走缓存 | 适合读多；缓存一致性问题 |
| **同步/半同步** | 写成功即从库已有 | 延迟低但写 RT 增加 |
| **Galera/MGR** | 组内一致读 | 架构升级成本高 |

**ShardingSphere _hint 示例**：

```java
// 强制走主库
HintManager.getInstance().setWriteRouteOnly();
try {
    orderMapper.selectById(orderId);
} finally {
    HintManager.clear();
}
```

**位点等待（MySQL 5.7+）**：

```sql
-- 从库执行，等待追上指定 GTID
SELECT WAIT_FOR_EXECUTED_GTID_SET('uuid:1-100', 10);
```

Java 可在写后于从库连接调用，超时则 fallback 主库。

### 5.3 从库读的一致性级别（产品语义）

| 级别 | 说明 |
|------|------|
| 最终一致 | 默认，延迟秒级可接受 |
| 会话一致 | 同用户写后读不旧 |
| 强一致 | 全走主库或 MGR 同步读 |

## 六、GTID（Global Transaction Identifier）

### 6.1 是什么

每个事务在 Binlog 中携带全局唯一 ID：`source_uuid:transaction_id`

```
3E11FA47-71CA-11E1-9E33-C80AA9429562:1-100
│                                    │ │
└─ server_uuid（主库实例）              └─ 递增序号
```

### 6.2 为什么需要 GTID

| 传统 file+pos 痛点 | GTID 解决 |
|-------------------|----------|
| Failover 后找新位点困难 | 自动定位，`MASTER_AUTO_POSITION=1` |
| 主从切换易错 | 按 GTID 集合对齐 |
| 级联复制复杂 | 跳过已执行 GTID，避免重复 |

### 6.3 配置要点

```ini
# 主从均开
gtid_mode = ON
enforce_gtid_consistency = ON
```

```sql
-- 查看 GTID 执行情况
SHOW MASTER STATUS;           -- Executed_Gtid_Set
SHOW SLAVE STATUS\G;          -- Retrieved_Gtid_Set / Executed_Gtid_Set

-- 跳过错误 GTID（慎用，仅测试或明确可丢事务）
SET GTID_NEXT='uuid:N';
BEGIN; COMMIT;  -- 空事务占位
SET GTID_NEXT='AUTOMATIC';
```

### 6.4 Failover 与 GTID

Promote 从库为主：

```sql
STOP SLAVE;
RESET SLAVE ALL;              -- 或 RESET REPLICA ALL (8.0.22+)
SET GLOBAL read_only=OFF;
-- 其他从库 CHANGE MASTER TO MASTER_AUTO_POSITION=1 指向新主
```

**注意**：`Executed_Gtid_Set` 必须是 `Retrieved_Gtid_Set` 的超集才能安全切换。

## 七、主从切换与双主问题

### 7.1 计划内切换（Switchover）

1. 设置主库 **read_only=1**，等待从库追上（SBM=0 且 GTID 对齐）
2. 业务断写或短暂停写
3. 提升从库：停复制 → 关 read_only → VIP/DNS 切到新主
4. 其他从库 `CHANGE MASTER` 指向新主
5. 旧主降为从库或下线

### 7.2 故障切换（Failover）

| 工具/方案 | 说明 |
|-----------|------|
| **MHA** | 经典，自动选最新从库、补 binlog、切换 VIP |
| **Orchestrator** | 拓扑可视化、可控 failover |
| **InnoDB Cluster** | 官方 MGR + MySQL Shell |
| **云 RDS** | 控制台一键主备切换 |

**脑裂风险**：旧主未死透又接受写 → 双主。需 **STONITH**（隔离旧主）、VIP 漂移、fence 旧主。

### 7.3 双主（Dual Master）架构与问题

```
Master A ◄────复制────► Master B
   ▲                        ▲
   └──── 双向复制 ──────────┘
```

**用途**：双活写（不同分片键）、异地双活（谨慎）。

**核心问题**：

| 问题 | 说明 |
|------|------|
| **循环复制** | A 的写同步到 B，B 又回写 A | 用 **log_slave_updates** + **自增 ID 步长** 或 GTID 防环 |
| **冲突** | 两端改同一行 | 业务避免；或 MGR 多主 certification |
| **自增 ID 冲突** | 双端 insert | `auto_increment_offset` / `increment` 错开（如 1,3,5 vs 2,4,6） |
| **数据不一致** | 异步双向延迟 | 尽量单写；或分业务域各写各库 |

**推荐**：生产更常见 **单主多从 + 自动 failover**，而非真正的双主双写。

### 7.4 延迟从库（Delayed Replica）

```sql
CHANGE MASTER TO MASTER_DELAY = 3600;  -- 延迟 1 小时应用
```

**用途**：误 `DROP TABLE` 后在延迟从库 **stop slave** 再 **skip 到事故前**，做数据救援。

## 八、高可用架构选型（7 年工程师视角）

| 方案 | RPO/RTO | 复杂度 | 典型场景 |
|------|---------|--------|---------|
| 主从 + 手动切换 | RPO 分钟级 | 低 | 中小业务 |
| 主从 + MHA/Orchestrator | RPO 秒～分钟 | 中 | 自建 HA |
| 半同步主从 | RPO≈0（单从 ack） | 中 | 订单、支付 |
| MGR / InnoDB Cluster | 组内一致 | 高 | 金融、核心库 |
| 云 RDS 多 AZ | SLA 保障 | 低（托管） | 快速上线 |

**Java 应用配合**：

- 连接池配置 **多数据源** 或 **单一入口 + 中间件**
- 故障切换后 **连接池刷新**（旧连接指向 dead master）
- **重试 + 熔断**：`Communications link failure` 时切换读节点

## 九、面试题精选

### 基础原理

**1. MySQL 主从复制原理？三个线程分别做什么？**  
主库 Binlog Dump 读 binlog 发给从库；从库 IO 线程接收写 Relay Log；SQL 线程重放 relay log 更新数据。

**2. 为什么生产用 ROW 格式 binlog？**  
记录行级变更，避免 STATEMENT 下 UDF、NOW() 等导致主从不一致；便于 CDC 消费。

**3. Relay Log 和 Binlog 区别？**  
Binlog 在主库，Server 层，用于复制和归档；Relay Log 只在从库，是 IO 线程暂存待 SQL 线程重放的副本。

### 延迟与一致性

**4. Seconds_Behind_Master 为 0 一定没延迟吗？**  
不一定。SQL 线程空闲、或大事务 IO 已完成但 SQL 未执行完时，该值可能不准确。

**5. 复制延迟怎么排查？**  
看 `SHOW SLAVE STATUS`、主 binlog 增速、relay log 堆积、SQL 线程状态、MTS worker、从库硬件与慢 SQL。

**6. 什么是读己之写？怎么解决？**  
写主库后立即读从库可能读到旧数据。解决：关键读走主、写后缓存、GTID 位点等待、半同步/MGR。

### 高可用

**7. 异步和半同步复制区别？**  
异步主库 commit 即返回，可能丢数据；半同步等从库 ack 再返回，RPO 更好，超时降级异步。

**8. MGR 和传统主从有什么区别？**  
MGR 基于 Paxos 组复制，certification 保证组内一致、自动故障转移；主从是单向异步/半同步，最终一致。

**9. GTID 的好处？**  
全局事务标识，failover 无需手工对 file+pos，`MASTER_AUTO_POSITION` 自动追增量，简化拓扑变更。

**10. 主从切换要注意什么？**  
先确保从库追上、设 read_only、防脑裂（隔离旧主）、应用连接池刷新、其他从库改指向新主。

### 进阶

**11. 双主架构有什么问题？**  
循环复制、自增冲突、双写数据冲突；需 log_slave_updates、错开 auto_increment、或业务分写。

**12. 并行复制原理？**  
`slave_parallel_workers` 多 worker 并行重放，按 LOGICAL_CLOCK（同 commit group）或 DATABASE 粒度并行。

**13. 半同步 AFTER_SYNC 和 AFTER_COMMIT 区别？**  
AFTER_SYNC 在存储引擎 commit 前等 ack，主库 crash 不丢已确认事务；AFTER_COMMIT 已 commit 再等，极端情况可能丢。

**14. 如何从延迟从库恢复误删数据？**  
在延迟从库上 STOP SLAVE，找到事故前 binlog/relay 位点，导出数据或 skip 到事故前再恢复。

**15. 主库 binlog 满了磁盘会怎样？**  
无法写入新事务，主库 **只读** 或写失败；需扩容、`PURGE BINARY LOGS`、或调整 expire 策略。

| 要点 | 一句话 |
|------|--------|
