# 03 · 可靠性与幂等

> **目标**：系统掌握消息丢失、重复消费、顺序保证、消息积压等生产核心问题，能设计端到端可靠投递与幂等方案。

---

## 一、消息可靠性全景

### 1.1 消息生命周期

```
Producer → 网络 → Broker 存储 → 网络 → Consumer → 业务处理 → Offset 提交
   ①          ②        ③           ④        ⑤          ⑥
```

**任一环节失败**都可能导致：丢失、重复、乱序。

### 1.2 投递语义

| 语义 | 含义 | 实现难度 |
|------|------|----------|
| **At Most Once** | 最多一次，可能丢 | 低 |
| **At Least Once** | 至少一次，可能重复 | 中（业界默认） |
| **Exactly Once** | 精确一次 | 高 |

**现实**：分布式环境下 Exactly Once 通常指 **端到端语义**（Kafka 事务 EOS），业务层仍需 **幂等** 兜底。

## 二、消息丢失

### 2.1 丢失环节分析

| 环节 | 丢失场景 | Kafka 防护 | RocketMQ 防护 |
|------|----------|------------|---------------|
| **Producer** | 发送失败未重试、异步丢失 | acks=all、retries、同步发送 | 同步 send、发送回调检查 |
| **Broker** | 未刷盘宕机、副本未同步 | replication、min.insync.replicas | SYNC_FLUSH、SYNC_MASTER |
| **Consumer** | 自动提交 offset 后处理失败 | 手动 commit、处理完再提交 | 消费成功再返回 CONSUME_SUCCESS |

### 2.2 Producer 端防丢失

#### Kafka

```properties
acks=all
retries=3
enable.idempotence=true
max.in.flight.requests.per.connection=1  # 与幂等配合保顺序
```

- **acks=all**：ISR 全部确认
- **同步发送**或 **异步 + 失败重发** + 失败告警
- 关键消息：发送结果回调中检查 `RecordMetadata`，失败写 DB 补偿表

#### RocketMQ

```java
SendResult result = producer.send(msg);  // 同步
if (result.getSendStatus() != SendStatus.SEND_OK) {
    // 记录失败，定时补偿
}
```

- 同步刷盘 + 同步复制（Broker 配置）
- 单向发送 `sendOneway` **不用于**关键业务

### 2.3 Broker 端防丢失

#### Kafka

| 配置 | 说明 |
|------|------|
| `replication.factor=3` | 三副本 |
| `min.insync.replicas=2` | acks=all 时至少 2 副本同步 |
| `unclean.leader.election.enable=false` | 不从非 ISR 选 Leader |

#### RocketMQ

| 配置 | 说明 |
|------|------|
| `flushDiskType=SYNC_FLUSH` | 同步刷盘 |
| `brokerRole=SYNC_MASTER` | 同步复制到 Slave |
| Dledger 三副本 | 自动选主，Raft 多数派确认 |

### 2.4 Consumer 端防丢失

**核心原则**：**业务处理成功后再提交 offset / 返回消费成功**。

#### Kafka 错误示范

```java
// 错误：自动提交，处理失败消息已 commit
enable.auto.commit = true
process(message);  // 可能失败
```

#### Kafka 正确做法

```java
while (true) {
    ConsumerRecords records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord record : records) {
        try {
            businessProcess(record);
            // 单条或批量处理成功后
        } catch (Exception e) {
            // 不 commit，下次重新消费；或进死信
        }
    }
    consumer.commitSync();  // 本 batch 全部成功后提交
}
```

#### RocketMQ

```java
@Override
public ConsumeConcurrentlyStatus consumeMessage(List<MessageExt> msgs, ...) {
    try {
        process(msgs);
        return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
    } catch (Exception e) {
        return ConsumeConcurrentlyStatus.RECONSUME_LATER;  // 不丢，会重试
    }
}
```

**注意**：`RECONSUME_LATER` 保证不丢但会重复 → 需幂等。

## 三、重复消费

### 3.1 重复原因

| 原因 | 说明 |
|------|------|
| Producer 重试 | 网络超时实际已成功，重试导致 Broker 两条（Kafka 幂等 Producer 可解） |
| Consumer 重平衡 | 消费完未 commit，Rebalance 后新 Consumer 再消费 |
| Consumer 处理成功 commit 失败 | 下次从旧 offset 重新拉 |
| Broker 主从切换 | 未同步消息重复 |
| 手动回溯 | 运维误操作 reset offset |

### 3.2 幂等性设计原则

> **同一条消息消费多次，业务结果与消费一次相同。**

### 3.3 幂等方案

#### 方案一：数据库唯一索引

```sql
CREATE TABLE order_notify (
    id BIGINT PRIMARY KEY,
    message_id VARCHAR(64) UNIQUE,  -- MQ 消息 ID
    order_id BIGINT,
    status TINYINT,
    ...
);
```

```java
try {
    insert into order_notify (message_id, ...) values (?, ...);
    // 执行业务
} catch (DuplicateKeyException e) {
    // 已处理，直接返回成功
}
```

**适用**：有 DB、可建唯一键。

#### 方案二：Redis SETNX

```java
String key = "mq:consumed:" + messageId;
if (!redis.setNX(key, "1", 7, TimeUnit.DAYS)) {
    return; // 已消费
}
try {
    businessProcess(msg);
} catch (Exception e) {
    redis.del(key);  // 失败允许重试
    throw e;
}
```

**注意**：
- 设置 TTL 防 Redis 膨胀
- 业务失败删 key，允许重试
- Redis 与 DB 非原子，极端情况仍可能重复 → 结合 DB 唯一键双保险

#### 方案三：状态机

```
订单状态：CREATED → PAID → SHIPPED → COMPLETED

收到 PAY 消息：
  if (current == CREATED) { update PAID; }
  else if (current == PAID) { 幂等，直接返回; }
  else { 非法，告警或进 DLQ; }
```

**适用**：有明确状态流转的业务。

#### 方案四：版本号 / CAS

```sql
UPDATE account SET balance = balance - 100, version = version + 1
WHERE user_id = ? AND version = ?;
-- affected rows = 0 → 已被其他消费处理或需重试
```

#### 方案五：Kafka 幂等 Producer + 事务

- Producer：`enable.idempotence=true` → Broker 端去重（单 Session 单 Partition）
- 事务：`transactional.id` + `read_committed` → 端到端 EOS
- **Consumer 业务仍需幂等**（Rebalance 等场景）

### 3.4 方案选型

| 场景 | 推荐 |
|------|------|
| 订单、支付 | 唯一索引 + 状态机 |
| 高吞吐日志 | Redis 去重 + 批量 |
| 金融账务 | DB 唯一键 + 乐观锁 + 对账 |
| Kafka EOS 管道 | 事务 + 业务幂等双保险 |

## 四、顺序消息

### 4.1 为什么难

- 多 Partition/Queue 并行 → 天然乱序
- 重试 → 失败消息晚于后续消息被消费
- Rebalance → Queue 迁移短暂乱序

### 4.2 保证顺序的条件

```
1. 同业务 Key → 同 Partition/Queue（Producer 路由）
2. 单 Partition/Queue → 单 Consumer 线程消费
3. 消费失败不跳过（阻塞或进 DLQ，不 commit）
```

### 4.3 Kafka 顺序实践

```java
// Producer
producer.send(new ProducerRecord<>(topic, orderId, message));

// Consumer：每个 Partition 单线程
// 方式1：max.in.flight.requests.per.connection=1 + acks=all
// 方式2：自定义 ThreadPool，按 Partition 分线程
```

### 4.4 RocketMQ 顺序实践

```java
// Producer：MessageQueueSelector 同 Key 同 Queue
// Consumer：MessageListenerOrderly
consumer.registerMessageListener(new MessageListenerOrderly() {
    @Override
    public ConsumeOrderlyStatus consumeMessage(List<MessageExt> msgs, ...) {
        for (MessageExt msg : msgs) {
            process(msg);  // 顺序处理，失败 suspend 当前 Queue
        }
        return ConsumeOrderlyStatus.SUCCESS;
    }
});
```

### 4.5 顺序与吞吐权衡

| 策略 | 顺序 | 吞吐 |
|------|------|------|
| 全局单 Queue | 全局有序 | 最低 |
| Key 分区顺序 | 同 Key 有序 | 中，按 Key 分布 |
| 无顺序要求 | 无序 | 最高 |

**7 年工程师答法**：明确「谁与谁之间有序」，通常只需 **同一订单/同一用户** 有序，而非全局。

## 五、消息积压

### 5.1 积压原因

| 原因 | 表现 |
|------|------|
| 消费速度 < 生产速度 | Lag 持续上升 |
| Consumer 宕机 | 某 Partition 无人消费 |
| 消费逻辑慢 | DB 慢、外部调用超时 |
| Rebalance 频繁 | 有效消费时间少 |
| 下游故障 | 消费 block 或重试风暴 |

### 5.2 监控指标

| 指标 | Kafka | RocketMQ |
|------|-------|----------|
| 积压量 | Consumer Lag | `consumerOffset - maxOffset` |
| 消费 TPS | records-consumed-rate | Consumer TPS |
| 生产 TPS | bytes-in-rate | Put TPS |

**告警**：Lag > 阈值持续 N 分钟。

### 5.3 应急处理

```
1. 定位：哪个 Topic/Group/Partition 积压
2. 止血：
   - 扩容 Consumer（≤ 分区/队列数）
   - 临时跳过非核心消息（独立 Topic 隔离）
   - 降级：只写 DB 不落 ES 等
3. 加速：
   - 批量消费
   - 优化 DB（索引、批量 insert）
   - 异步化消费内重逻辑
4. 兜底：
   - 积压过大时新建临时 Consumer Group 快速消费进冷库
   - 事后补偿对账
```

### 5.4 扩容限制

```
Kafka：Consumer 数 > Partition 数 → 多余 Consumer 空闲
RocketMQ：Consumer 数 > Queue 数 → 同上

扩容 Consumer 无效时 → 增加 Partition/Queue（Kafka 可在线增加）
```

### 5.5 预防设计

| 手段 | 说明 |
|------|------|
| Topic 隔离 | 核心与非核心分离，避免相互拖累 |
| 限流 | Producer 端 rate limit |
| 背压 | Consumer 慢时 pause Partition |
| 容量规划 | 峰值 TPS × 余量 > 消费能力的持续验证 |

## 六、死信队列（DLQ）

### 6.1 作用

- 多次重试仍失败的消息 → 隔离，**不阻塞主队列**。
- 人工排查、脚本补偿、告警。

### 6.2 RocketMQ DLQ

- 自动：`%DLQ%+{consumerGroup}`
- 默认最多重试 16 次后进 DLQ

### 6.3 Kafka DLQ

- **无原生 DLQ**，需自行实现：
  - 消费失败 → 写入 `{topic}.DLQ`
  - 或使用 Kafka Connect Dead Letter Queue

### 6.4 DLQ 处理流程

```
主 Topic 消费失败 → 重试 N 次 → DLQ
                                    ↓
                              监控告警
                                    ↓
                         人工/定时任务重新投递或补偿
```

## 七、分布式事务与 MQ

### 7.1 本地消息表

```
同一 DB 事务：
  INSERT order ...
  INSERT local_message (status=PENDING, payload=...)

定时任务扫描 PENDING → 发 MQ → 成功改 SENT
```

**优点**：简单、不依赖 MQ 事务。**缺点**：耦合 DB、需扫表。

### 7.2 RocketMQ 事务消息

见 [02-RocketMQ核心原理](./02-RocketMQ核心原理.md) 第十一章。

### 7.3 Outbox 模式

```
业务表 + outbox 表同事务写入
CDC（Debezium/Canal）监听 outbox → 发 MQ
```

**优点**：解耦、可靠。**缺点**：需 CDC 组件。

### 7.4 Saga

- 长事务拆为多步，每步本地事务 + 发消息。
- 失败执行 **补偿消息**。
- 适合跨多个服务的业务流程。

## 八、Exactly-Once 深入（Kafka）

### 8.1 三层 EOS

| 层级 | 机制 |
|------|------|
| Producer | 幂等 + 事务 |
| Broker | 事务协调、Commit Marker |
| Consumer | `isolation.level=read_committed` |

### 8.2 Consume-Transform-Produce

```java
consumer.poll();
producer.beginTransaction();
producer.send(result);
producer.sendOffsetsToTransaction(offsets, groupId);
producer.commitTransaction();
```

### 8.3 局限

- 仅 Kafka 生态内端到端
- 写 DB 仍需 **幂等** 或 **外部事务**
- 性能开销（事务协调）

## 九、对账与补偿

### 9.1 为什么需要对账

MQ 保证 At Least Once，**业务最终一致**需对账兜底。

### 9.2 对账方式

| 方式 | 说明 |
|------|------|
| 定时全量 | 源系统 vs 目标系统逐条比对 |
| 增量对账 | 按时间窗口比对流水 |
| 消息表状态 | local_message 表 PENDING 超时告警 |

### 9.3 补偿

- 缺失 → 重新发送或直调接口
- 重复 → 幂等忽略
- 不一致 → 人工介入 + 审计日志

## 十一、案例：订单支付通知

### 11.1 需求

支付成功 → 通知库存、积分、短信，不能丢、不能重复加积分。

### 11.2 方案

```
1. 支付服务：本地事务更新订单 + 写 local_message
2. 定时任务发 RocketMQ，Tag=PAY_SUCCESS，Key=orderId
3. 积分服务：Redis SETNX(orderId) + DB 唯一索引 + 状态机
4. 消费失败进 DLQ，对账任务每小时扫 unpaid 订单 vs 消息表
```

### 11.3 故障演练

| 故障 | 结果 |
|------|------|
| MQ 发送失败 | local_message 重试 |
| 积分 Consumer 宕机 | 积压，恢复后继续，幂等防重复 |
| 重复消息 | 唯一索引拦截 |

## 十三、消费超时与重试策略设计

### 13.1 超时层级

| 层级 | Kafka | RocketMQ |
|------|-------|----------|
| 拉取超时 | fetch.max.wait.ms | pullTimeout |
| 处理超时 | max.poll.interval.ms | consumeTimeout |
| 重试间隔 | 自行实现 | 内置 16 级递增 |

### 13.2 重试与 DLQ 设计原则

```
1. 可重试异常（网络、下游暂时不可用）→ 重试
2. 不可重试异常（数据格式错误、业务规则拒绝）→ 直接 DLQ
3. 重试次数上限 + 指数退避
4. DLQ 消费需独立 Group，人工/脚本处理
5. 监控 DLQ 深度，自动告警
```

### 13.3 重试风暴防护

- 下游故障时 Consumer 持续 RECONSUME_LATER → 放大压力
- **熔断**：连续失败 N 次 pause 消费，定时 probe
- **限流**：令牌桶控制消费速率

## 十四、消息轨迹与审计

### 14.1 RocketMQ Message Trace

- 记录：Producer 发送 → Broker 存储 → Consumer 消费
- 依赖 `_TraceTopic`，开启 `enableMsgTrace`

### 14.2 Kafka 审计

- **Kafka Audit** 或 **Confluent Audit Logs**
- 自行：Interceptor 记录到独立 Topic

### 14.3 业务审计

- 关键消息落 **audit_log** 表：messageId、payload hash、status、timestamp
- 合规场景（金融、订单）必备
