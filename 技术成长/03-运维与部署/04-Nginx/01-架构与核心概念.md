# 01 · 架构与核心概念

> **目标读者**：7 年 Java 后端，需理解 Nginx 进程模型、配置语法、与 Tomcat/Netty 的对比，并能独立编写可维护的 server 块。
> **预计阅读**：50 min · **难度**：★★★

## 1. Nginx 是什么、解决什么问题

Nginx（engine x）是高性能 **Web 服务器** + **反向代理** + **负载均衡器**，也可做 **API 网关**（限流、SSL 终结、静态资源）。

| 角色 | 典型场景 |
|------|----------|
| Web 服务器 | 直接返回 HTML/CSS/JS/图片 |
| 反向代理 | 隐藏内网 Java 服务，统一入口 |
| 负载均衡 | 多台 Spring Boot 实例分流 |
| SSL 终结 | 在 Nginx 解密 HTTPS，后端走 HTTP |
| 缓存 / 压缩 | 减轻后端压力 |

**Java 后端常见拓扑**：

```
Internet → SLB/云负载均衡 → Nginx（多台）→ Spring Boot × N
                                    ↓
                              静态资源 / Vue 打包产物
```

## 2. Master / Worker 进程模型

```
启动: nginx
  │
  ├── Master 进程（root 运行）
  │     ├── 读取 /etc/nginx/nginx.conf
  │     ├── 绑定 80/443 端口（启动时）
  │     ├── fork Worker 进程
  │     └── 接收 reload 信号 → 平滑重启 Worker
  │
  └── Worker 进程 × N（通常 = CPU 核数）
        └── 每个 Worker 单线程事件循环处理连接
```

| 进程 | 职责 |
|------|------|
| **Master** | 配置解析、Worker 管理、信号处理；**不处理业务请求** |
| **Worker** | accept 连接、读写 socket、执行模块逻辑 |

**为什么 Worker 通常设为 CPU 核数**：

```nginx
worker_processes auto;   # 自动 = CPU 核数
```

- 每个 Worker 独立事件循环，无锁竞争（连接分配由 accept_mutex 或 SO_REUSEPORT 协调）。
- 过多 Worker 增加上下文切换，过少无法吃满多核。

**对比 Tomcat**：

| | Nginx | Tomcat |
|---|-------|--------|
| 模型 | 多进程 + 单线程事件循环 | 线程池（BIO/NIO） |
| 擅长 | 静态文件、高并发短连接、代理 | Servlet、长业务逻辑 |
| 典型组合 | Nginx 前置 + Tomcat 8080 | — |

## 3. 事件驱动与非阻塞 IO

Worker 使用 **epoll**（Linux）/ kqueue（BSD）实现 **Reactor** 模型：

```
                    ┌─────────────────┐
  新连接 ──────────►│  epoll_wait     │
  可读事件 ────────►│  事件循环        │──► 读请求 → 处理 → 写响应
  可写事件 ────────►│  （单线程）      │
                    └─────────────────┘
```

- **非阻塞**：一个 Worker 可同时挂起数万连接，不会「一个慢客户端拖死线程池」。
- **与 Java NIO / Netty 同族**：Netty 的 EventLoop 思想类似，面试可类比。

```nginx
events {
    worker_connections 1024;   # 每个 Worker 最大并发连接
    use epoll;                 # Linux 默认
    multi_accept on;           # 一次 accept 多个连接
}
```

**理论最大连接数** ≈ `worker_processes × worker_connections`（实际还受 `ulimit -n`、内存限制）。

## 4. 配置文件结构

默认路径：`/etc/nginx/nginx.conf`（Linux）、`/usr/local/etc/nginx/nginx.conf`（Homebrew macOS）。

```nginx
# main 上下文
user nginx;
worker_processes auto;
error_log /var/log/nginx/error.log warn;
pid /run/nginx.pid;

events {
    worker_connections 1024;
}

http {
    include       /etc/nginx/mime.types;
    default_type  application/octet-stream;

    log_format main '$remote_addr - $remote_user [$time_local] '
                    '"$request" $status $body_bytes_sent '
                    '"$http_referer" "$http_user_agent" '
                    'rt=$request_time uct=$upstream_connect_time '
                    'uht=$upstream_header_time urt=$upstream_response_time';

    access_log /var/log/nginx/access.log main;

    sendfile on;
    tcp_nopush on;
    keepalive_timeout 65;

    # 可在此定义 upstream、gzip、limit_zone
    include /etc/nginx/conf.d/*.conf;   # 各 server 块常放这里
}
```

### 4.1 配置上下文嵌套

| 上下文 | 说明 |
|--------|------|
| `main` | 全局，仅顶层 |
| `events` | 连接处理模型 |
| `http` | HTTP 服务，含 server |
| `server` | 虚拟主机（按域名/IP 区分） |
| `location` | URI 匹配规则 |
| `upstream` | 后端服务器组（在 http 内） |
| `stream` | TCP/UDP 四层代理（与 http 平级，需 `--with-stream`） |

### 4.2 指令继承

```nginx
http {
    gzip on;                    # 全局开 gzip

    server {
        listen 80;
        # 继承 gzip on

        location /api {
            gzip off;           # 仅 /api 关闭
        }
    }
}
```

## 5. location 匹配规则（高频考点）

语法：`location [=|~|~*|^~] /path { ... }`

| 修饰符 | 含义 | 示例 |
|--------|------|------|
| `=` | 精确匹配 | `location = /health { return 200 'ok'; }` |
| `^~` | 前缀匹配，**匹配后不再检查正则** | `location ^~ /static/ { ... }` |
| `~` | 正则，**区分大小写** | `location ~ \.(jpg\|png)$ { ... }` |
| `~*` | 正则，不区分大小写 | |
| 无修饰符 | 前缀匹配 | `location /api { ... }` |

**匹配顺序**（简化记忆）：

1. 精确 `=`
2. 最长前缀 `^~`（命中则停止）
3. 正则 `~` / `~*`（按配置文件出现顺序，**第一个命中**）
4. 普通前缀（最长 wins）

```nginx
server {
    location = /health { return 200; }      # 1. 精确
    location ^~ /static/ { root /data; }   # 2. 前缀优先于下面正则
    location ~ \.php$ { ... }              # 3. 正则
    location / { proxy_pass http://backend; }  # 4. 兜底
}
```

**易错**：多个正则 location 时，**不是**「最精确的那个」，而是 **conf 里先出现的**。

## 6. 核心模块概览

| 模块 | 功能 |
|------|------|
| `ngx_http_core_module` | 基础 HTTP、location、root、index |
| `ngx_http_proxy_module` | 反向代理 `proxy_pass` |
| `ngx_http_upstream_module` | 负载均衡 |
| `ngx_http_ssl_module` | HTTPS |
| `ngx_http_gzip_module` | 压缩 |
| `ngx_http_limit_req_module` | 限流 |
| `ngx_http_rewrite_module` | `rewrite`、`return` |
| `ngx_http_access_module` | IP 黑白名单 |

查看已编译模块：

```bash
nginx -V 2>&1 | tr ' ' '\n' | grep module
```

## 7. 日志与排查

### 7.1 access_log 关键变量

| 变量 | 含义 |
|------|------|
| `$request_time` | 请求总耗时（秒） |
| `$upstream_response_time` | 后端响应耗时 |
| `$upstream_status` | 后端 HTTP 状态 |
| `$status` | 返回给客户端的状态 |

**慢请求排查**：`$request_time > 1` 且 `$upstream_response_time` 大 → 后端慢；`$upstream_response_time` 小但总时间长 → Nginx 或网络问题。

### 7.2 error_log 级别

`debug | info | notice | warn | error | crit | alert | emerg`

生产通常 `warn` 或 `error`。

## 8. 平滑 reload

```bash
nginx -t && nginx -s reload
```

流程：

1. Master 读新配置
2. 启动新 Worker
3. 旧 Worker 处理完当前连接后退出
4. **不丢在途请求**（长连接需注意旧 Worker  drain 时间）

**与 Java 优雅停机**：类似 Spring Boot `server.shutdown=graceful`，K8s `preStop`。

## 10. 本章小结

| 要点 | 记住 |
|------|------|
| 进程 | Master 管理，Worker 处理，通常 `worker_processes auto` |
| 并发 | epoll + 非阻塞，不是「一连接一线程」 |
| 配置 | main → events → http → server → location |
| location | `=` > `^~` > 正则顺序 > 前缀最长 |
| 运维 | `nginx -t` 再 reload |
