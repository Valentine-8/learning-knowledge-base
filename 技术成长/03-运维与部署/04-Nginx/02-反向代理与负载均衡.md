# 02 · 反向代理与负载均衡

> **目标读者**：能配置 upstream、理解 proxy_pass URI 变换、处理 502/504，并在 Java 微服务前部署 Nginx。
> **预计阅读**：60 min · **难度**：★★★★

## 1. 正向代理 vs 反向代理

```
正向代理（客户端知道代理）          反向代理（客户端不知道后端）
  Client ──► Proxy ──► Internet       Client ──► Nginx ──► Java:8080
  例：公司上网代理、VPN               例：生产 API 网关
```

| | 正向 | 反向 |
|---|------|------|
| 谁配置代理 | 客户端 | 服务端 |
| 隐藏谁 | 客户端身份 | 后端服务器 |
| Nginx 角色 | `proxy` 指令较少用 | **核心场景** |

## 2. proxy_pass 基础

### 2.1 HTTP 代理最小集

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8080;

    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

**为什么要带 Header**：

| Header | 作用 |
|--------|------|
| `Host` | 后端有时依 Host 做虚拟主机或租户路由 |
| `X-Real-IP` | 后端拿真实客户端 IP（否则看到 Nginx IP） |
| `X-Forwarded-For` | 代理链路上的 IP 列表 |
| `X-Forwarded-Proto` | 原始协议 http/https，Spring 可生成正确跳转 URL |

Spring Boot 识别客户端 IP：

```yaml
server:
  forward-headers-strategy: framework   # 信任 X-Forwarded-*
```

或 Tomcat `RemoteIpValve`。

### 2.2 proxy_pass 末尾 `/` 规则（必考）

| location | proxy_pass | 客户端请求 | 转发到后端 |
|----------|------------|------------|------------|
| `/api/` | `http://backend/` | `/api/user/1` | `/user/1` |
| `/api/` | `http://backend` | `/api/user/1` | `/api/user/1` |
| `/api` | `http://backend/` | `/api/user/1` | `//user/1`（易错） |

**规则**：

- `proxy_pass` **带 URI**（如 `http://host/` 或 `http://host/v1/`）：location 匹配部分被 **替换**。
- **不带 URI**（仅 `http://host` 或 `http://upstream_name`）：原始 URI **原样** 转发。

```nginx
# 常见：对外 /api，对内 Spring Boot 根路径
location /api/ {
    proxy_pass http://127.0.0.1:8080/;   # 去掉 /api 前缀
}
```

### 2.3 超时与缓冲

```nginx
location / {
    proxy_connect_timeout 5s;      # 连后端超时
    proxy_send_timeout    60s;     # 发请求到后端超时
    proxy_read_timeout    60s;     # 等后端响应超时（504 常见原因）

    proxy_buffering on;
    proxy_buffer_size 4k;
    proxy_buffers 8 4k;
}
```

| 现象 | 可能原因 |
|------|----------|
| **504 Gateway Timeout** | `proxy_read_timeout` 太短或后端处理慢 |
| **502 Bad Gateway** | 后端未启动、连接拒绝、返回非法响应 |
| **499**（access_log） | 客户端主动断开 |

## 3. upstream 负载均衡

### 3.1 基本定义

```nginx
upstream java_backend {
    server 192.168.1.10:8080 weight=3;
    server 192.168.1.11:8080 weight=1;
    server 192.168.1.12:8080 backup;      # 备用，主全挂才用
    server 192.168.1.13:8080 down;        # 维护，不参与

    keepalive 32;   # 与后端长连接池（需 proxy_http_version 1.1）
}

server {
    location / {
        proxy_pass http://java_backend;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
    }
}
```

### 3.2 负载均衡算法

| 算法 | 配置 | 说明 |
|------|------|------|
| 轮询 | 默认 | 依次分发 |
| 加权轮询 | `weight=n` | 按权重 |
| IP Hash | `ip_hash;` | 同一客户端 IP 固定到同一节点（会话粘滞） |
| 最少连接 | `least_conn;` | 分给当前连接最少的节点 |
| 通用 Hash | `hash $key consistent;` | 一致性 hash，节点增减影响面小 |

```nginx
upstream session_sticky {
    ip_hash;
    server app1:8080;
    server app2:8080;
}
```

**Java 会话注意**：生产更推荐 **Redis Session / JWT 无状态**，而非 ip_hash（扩容、故障转移会丢会话）。

### 3.3 被动健康检查（开源版）

Nginx 开源版无主动 HTTP 探针，靠 **被动失败**：

```nginx
upstream backend {
    server 10.0.0.1:8080 max_fails=3 fail_timeout=30s;
}
```

- 30s 内失败 3 次 → 标记不可用 30s。
- 商业版 `nginx plus` 或 `nginx_upstream_check_module` 可主动 check。

**生产常见**：前面再加云 SLB / K8s Service 做健康检查，Nginx 只做七层路由。

## 4. 灰度与分流

### 4.1 按权重分流（两套 upstream）

```nginx
upstream stable {
    server app-v1:8080;
}

upstream canary {
    server app-v2:8080;
}

split_clients "${remote_addr}${date_gmt}" $backend {
    95%     stable;
    5%      canary;
}

location / {
    proxy_pass http://$backend;
}
```

### 4.2 按 Header / Cookie

```nginx
map $http_x_canary $backend {
    default stable;
    "1"     canary;
}

location / {
    proxy_pass http://$backend;
}
```

### 4.3 与 Java 灰度配合

- 网关层：Nginx 分流到不同 Deployment（K8s）。
- 应用层：Spring Cloud Gateway + 元数据路由。
- **面试答法**：「入口 Nginx 做粗粒度流量切分，服务内用 Feature Flag 做细粒度」。

## 5. rewrite 与 redirect

```nginx
# 永久重定向
location /old-api/ {
    return 301 /api/;
}

# 内部 rewrite（浏览器 URL 不变）
location /api/v1/ {
    rewrite ^/api/v1/(.*)$ /v2/$1 break;
    proxy_pass http://backend;
}

# 强制 HTTPS
server {
    listen 80;
    return 301 https://$host$request_uri;
}
```

| 指令 | 区别 |
|------|------|
| `return` | 直接返回状态码/文本，停止处理 |
| `rewrite ... last` | 重新走 location 匹配 |
| `rewrite ... break` | 当前 location 内停止 rewrite |

## 6. 静态资源与反向代理共存

```nginx
server {
    listen 80;
    root /var/www/frontend/dist;

    location / {
        try_files $uri $uri/ /index.html;   # Vue SPA
    }

    location /api/ {
        proxy_pass http://java_backend/;
    }

    location ~* \.(js|css|png|jpg|gif|ico|woff2)$ {
        expires 7d;
        add_header Cache-Control "public, immutable";
    }
}
```

## 7. 四层 stream 代理（了解）

MySQL、Redis、 gRPC（部分场景）需要 TCP 代理：

```nginx
stream {
    upstream mysql_backend {
        server 10.0.0.1:3306;
        server 10.0.0.2:3306;
    }

    server {
        listen 3306;
        proxy_pass mysql_backend;
        proxy_connect_timeout 5s;
    }
}
```

需编译 `--with-stream` 或标准包已含。

## 8. 生产案例

### 案例 1：502 突发

**现象**：发布 Java 服务后 Nginx 502。

**排查**：

1. `curl http://127.0.0.1:8080/actuator/health` 本机是否通
2. SELinux / 防火墙是否拦 8080
3. `proxy_pass` 地址是否写错（Docker 里不能用 127.0.0.1 指容器内，要用 service 名）

### 案例 2：上传大文件 413

```nginx
client_max_body_size 50m;   # 默认 1m，放 http 或 server
```

Spring 同步配置：

```yaml
spring.servlet.multipart.max-file-size: 50MB
```

### 案例 3：WebSocket 404

需升级头（见第 05 章），否则 Nginx 当普通 HTTP 代理。

## 9. 面试题精选

| 问 | 答 |
|----|-----|
| Nginx 负载均衡算法？ | 轮询、加权、ip_hash、least_conn、hash consistent |
| 如何保证会话粘滞？ | ip_hash / sticky cookie；更好是无状态 + Redis |
| 502 和 504 区别？ | 502 无效网关响应；504 等待上游超时 |
| upstream  keepalive 作用？ | 复用到后端的 TCP 连接，减握手开销 |
| 如何做蓝绿？ | 两套 upstream，改 DNS 或 `proxy_pass` 指向；K8s 用 Service selector 切换 |

## 10. 自测

1. 写配置：外部 `/api/user` → 内部 `http://spring:8080/user`（去前缀）。
2. 三台后端 weight 3:2:1，说明请求比例期望。
3. 解释 `max_fails` 和 `fail_timeout` 配合行为。
