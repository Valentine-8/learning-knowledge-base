# 10 · 本地模型部署与推理优化

> **能力层**：L4→L5　**难度**：★★★　**预计工时**：12h
> **一句话**：把开源大模型（Qwen、Llama、DeepSeek 等）部署在自己的机器/GPU 上，实现**数据不出内网、无 API 费用、可控可定制**。这是数据敏感型企业（金融/政务/医疗）的刚需。
> **前置**：[02-LLM-API集成实战](./02-LLM-API集成实战(Java).md)、Linux/Docker、了解 GPU 基础。

---

## 一、为什么要本地部署

| 驱动 | 说明 |
|------|------|
| **数据合规** | 金融/政务/医疗数据不能发给第三方 API（呼应 [09-安全](./09-LLM安全与合规.md)）|
| **成本** | 高频调用时，自建可能比 API 便宜（但要算 GPU 成本，见 [12](./12-AI应用架构与成本工程.md)）|
| **可控** | 不受 API 限流/涨价/下线影响，版本固定 |
| **定制** | 可微调（见 [11](./11-模型微调入门(LoRA).md)）、可离线 |
| **低延迟** | 内网部署无网络往返 |

代价：要 GPU、要运维、开源模型能力通常弱于顶级闭源模型。**决策见 [12-选型](./12-AI应用架构与成本工程.md)**。

## 二、两条路线：开发试用 vs 生产部署

| | Ollama | vLLM |
|--|--------|------|
| 定位 | 本地开发/单机试用 | 生产级高吞吐推理服务 |
| 上手 | 极简，一条命令 | 需配置，Python 环境 |
| 性能 | 一般（够个人用） | 高（PagedAttention、连续批处理）|
| 并发 | 弱 | 强（生产多用户）|
| 硬件 | CPU 也能跑小模型 | 基本要 GPU |
| 何时用 | 学习、Demo、[前面所有篇](./README.md)的本地测试 | 真上生产、多并发 |

其他：LM Studio（图形界面）、TGI（HuggingFace）、SGLang、llama.cpp（极致量化/端侧）。

## 三、Ollama 实战（开发首选，前面各篇的本地后端）

```bash
# 安装后拉模型
ollama pull qwen2.5:7b            # 通义 7B，中文好
ollama pull deepseek-r1:7b        # 推理模型
ollama pull nomic-embed-text      # embedding（给 04/05 用）

ollama run qwen2.5:7b             # 命令行聊天
ollama list                       # 已装模型
```

Ollama 自带 **OpenAI 兼容 API**，你 [02 篇](./02-LLM-API集成实战(Java).md) 的 Java 代码改个 base_url 就能用：
```yaml
spring:
  ai:
    openai:
      base-url: http://localhost:11434
      api-key: ollama          # 占位即可
      chat:
        options:
          model: qwen2.5:7b
```

> **这就是为什么本目录所有 Demo 都能免 API Key 学**——统一用 Ollama 当本地后端。

## 四、量化（Quantization）—— 让大模型跑在小显存

模型参数默认 FP16（每参数 2 字节）。**量化**用更低精度（INT8/INT4）存储，大幅降显存，代价是精度略降。

| 精度 | 每参数 | 7B 模型约需显存 | 质量 |
|------|--------|----------------|------|
| FP16 | 2 B | ~14 GB | 最好 |
| INT8 | 1 B | ~7 GB | 几乎无损 |
| INT4 | 0.5 B | ~4 GB | 略降，多数场景可接受 |

常见量化格式：
- **GGUF**：llama.cpp/Ollama 用，CPU/GPU 混合，端侧友好
- **AWQ / GPTQ**：GPU 推理常用，vLLM 支持
- **BitsAndBytes (bnb)**：训练/微调时的量化（见 [11](./11-模型微调入门(LoRA).md) QLoRA）

**显存估算口诀**：`模型显存 ≈ 参数量(B) × 每参数字节数`，再加 KV Cache（随上下文长度和并发增长，常占额外 20~50%）。

## 五、vLLM 生产部署

```bash
# 启动一个 OpenAI 兼容的推理服务
python -m vllm.entrypoints.openai.api_server \
  --model Qwen/Qwen2.5-7B-Instruct \
  --quantization awq \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.9 \
  --port 8000
```

vLLM 的两个关键优化（面试点）：
- **PagedAttention**：像操作系统分页管理 KV Cache，显存利用率高、支持更大并发
- **Continuous Batching（连续批处理）**：动态拼批，不同长度请求高效共享 GPU，吞吐远高于静态批处理

同样是 OpenAI 兼容接口，Java 侧无缝切换。

## 六、推理性能指标与优化

| 指标 | 含义 |
|------|------|
| **TTFT** (Time To First Token) | 首 token 延迟，影响体验 |
| **TPOT / ITL** | 每 token 生成时间，决定"打字"速度 |
| **Throughput** | 吞吐（tokens/s 或 请求/s），决定成本 |
| **并发数** | 同时能服务多少请求 |

优化手段：量化、连续批处理、合适的 `max-model-len`、KV Cache 优化、多卡张量并行（大模型）、投机解码（speculative decoding）。

## 八、常见坑

| 坑 | 现象 | 解法 |
|----|------|------|
| 显存不够 OOM | 加载/推理崩 | 量化(INT4)、换小模型、减 max-len、减并发 |
| 只算模型没算 KV Cache | 上线并发就爆显存 | 预留 KV Cache 显存，压测定并发 |
| Ollama 扛生产并发 | 高并发慢/排队 | 生产用 vLLM/TGI |
| 量化太狠 | 质量明显下降 | INT8 更稳，INT4 要评估(用[08](./08-AI可观测与评测.md)评估集) |
| 开源模型当闭源用 | 效果不及预期 | 认清能力差距，配合 RAG/微调，或混合路由 |
| 忽略许可证 | 商用侵权 | 查模型 license（部分限商用）|
| CPU 跑大模型 | 巨慢 | 小模型 + 量化，或上 GPU |

## 九、面试考点

- **Q：什么场景要本地部署 LLM？代价？**
  A：数据合规（不能出内网）、高频降本、可控可定制、离线。代价：GPU 成本、运维、开源模型能力通常弱于顶级闭源。
- **Q：量化是什么？INT4 vs FP16？**
  A：用低精度存参数降显存。FP16 每参 2 字节质量最好；INT4 每参 0.5 字节、显存约 1/4，质量略降。要用评估集确认可接受。
- **Q：vLLM 为什么快？**
  A：PagedAttention（分页管理 KV Cache 提升显存利用）+ 连续批处理（动态拼批提升吞吐）。
- **Q：怎么估算模型显存？**
  A：参数量 × 每参字节数（FP16=2, INT8=1, INT4=0.5）+ KV Cache（随上下文/并发增长）。
- **Q：Ollama 和 vLLM 区别？**
  A：Ollama 开发试用极简、并发弱；vLLM 生产级、高吞吐、需 GPU。都提供 OpenAI 兼容接口。
