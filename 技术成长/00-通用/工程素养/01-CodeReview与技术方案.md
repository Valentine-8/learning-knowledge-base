# 01 · Code Review 与技术方案

> **预计阅读**：90 min

---

## 1. Code Review 的价值

| 对谁 | 价值 |
|------|------|
| 作者 | 早期发现缺陷、统一风格 |
| Reviewer | 熟悉模块、传播最佳实践 |
| 团队 | 知识共享、降低 bus factor |

**7 年角色**：不只审代码，还要**定标准、示范 Review 质量**。

---

## 2. Review 什么

### 2.1 正确性

- 边界条件：空、null、越界
- 并发：共享变量、锁粒度、ThreadLocal 泄漏
- 事务：边界、传播、自调用失效
- 业务规则：与 PRD/接口契约一致

### 2.2 可读性与设计

- 命名是否表达意图
- 函数长度、单一职责
- 重复代码是否可抽取（但不过度抽象）
- 设计模式：该用否？滥用否？

### 2.3 性能

- N+1 查询
- 无界集合（`select *` 大表）
- 循环内 RPC/DB
- 缓存使用是否合理

### 2.4 安全

- SQL 注入（`#{}` vs `${}`）
- 越权：是否校验资源归属
- 敏感数据日志脱敏
- 依赖漏洞（CVE）

### 2.5 测试

- 核心路径有单测？
- 边界与异常分支？
- 集成测试是否需要？

---

## 3. 怎么 Review

```
1. 先读 PR 描述，理解意图
2. 看整体结构，再看细节
3. 提建议不说教；区分 must-fix / nit
4. 小 PR（<400 行）效率最高
5. 24h 内响应
```

**评论模板**：

- 「这里如果并发 X 和 Y，会不会…？」（引导思考）
- 「建议提取方法，便于单测」（具体可执行）
- 「nit: 命名可改为…」（不阻塞）

---

## 4. AI 时代 Review 重点

AI 生成代码常见问题：

- 事务边界错误
- 线程池误用 / 阻塞在 reactive 线程
- 安全校验遗漏
- 「看起来对」但未处理幂等
- 过度抽象、难维护

**原则**：AI 写初稿，人负责**正确性与生产风险**。

## 5. 技术方案设计（ADR）

### 5.1 何时写 ADR

- 引入新中间件
- 架构变更
- 跨团队接口约定
- 有争议的技术选型

### 5.2 ADR 模板

```markdown
# ADR-001：订单超时取消用延迟消息

## 背景
30 分钟未支付需自动取消

## 目标
- 准时取消，误差 < 1 min
## 非目标
- 不处理已支付退款

## 方案对比
| 方案 | 优点 | 缺点 |
| 扫表 | 简单 | DB 压力、延迟大 |
| 延迟 MQ | 精准、解耦 | 依赖 MQ、需幂等 |
| 时间轮 | 本地高效 | 多实例复杂 |

## 决策
选 RocketMQ 延迟消息

## 风险与缓解
- 消息重复 → 幂等表
- MQ 不可用 → 降级扫表补偿

## 回滚
关闭延迟消费，切回扫表

## 监控
取消成功率、延迟分布、MQ 积压
```

### 5.3 好方案的特征

- 有**数据**支撑（QPS、存储、成本）
- 明确**不做什么**
- 风险与回滚可操作
- 监控指标可验证

---

## 6. 方案评审会议

| 角色 | 关注点 |
|------|--------|
| 架构 | 边界、扩展、一致性 |
| 开发 | 实现成本、工期 |
| 测试 | 可测性、环境 |
| 运维 | 部署、监控、容量 |
| 安全 | 合规、漏洞 |

**输出**：结论、待办、决策记录（ADR 编号）。

---

## 7. 常见反模式

- [ ] Review 只改格式不改逻辑
- [ ] 方案只写一种选项（伪选型）
- [ ] 无监控就上线
- [ ] ADR 写完无人维护
