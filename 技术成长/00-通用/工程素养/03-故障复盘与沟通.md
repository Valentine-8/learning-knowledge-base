# 03 · 故障复盘与沟通

> **预计阅读**：90 min

---

## 1. 故障复盘的目标

```
找根因 → 改进落地 → 组织学习
```

**不是**：甩锅、走过场、只写「加强意识」。

---

## 2. 复盘模板

```markdown
## 基本信息
- 标题、等级（P0-P3）、时间线
- 影响面：用户量、时长、资损

## 时间线
14:00 告警触发
14:05 值班响应
14:20 定位慢 SQL
14:45 扩容 + 杀慢查询
15:00 恢复

## 根因（5 Whys）
现象：支付成功率下降
Why1：网关超时
Why2：连接池耗尽
Why3：慢 SQL 占满连接
Why4：缺索引
Why5：上线前未 explain
→ 根因：缺少 SQL 评审门禁

## 改进项
| 项 | 负责人 | DDL | 状态 |
| 慢 SQL CI 门禁 | 张三 | 2025-08-01 | 进行中 |
| 连接池监控告警 | 李四 | 2025-07-15 | 完成 |

## 经验总结
可复用的排查路径、文档链接
```

---

## 3. 5 Whys 技巧

- 每层要有**证据**，不是猜
- 区分**触发原因**和**根本原因**
- 止于**可行动的改进**
- 多人参与避免盲点

**常见根因类别**：变更、容量、依赖、配置、代码缺陷、流程缺失。

---

## 4. 复盘文化

| 做法 | 说明 |
|------|------|
| 不追责个人 | 聚焦系统和流程 |
| 改进项跟踪 | 有 DDL，复盘会复查 |
| 分级 | P0 必须复盘，P2 可选 |
| 分享 | 匿名案例内部分享 |

## 5. 跨团队沟通

### 5.1 与产品

| 场景 | 要点 |
|------|------|
| 需求澄清 | 业务规则、异常流、边界 |
| 排期冲突 | 分期交付、砍 scope |
| 线上问题 | 影响面、恢复 ETA、用户话术 |

**技巧**：用用户语言复述需求，确认后再开发。

### 5.2 与测试

- 提前对齐**核心用例**和**边界**
- 提供**可测性**：测试 hook、Mock 接口
- 环境、数据、账号提前准备
- 缺陷分级与修复优先级

### 5.3 与运维/SRE

- 部署步骤、回滚方案、配置变更
- 监控指标、告警阈值
- 容量评估、扩容预案
- 变更窗口沟通

### 5.4 与上级

- **风险透明**：黄灯早报
- **要资源要早**：人力、优先级、跨团队协调
- **结果量化**：性能提升 %、故障时长缩短

---

## 6. 书面沟通

| 文档 | 用途 |
|------|------|
| 会议纪要 | 结论 + 待办 + 负责人 |
| 技术方案 | ADR、设计文档 |
| 变更通知 | 上下游知悉 |
| 故障报告 | 复盘输出 |

**原则**：口头说的，重要事项**书面确认**；避免「口头需求」。

---

## 7. 冲突处理

1. 对事不对人
2. 摆数据、摆方案，不只摆观点
3. 升级路径清晰（TL → 总监）
4. 记录决策，避免反复

---

## 8. 线上故障 ONCALL 沟通

```
1. 确认影响面（监控、客服）
2. 拉 war room（IM 群）
3. 指定 incident commander
4. 时间线记录
5. 恢复后同步状态
6. 48h 内复盘
```

---

5. 线上故障如何对外沟通？
