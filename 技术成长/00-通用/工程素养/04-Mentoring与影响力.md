# 04 · Mentoring 与影响力

> **预计阅读**：70 min

---

## 1. Mentoring 的定位

7 年工程师通常带 **1～3 人**：

```
不是替人写代码，而是提升团队产能与质量
```

---

## 2. 带新人方法

### 2.1 任务拆解

- 大需求拆成**可独立验证**的小步
- 第一步 often 是「读代码 + 画流程图」
- 明确**完成标准**和**截止时间**

### 2.2 结对编程

- 复杂模块首次一起写
- Reviewer 先讲思路，再让新人动手
- 轮换 driver/navigator

### 2.3 Code Review 作教学

- 不只改代码，解释**为什么**
- 推荐文档/章节链接
- 鼓励新人 Review 你的 PR

### 2.4 排查思路

```
现象 → 假设 → 验证 → 缩小范围 → 根因
```

**避免**：直接给答案；应问「你会先查什么？为什么？」

---

## 3. 1:1 与反馈

| 频率 | 内容 |
|------|------|
| 双周 1:1 | 进展、困难、成长目标 |
| 即时反馈 | 具体行为 + 影响 |
| 季度 | 目标回顾、晋升材料 |

**反馈公式**：SBI（情境-行为-影响）

「昨天 PR 里（S）直接改了核心逻辑没沟通（B），可能导致理解偏差（I）」

---

## 4. 技术影响力

### 4.1 文档沉淀

- 本知识库即是范例
- Runbook、架构图、FAQ
- 新人 onboarding 文档

### 4.2 内部分享

| 形式 | 频率 |
|------|------|
| 技术分享会 | 月/季 |
| 读书会 | 可选 |
| 故障案例复盘 | 事件驱动 |

**费曼技巧**：能讲清楚才是真的懂。

### 4.3 规范制定

| 规范 | 内容 |
|------|------|
| 日志 | traceId、级别、脱敏 |
| 异常 | 业务码、不吞异常 |
| API | 命名、版本、错误体 |
| DB 变更 | 评审、回滚、灰度 |

规范要**可执行**（lint/CI  enforce），不只写在 wiki。

### 4.4 开源与对外

- 博客、演讲、开源贡献
- 求职与晋升加分
- 选型：与业务相关、能持续维护的主题

---

## 5. Tech Lead 日常

```
30% 编码  +  30% Review/设计  +  20% 沟通  +  20% 带人
```

平衡：**不能只做救火队长**，要留时间建机制。

---

## 6. 常见误区

- [ ]  micromanage 每行代码
- [ ] 只分配脏活累活
- [ ] 不给成长空间（全自己扛）
- [ ] 规范写完不推广
- [ ] 分享只讲结论不讲踩坑

---

## 7. 面试要点

1. 如何带新人上手？
2. 新人代码质量差怎么办？
3. 如何建立团队规范？
4. 技术影响力体现在哪？
5. 如何做内部分享？
