# 02 · 估时排期与选型

> **预计阅读**：80 min

---

## 1. 估时的本质

估时不是「猜天数」，而是：

```
WBS 拆分 → 风险识别 → 留 buffer → 对齐优先级
```

**7 年工程师**：估时要能解释假设，而不是拍脑袋。

---

## 2. WBS 工作分解

| 原则 | 说明 |
|------|------|
| 粒度 | 0.5～2 天/项 |
| 可交付 | 每项有明确产出 |
| 依赖显式 | 前后端、联调、数据迁移 |
| 可验证 | 测试可覆盖 |

**示例：订单导出功能**

```
1. 接口设计 + 评审（0.5d）
2. 异步任务框架接入（1d）
3. 查询与分页逻辑（1d）
4. Excel 生成与 OSS 上传（1d）
5. 单测 + 集成测试（1d）
6. 联调 + 压测（1d）
7. 上线 + 监控（0.5d）
合计：6d → buffer 30% → 约 8d
```

---

## 3. Buffer 与风险

| 风险类型 | 示例 | 应对 |
|----------|------|------|
| 技术 | 首次用新 MQ | spike + 原型 |
| 依赖 | 第三方 API 不稳定 | 早对接、Mock |
| 环境 | 测试数据不全 | 提前准备 |
| 范围蔓延 | 产品加需求 | 必须/可砍清单 |
| 线上 | 发布后救火 | 留 20% 机动 |

**Buffer 建议**：常规 20～30%；新技术/迁移 40%+。

---

## 4. 排期沟通

### 4.1 与产品

- 交付**分期**：MVP vs 完整版
- 明确**截止日期的代价**（砍 scope / 加人 / 延期）
- 书面确认优先级

### 4.2 与上级

- 风险**早说**，不要临近 deadline 爆雷
- 用数据：「联调依赖 X 团队，他们排期到下周」
- 要资源：人力、环境、优先级升级

---

## 5. 技术选型方法论

### 5.1 澄清需求

| 维度 | 问题 |
|------|------|
| 规模 | QPS、数据量、增长 |
| 一致性 | 强一致 / 最终一致 |
| 延迟 | P99 要求 |
| 团队 | 熟悉度、运维能力 |
| 成本 |  license、云费用、人力 |

### 5.2 列方案并打分

| 维度 | 权重 | 方案 A | 方案 B |
|------|:----:|:------:|:------:|
| 性能 | 25% | 4 | 3 |
| 成本 | 20% | 3 | 5 |
| 运维 | 20% | 3 | 4 |
| 生态 | 15% | 5 | 3 |
| 团队 | 20% | 4 | 2 |

### 5.3 决策原则

- 选**够用**，不追新
- 优先**团队能运维**的
- 有**退出策略**（vendor lock-in 评估）
- **写 ADR** 记录

---

## 6. 常见选型场景

| 场景 | 考量 |
|------|------|
| MySQL vs PostgreSQL | JSON、GIS、团队经验 |
| Redis vs Memcached | 数据结构、持久化 |
| Kafka vs RocketMQ | 顺序、事务消息、生态 |
| MyBatis vs JPA | SQL 控制 vs 开发效率 |
| MVC vs WebFlux | 阻塞 vs 高并发 IO |

---

## 7. 估时反模式

- [ ] 只估开发不测联调
- [ ] 忽略 Code Review 和修复轮次
- [ ] 假设「不会有 bug」
- [ ] 多人并行却按串行估
- [ ] 选型只看 GitHub star
