# 04 · 性能优化与限流

> **目标读者**：能调 worker/连接数、gzip/缓存、limit_req 保护 Java API，并读懂 access_log 中的耗时字段。
> **预计阅读**：50 min · **难度**：★★★★

---

## 1. 性能调优总览

```
┌─────────────┐   ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│ 系统层       │ → │ Nginx 核心   │ → │ 代理/缓存    │ → │ 后端 Java    │
│ ulimit CPU  │   │ worker/epoll│   │ gzip buffer │   │ 线程池 SQL   │
└─────────────┘   └─────────────┘   └─────────────┘   └─────────────┘
```

Nginx 本身通常不是瓶颈；**先定位是 Nginx、网络还是 Java**。

## 2. 系统与 Worker 调优

```bash
# 文件描述符
ulimit -n 65535

# /etc/security/limits.conf
nginx soft nofile 65535
nginx hard nofile 65535
```

```nginx
worker_processes auto;
worker_rlimit_nofile 65535;

events {
    worker_connections 65535;
    multi_accept on;
    use epoll;
}
```

**最大连接估算**：`worker_processes × worker_connections`；HTTPS 还受 **SSL 握手 CPU** 限制，未必能跑满理论值。

| 参数 | 建议 |
|------|------|
| `worker_processes` | `auto` 或 CPU 核数 |
| `worker_connections` | 1024～65535，看内存 |
| `multi_accept` | on，高并发 accept |

## 3. HTTP 基础优化

```nginx
http {
    sendfile on;           # 零拷贝发静态文件
    tcp_nopush on;         # 配合 sendfile，攒包再发
    tcp_nodelay on;        # 小包立即发，降延迟

    keepalive_timeout 65;
    keepalive_requests 1000;

    types_hash_max_size 2048;
    server_tokens off;     # 隐藏版本号，安全
}
```

## 4. gzip 压缩

```nginx
gzip on;
gzip_vary on;
gzip_proxied any;
gzip_comp_level 5;          # 1～9，6 以上 CPU 陡增
gzip_min_length 256;
gzip_types
    text/plain
    text/css
    application/json
    application/javascript
    text/xml
    application/xml;
```

| 注意 | 说明 |
|------|------|
| 已压缩格式 | jpg/png/gzip 不要再压 |
| JSON API | 通常可压 70%+，减带宽 |
| CPU | 高 QPS 时 comp_level 降到 3～4 |

**与 Spring 对比**：`server.compression.enabled=true` 二选一即可，**避免重复压缩**。

## 5. 代理缓存（慎用）

```nginx
proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=api_cache:10m max_size=1g inactive=60m;

location /api/public/ {
    proxy_cache api_cache;
    proxy_cache_valid 200 10m;
    proxy_cache_key "$scheme$request_method$host$request_uri";
    add_header X-Cache-Status $upstream_cache_status;

    proxy_pass http://backend;
}
```

| 场景 | 是否缓存 |
|------|----------|
| 静态 GET 配置 | 可以 |
| 用户私有数据 | **禁止** |
| 带 Authorization | 需 `proxy_cache_bypass` |

**Java 侧**：用 Redis 做业务缓存更常见；Nginx 缓存适合静态或极少变的 GET。

## 6. 限流 limit_req（漏桶）

```nginx
http {
    limit_req_zone $binary_remote_addr zone=per_ip:10m rate=10r/s;
    limit_req_zone $server_name zone=global:10m rate=1000r/s;

    limit_conn_zone $binary_remote_addr zone=addr:10m;
}

server {
    location /api/login {
        limit_req zone=per_ip burst=5 nodelay;   # 允许突发 5
        limit_conn addr 10;
        proxy_pass http://backend;
    }
}
```

| 参数 | 含义 |
|------|------|
| `rate=10r/s` | 平均每秒 10 请求 |
| `burst=n` | 桶容量，短时突发 |
| `nodelay` | 突发立即处理，不排队延迟 |
| 无 nodelay | 超出 rate 部分延迟处理 |

**返回 503** 时可自定义：

```nginx
limit_req_status 429;
error_page 429 = @rate_limit;
location @rate_limit {
    default_type application/json;
    return 429 '{"code":429,"msg":"too many requests"}';
}
```

**与 Java 限流**：Sentinel / Guava RateLimiter 做 **业务维度**（用户 ID、接口）；Nginx 做 **入口防护**（防 DDoS、刷登录）。

## 7. 连接限制与 IP 黑白名单

```nginx
# 黑名单
deny 192.168.1.100;
allow 10.0.0.0/8;
deny all;

# geo 模块
geo $limit {
    default 1;
    10.0.0.0/8 0;    # 内网不限
}

map $limit $limit_key {
    0 "";
    1 $binary_remote_addr;
}

limit_req_zone $limit_key zone=limited:10m rate=10r/s;
```

## 8. 静态资源缓存头

```nginx
location ~* \.(js|css|png|jpg|jpeg|gif|ico|svg|woff2)$ {
    expires 30d;
    add_header Cache-Control "public, max-age=2592000, immutable";
    access_log off;    # 静态可关 access 减 IO
}
```

带 hash 的 webpack/vite 文件名 → `immutable` 长期缓存。

## 9. 监控指标

| 指标 | 来源 |
|------|------|
| QPS | access_log 统计 |
| 延迟 | `$request_time`、`$upstream_response_time` |
| 4xx/5xx 率 | `$status` |
| 活跃连接 | `stub_status` 模块 |

```nginx
location /nginx_status {
    stub_status on;
    allow 127.0.0.1;
    deny all;
}
```

输出：`Active connections`、`Reading/Writing/Waiting`。

**Prometheus**：nginx-prometheus-exporter 抓取 stub_status 或 VTS 模块。

## 10. 压测与瓶颈判断

```bash
# ab 简单压测
ab -n 10000 -c 100 https://api.example.com/health

# wrk
wrk -t4 -c200 -d30s https://api.example.com/api/list
```

| 现象 | 可能瓶颈 |
|------|----------|
| Nginx CPU 100%，upstream 低 | SSL、gzip、正则 location 过多 |
| upstream_response_time 高 | Java/SQL 慢 |
| Waiting 连接多 | keepalive 不够或后端慢 |
| 502/504 增多 | 后端线程池满或超时 |

## 11. 生产案例

**案例：大促登录接口被刷**

1. Nginx `limit_req` 每 IP 5r/s + burst 10
2. Java 验证码 + Sentinel 按 IP/账号限流
3. WAF / 云 DDoS 防护在 Nginx 前

**案例：静态资源占满磁盘 IO**

- CDN 托管静态
- Nginx `open_file_cache` 缓存文件句柄

```nginx
open_file_cache max=10000 inactive=20s;
open_file_cache_valid 30s;
```

## 12. 面试题

| 问 | 答 |
|----|-----|
| limit_req 原理？ | 漏桶；rate 平均速率，burst 桶深 |
| Nginx 和 Sentinel 限流分工？ | Nginx 入口 IP/连接；Sentinel 业务规则、熔断 |
| sendfile 是什么？ | 内核态直接磁盘到 socket，少用户态拷贝 |
