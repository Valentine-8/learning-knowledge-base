# 02 · DDD 与限界上下文

> **预计阅读**：90 min

---

## 1. 为什么需要 DDD

| 痛点 | DDD 回应 |
|------|----------|
| 贫血模型 | 行为内聚到领域对象 |
| 大泥球 | 限界上下文划边界 |
| 微服务乱拆 | 按业务能力拆分 |
| 跨团队扯皮 | 统一语言（Ubiquitous Language） |

**定位**：DDD 是**复杂业务**的建模方法，不是所有项目都需要全套战术设计。

---

## 2. 战略设计：限界上下文

```
┌─────────────┐     ACL      ┌─────────────┐
│  订单上下文  │ ──────────→ │  库存上下文  │
└─────────────┘              └─────────────┘
       │ 领域事件
       ▼
┌─────────────┐
│  支付上下文  │
└─────────────┘
```

| 概念 | 说明 |
|------|------|
| 限界上下文 | 模型有效边界；同一词在不同上下文含义可不同 |
| 上下文映射 | 合作关系、客户-供应商、防腐层等 |
| 防腐层 ACL | 隔离外部模型，内部保持纯净 |

**微服务拆分原则**：一个限界上下文 ≈ 一个服务（或一组紧耦合模块），**不是**一张表一个服务。

---

## 3. 战术设计核心

### 3.1 实体 Entity

- 有唯一标识（ID）
- 生命周期内属性可变
- 例：`Order`（orderId 不变，状态会变）

### 3.2 值对象 Value Object

- 无 ID，不可变
- 按属性相等
- 例：`Money`、`Address`、`OrderLine`（某些团队建模为值对象）

```java
public record Money(BigDecimal amount, Currency currency) {
    public Money add(Money other) { /* 校验币种 */ }
}
```

### 3.3 聚合 Aggregate

- **一致性边界**：事务内只改一个聚合
- **聚合根**：外部只能通过根访问内部实体
- 例：`Order` 是根，`OrderItem` 不单独对外暴露 Repository

**规则**：

- 跨聚合用 ID 引用，不直接持有对象
- 跨聚合一致性用领域事件或最终一致

### 3.4 领域服务 Domain Service

- 跨实体、不属于单一实体的业务逻辑
- 例：`PricingService` 计算复杂定价

### 3.5 领域事件

```java
// 订单已支付 → 触发库存扣减、积分增加
record OrderPaidEvent(OrderId orderId, Money amount) {}
```

解耦上下文，支持异步与扩展。

## 4. 分层架构（经典）

```
Interface（Controller / Facade）
    ↓
Application（用例编排、DTO、事务边界）
    ↓
Domain（实体、值对象、领域服务、仓储接口）
    ↓
Infrastructure（JPA/MyBatis 实现、MQ、RPC）
```

**反模式**：Controller 直接调 Mapper；Service 全是 CRUD 无领域行为。

---

## 5. 仓储 Repository

- 领域层定义接口：`OrderRepository`
- 基础设施层实现：JPA / MyBatis
- 只加载/持久化**聚合根**

---

## 6. 与微服务的关系

| DDD 概念 | 微服务实践 |
|----------|------------|
| 限界上下文 | 服务边界 |
| 聚合 | 单服务内事务边界 |
| 领域事件 | MQ 跨服务通信 |
| 防腐层 | 对接第三方 API 的 Adapter |

**分布式单体警告**：拆了很多服务但共享数据库、紧耦合调用链。

---

## 7. 落地建议（7 年视角）

1. **事件风暴**（可选）：梳理领域事件与聚合
2. **统一语言**：产品、开发、测试同一套术语
3. **先模块化再微服务**：单体内按包划分上下文
4. **不要过度**：CRUD 系统用贫血模型 + 清晰分层即可

---

## 8. 面试要点

| 问 | 答 |
|----|-----|
| 实体和值对象区别？ | ID、可变性、相等性 |
| 聚合根作用？ | 一致性入口，隐藏内部 |
| DDD 如何指导拆服务？ | 按限界上下文，数据归属清晰 |
| 跨聚合事务？ | 领域事件 + 最终一致，避免 2PC 滥用 |

---

## 9. 易错点

- [ ] 每个表一个聚合根
- [ ] 聚合过大（整个订单系统一个聚合）
- [ ] 领域层依赖 Spring/JPA 注解污染
- [ ] 为了 DDD 引入过多抽象层
