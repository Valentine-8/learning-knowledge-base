# 03 · 分布式锁与分布式 ID

> **目标读者**：7 年 Java 后端，能选型分布式锁与 ID 方案，Redis 细节跳转专题，ZK 锁见 [06 章](./06-ZooKeeper与注册中心.md)。
> **预计阅读**：50 min · **难度**：★★★★

---

## 1. 为什么需要分布式锁

多实例部署时，JVM `synchronized` / `ReentrantLock **仅进程内** 有效。

```
实例1 ──┐
实例2 ──┼──► 同一资源：库存扣减、定时任务、幂等门闩
实例3 ──┘
```

| 需求 | 说明 |
|------|------|
| 互斥 | 同一时刻单持有者 |
| 防死锁 | TTL 或续期 |
| 安全释放 | 仅持有者释放 |
| 可重入 | 可选 |

---

## 2. 实现对比总览

| 实现 | 优点 | 缺点 |
|------|------|------|
| **Redis SET NX EX** | 快、简单 | 主从切换边界；需正确 unlock |
| **Redisson** | 看门狗续期、可重入 | 同 Redis 基础设施 |
| **ZooKeeper 临时顺序节点** | **强一致**、会话断开自动释放 | 性能、运维、依赖 ZK |
| **DB 唯一索引 / for update** | 无新组件 | 性能差、DB 压力 |
| **etcd lease** | 强一致 | 偏云原生栈 |

---

## 3. Redis 分布式锁（概要）

**基本加锁**：

```bash
SET lock:order:10001 uuid NX EX 30
```

**释放须校验持有者**（Lua 原子）：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
else return 0 end
```

**主从切换丢锁**：主加锁未同步到从，主宕机，从升主后另一客户端可加锁 — **RedLock 有争议**，金融级敏感场景考虑 **ZK** 或 **DB**。

**深度文档**（SET NX、Redisson 看门狗、RedLock 争议）→

## 4. ZooKeeper 分布式锁（概要）

利用 **临时顺序节点** + **Watcher**：

```
/lock/order/
    lock-0000000001  ← 最小序号获锁
    lock-0000000002  ← watch 前一个
    lock-0000000003
```

- 会话断开 → 临时节点删除 → 自动释放
- 公平、无 TTL 误删问题

详见 [06-ZooKeeper与注册中心](./06-ZooKeeper与注册中心.md#5-分布式锁实现)。

## 5. 选型建议

| 场景 | 推荐 |
|------|------|
| 一般业务互斥、可接受极低概率异常 | Redis + Redisson |
| 定时任务抢跑、幂等 | Redis 或 DB 乐观锁 |
| 强一致、低 QPS（选主、配置） | ZK / etcd |
| 已有 ZK 集群 | Curator `InterProcessMutex` |

**原则**：锁粒度 **尽量小**；持锁时间 **尽量短**；锁内 **不做 RPC**。

## 6. 分布式 ID 需求

| 需求 | 说明 |
|------|------|
| 全局唯一 | 多机不碰撞 |
| 趋势递增 | 利于 B+ 树索引（非严格递增） |
| 高 QPS | 无单点瓶颈 |
| 可读性 | 可选嵌入时间、业务码 |

## 7. UUID

```java
UUID.randomUUID().toString();  // 128 bit，无序
```

| 优点 | 缺点 |
|------|------|
| 本地生成，无依赖 | **无序**，MySQL 插入页分裂 |
| 绝对唯一 | 36 字符长 |

适合 **日志 traceId**；不适合 **主键**（除非 UUID v7 时间有序）。

---

## 8. 雪花算法（Snowflake）

```
0 | 41 bit 时间戳 | 10 bit 机器ID | 12 bit 序列
```

| 优点 | 缺点 |
|------|------|
| 本地生成，QPS 高（4096/ms/机器） | **时钟回拨** 须处理 |
| 趋势递增 | 机器 ID 须分配（ZK/配置） |

**时钟回拨策略**：等待、借用未来序列、告警拒绝。

**实现**：美团 Leaf、百度 uid-generator、自定义 `SnowflakeIdWorker`。

---

## 9. 号段模式

```
DB 表：biz_tag, max_id, step
每次取 [max_id, max_id+step) 缓存本地，用完再取
```

| 优点 | 缺点 |
|------|------|
| DB 压力小（批量） | 号段浪费（重启丢段） |
| ID 纯数字递增 | 依赖 DB 高可用 |

**Leaf 号段 + Snowflake 双模式** 是工业界常见组合。

---

## 10. Redis INCR

```bash
INCR global:order:id
```

简单、有序；Redis 单点/集群高可用须保障；适合 **非核心** 或配合 **分段 key**。

---

## 11. 美团 Leaf / 百度 UidGenerator（了解）

| 方案 | 特点 |
|------|------|
| Leaf-segment | DB 号段，双 buffer 平滑切换 |
| Leaf-snowflake | ZK 分配 workerId |
| UidGenerator | RingBuffer 缓存 Snowflake |

7 年工程师：**能讲 Snowflake + 号段原理**；是否自研看公司基础设施。

---

## 12. 面试题精选

**Q：Redis 锁过期但业务未完成？**  
A：Redisson 看门狗续期；或合理 TTL + 业务可重入设计；或 ZK 会话锁。

**Q：Snowflake 时钟回拨怎么办？**  
A：检测 lastTimestamp > now 则抛异常/等待/借用序列；NTP 同步监控。

**Q：为什么不用 UUID 做订单号？**  
A：无序导致 DB 索引性能差；可读性差；无业务语义（可定制前缀+Snowflake）。
