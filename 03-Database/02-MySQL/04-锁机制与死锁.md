## 一、InnoDB 锁层次总览

```
                    ┌─────────────┐
                    │  Global Lock │  FLUSH TABLES WITH READ LOCK
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │  Table Lock  │  LOCK TABLES（Server 层）
                    └──────┬──────┘
                           │
              ┌────────────┼────────────┐
              │            │            │
         ┌────▼────┐  ┌────▼────┐  ┌────▼────┐
         │  MDL锁   │  │ Intention│  │  Row Lock│
         │ 元数据   │  │ 表级意向  │  │ 记录/间隙 │
         └─────────┘  └─────────┘  └─────────┘
```

| 锁类型 | 粒度 | 典型语句 | 说明 |
|--------|------|----------|------|
| **全局锁** | 整实例 | `FLUSH TABLES WITH READ LOCK` | 备份用；8.0 推荐 `mysqldump --single-transaction` |
| **表锁** | 整张表 | `LOCK TABLES t READ/WRITE` | 性能差，InnoDB 很少用 |
| **行锁** | 索引记录 | `FOR UPDATE`、`UPDATE` | InnoDB 默认；**必须走索引**否则退化为表锁 |
| **MDL** | 表元数据 | 任意 DML/DDL | 保护表结构；DDL 与 DML 互斥 |
| **意向锁** | 表级 | 加行锁前自动 | IS/IX，与行 S/X 配合 |

## 二、行锁三件套：Record / Gap / Next-Key

InnoDB 行锁**加在索引上**（聚簇或二级），不是加在「行数据」抽象对象上。

### 2.1 Record Lock（记录锁）

锁住**索引上已存在**的一条记录。

```sql
-- 表 t: id(PK), 行 id=10, id=20
START TRANSACTION;
SELECT * FROM t WHERE id = 10 FOR UPDATE;  -- 仅锁 id=10 这条索引记录
```

| 特点 | 说明 |
|------|------|
| 粒度 | 单条 index record |
| 冲突 | 与其他事务 X/S 锁同记录互斥 |
| 场景 | 等值查询命中唯一索引/主键 |

### 2.2 Gap Lock（间隙锁）

锁住**两个索引记录之间的间隙**，**不含**记录本身。防止其他事务在间隙 **INSERT**（防幻读）。

```
索引 id:  ... [5] ----gap---- [10] ----gap---- [15] ...
              │                 │
         锁 (7,10) 间隙      锁 (10,15) 间隙
```

```sql
START TRANSACTION;
SELECT * FROM t WHERE id > 7 AND id < 10 FOR UPDATE;
-- 若只有 id=5 和 id=10，可能锁 (5,10) 间隙，阻止 INSERT id=8
```

| 特点 | 说明 |
|------|------|
| 仅 RR | RC 下通常无间隙锁（例外：外键、唯一键检查） |
| 不互斥 | **间隙锁之间不冲突**（不同 trx 可同时持同一 gap S 锁） |
| 与 INSERT | 阻塞在间隙内的 INSERT（与 Insert Intention 冲突） |

### 2.3 Next-Key Lock（临键锁）

**Record Lock + 左开右闭 Gap Lock**，锁住记录及其前面的间隙。InnoDB 默认行锁算法。

```
Next-Key on id=10  →  锁区间 (5, 10]  （假设前一记录 id=5）
```

```sql
-- 会话 A
START TRANSACTION;
SELECT * FROM t WHERE id >= 10 AND id < 20 FOR UPDATE;
-- 可能对 10、15 各加 Next-Key，并锁相应间隙
```

**优化**：若 `WHERE id=10` 且 **唯一索引等值命中**，InnoDB 会 **退化为 Record Lock**（无 gap），减少锁范围。

### 2.4 三种锁对照表

| 锁 | 锁定对象 | 防止操作 | RR 下 |
|----|----------|----------|-------|
| Record | 已存在记录 | UPDATE/DELETE 同记录 | ✓ |
| Gap | 记录间空隙 | 间隙 INSERT | ✓ |
| Next-Key | 记录+前间隙 | 幻读（当前读） | ✓ 默认 |

## 三、Insert Intention Lock（插入意向锁）

事务 INSERT 前在**间隙**上加的**意向锁**，表示「我打算在这个间隙插入」。

| 规则 | 说明 |
|------|------|
| 类型 | 一种特殊的 Gap 锁（INSERT INTENTION） |
| 冲突 | 与**其他** Insert Intention 不互斥；与 **Gap Lock（FOR UPDATE 产生）** 互斥 |
| 场景 | T1 锁 (10,20) gap → T2 INSERT id=15 等待 |

```sql
-- 会话 A
START TRANSACTION;
SELECT * FROM t WHERE id = 10 FOR UPDATE;  -- Next-Key on 10

-- 会话 B
INSERT INTO t(id) VALUES(10);  -- 主键冲突，等 A 释放
-- 或 INSERT id=12 若 gap 被锁则等待
```

**生产启示**：范围 `FOR UPDATE` + 高并发 INSERT → 大量锁等待；可改 RC、缩小锁范围、或乐观锁。

---

## 四、意向锁（Intention Lock）

表级锁，表示事务即将/正在对表中哪些行加 S/X 锁。

| 意向锁 | 含义 | 与表锁关系 |
|--------|------|------------|
| IS | 意向共享 | 与表 X 互斥 |
| IX | 意向排他 | 与表 S、表 X 互斥 |

**作用**：加表锁时快速判断是否与行锁冲突，无需扫描全表。

---

## 五、MDL 元数据锁（Metadata Lock）

Server 层锁，**与存储引擎无关**，保护表结构定义。

| 操作 | MDL 类型 | 阻塞关系 |
|------|----------|----------|
| SELECT | SHARED_READ | 与 SHARED_UPGRADABLE 兼容 |
| INSERT/UPDATE/DELETE | SHARED_WRITE | 与 UPGRADABLE 兼容 |
| ALTER TABLE | SHARED_UPGRADABLE → EXCLUSIVE | 阻塞/被阻塞 DML |

### 5.1 经典线上故障：DDL 堵死全站

```
T1: 大查询 SELECT（持 MDL SR）
T2: ALTER TABLE ADD COLUMN（要 MDL X，等待 T1）
T3: 新 INSERT（要 MDL SW，等待 T2 的 UPGRADABLE 队列）
→ 后续所有访问该表的会话排队 → 连接池耗尽
```

**排查**：

```sql
SELECT * FROM performance_schema.metadata_locks;
SELECT OBJECT_NAME, LOCK_TYPE, LOCK_STATUS, OWNER_THREAD_ID
FROM performance_schema.metadata_locks
WHERE OBJECT_SCHEMA = 'your_db';

-- 找阻塞链
SELECT * FROM sys.schema_table_lock_waits;  -- 需 sys 库
```

**治理**：`pt-online-schema-change`、`gh-ost`；低峰 DDL；设置 `lock_wait_timeout`；监控 MDL 等待。

## 六、SELECT ... FOR UPDATE vs LOCK IN SHARE MODE

| 语句 | 锁类型 | 别名 | 典型用途 |
|------|--------|------|----------|
| `SELECT ... FOR UPDATE` | 排他锁 X | 悲观写锁 | 扣库存、改状态 |
| `SELECT ... LOCK IN SHARE MODE` | 共享锁 S | 悲观读锁 | 防止他人修改，允许多个 S |

```sql
START TRANSACTION;
-- 排他：其他 FOR UPDATE / UPDATE / DELETE 阻塞
SELECT * FROM account WHERE id = 1 FOR UPDATE;

-- 共享：其他 FOR UPDATE 阻塞；其他 LOCK IN SHARE MODE 允许
SELECT * FROM account WHERE id = 1 LOCK IN SHARE MODE;
COMMIT;
```

### 6.1 锁兼容矩阵（行级 S/X）

| 已持有 \ 请求 | S | X |
|---------------|---|---|
| **S** | ✓ | ✗ |
| **X** | ✗ | ✗ |

Gap / Next-Key 在 RR 下额外规则见 2.2。

### 6.2 NOWAIT 与 SKIP LOCKED（8.0+）

```sql
SELECT * FROM job WHERE status = 'PENDING' LIMIT 1
FOR UPDATE SKIP LOCKED;   -- 跳过已锁行，抢单队列

SELECT * FROM job WHERE id = 1 FOR UPDATE NOWAIT;  -- 立即报错不等待
```

**生产**：任务队列消费、秒杀分片抢单。

### 6.3 无索引则锁全表

```sql
-- name 无索引
SELECT * FROM user WHERE name = 'alice' FOR UPDATE;
-- 可能对聚簇索引所有记录加 Next-Key → 等价表锁
```

**必记**：`FOR UPDATE` 的 WHERE 必须能走索引，且尽量唯一等值。

## 七、死锁（Deadlock）

### 7.1 四个必要条件

| 条件 | InnoDB 场景 |
|------|-------------|
| 互斥 | 行 X 锁互斥 |
| 持有并等待 | T1 持 id=1 等 id=2 |
| 不可剥夺 | 锁只能事务释放 |
| 环路等待 | T1→T2→T1 |

### 7.2 InnoDB 死锁检测与处理

- **自动检测**：锁等待图有环 → 选 **undo 代价小** 的事务 **回滚**。
- 另一事务继续；被回滚方收到 `1213 Deadlock found`。
- `innodb_deadlock_detect=ON`（默认）；OFF 则靠 `innodb_lock_wait_timeout` 超时。

### 7.3 SHOW ENGINE INNODB STATUS 解读

```sql
SHOW ENGINE INNODB STATUS\G
```

关注 **LATEST DETECTED DEADLOCK** 段：

```
------------------------
LATEST DETECTED DEADLOCK
------------------------
*** (1) TRANSACTION:
TRANSACTION 4217, ACTIVE 2 sec starting index read
mysql tables in use 1, locked 1
LOCK WAIT 2 lock struct(s), heap size 1136, 1 row lock(s)
MySQL thread id 10, OS thread handle 140..., query id 100 ... updating
UPDATE t SET k = k + 1 WHERE id = 2
*** (1) WAITING FOR THIS LOCK TO BE GRANTED:
RECORD LOCKS space id 58 page no 3 n bits 72 index PRIMARY of table `test`.`t`
 trx id 4217 lock_mode X locks rec but not gap waiting
Record lock, heap no 3 PHYSICAL RECORD: n_fields 3 ...

*** (2) TRANSACTION:
...
UPDATE t SET k = k + 1 WHERE id = 1
*** (2) HOLDS THE LOCK(S):
RECORD LOCKS ... lock_mode X locks rec but not gap
*** (2) WAITING FOR THIS LOCK TO BE GRANTED:
RECORD LOCKS ... id = 2

*** WE ROLL BACK TRANSACTION (1)
```

**阅读顺序**：两个事务各自持有什么锁、等什么锁 → 谁被回滚。

### 7.4 8.0 performance_schema 死锁日志

```sql
-- 开启
SET GLOBAL innodb_print_all_deadlocks = ON;

SELECT * FROM performance_schema.data_locks;
SELECT * FROM performance_schema.data_lock_waits;
```

### 7.5 典型死锁场景

**场景 A：相反顺序更新**

```sql
-- T1                    -- T2
UPDATE t SET ... id=1;   UPDATE t SET ... id=2;
UPDATE t SET ... id=2;   UPDATE t SET ... id=1;  -- 死锁
```

**场景 B：间隙锁 + 插入**

```sql
-- T1: SELECT * FROM t WHERE id=5 FOR UPDATE;  -- Next-Key
-- T2: SELECT * FROM t WHERE id=5 FOR UPDATE;  -- 等待
-- T1: INSERT id=8;  -- 等待 T2 的 gap（历史版本可能死锁，依实现）
```

**场景 C：二级索引 + 主键顺序**

```sql
-- 两事务通过不同二级索引更新，最终以不同顺序锁 PK → 死锁
-- 常见于没有统一主键访问顺序的并发 UPDATE
```

### 7.6 如何避免死锁

| 策略 | 说明 |
|------|------|
| **固定加锁顺序** | 所有业务按 id 升序 UPDATE |
| **缩短事务** | 减少持锁时间 |
| **降低隔离级别** | RC 减少 gap lock（评估业务） |
| **乐观锁** | `UPDATE ... WHERE id=? AND version=?` 无显式行锁等待 |
| **重试** | 捕获 1213 有限次数重试 |
| **拆分热点行** | 单行库存改分桶 `stock_0`~`stock_9` |
| **SKIP LOCKED** | 队列场景避免互等 |

**无法完全避免**：InnoDB 选择牺牲一方，应用需 **幂等 + 重试**。

## 八、乐观锁 vs 悲观锁（业务层）

| 维度 | 悲观锁 | 乐观锁 |
|------|--------|--------|
| 实现 | `SELECT FOR UPDATE` + UPDATE | version / CAS UPDATE |
| 冲突高 | 适合 | 大量失败重试 |
| 冲突低 | 锁开销浪费 | 适合 |
| 死锁 | 可能 | 基本无 |
| 一致性 | 强 | 依赖版本校验 |

### 8.1 悲观锁示例（Java + MySQL）

```sql
START TRANSACTION;
SELECT stock FROM product WHERE id = 100 FOR UPDATE;
-- 应用判断 stock > 0
UPDATE product SET stock = stock - 1 WHERE id = 100;
COMMIT;
```

### 8.2 乐观锁示例

```sql
-- 不加 FOR UPDATE
UPDATE product SET stock = stock - 1, version = version + 1
WHERE id = 100 AND stock > 0 AND version = 5;
-- affected rows = 0 → 重试或返回失败
```

### 8.3 选型建议

| 场景 | 推荐 |
|------|------|
| 秒杀热点 SKU | 悲观 + 分桶 或 Redis 预扣 |
| 订单状态机 | 乐观 version |
| 账户余额 | 悲观或 DB 约束 + 单行原子 UPDATE |
| 读多写少配置 | 乐观或缓存 |

## 九、锁升级误区

### 9.1 MySQL **没有** SQL Server 式行→页→表自动升级

| 误区 | 事实 |
|------|------|
| 「行锁会自动升级成表锁」 | InnoDB **不会**锁升级 |
| 「锁多了就锁全表」 | 是 **没走索引** 导致对聚簇索引逐条加锁，效果像表锁 |
| 「表锁比行锁快」 | 表锁并发度极差，除备份/迁移外避免 |

### 9.2 类似「全表锁」的情况

```sql
-- 1. 无索引 UPDATE
UPDATE user SET score = 0 WHERE nickname = 'x';  -- 全表扫描 + 逐行 X 锁

-- 2. 锁表语句
LOCK TABLES user WRITE;

-- 3. 意向锁与表级 LOCK TABLES 共存场景
```

### 9.3 与 Oracle / SQL Server 对比（面试）

| 数据库 | 锁升级 |
|--------|--------|
| SQL Server | 行→页→表，有阈值 |
| Oracle | 无升级，行锁 + 表级 TM 锁 |
| **InnoDB** | **无升级**；注意索引退化 |

## 十、生产案例

### 案例 1：库存超卖与锁

**问题**：先 SELECT stock 再 UPDATE，无锁。  
**修复**：`UPDATE stock SET s=s-1 WHERE id=? AND s>0` 或 `FOR UPDATE`。

### 案例 2：死锁日志每日百次

**根因**：转账 A→B 与 B→A 并发，两事务按不同账户顺序加锁。  
**修复**：按 `account_id` 字典序加锁；1213 重试 3 次。

### 案例 3：间隙锁拖慢批量导入

**根因**：报表事务 RR + `SELECT * FROM orders WHERE create_time > ? FOR UPDATE` 未提交。  
**修复**：报表改快照读；导入用 RC session；或从库导入。

### 案例 4：MDL 导致发版故障

**根因**：发版 ALTER 遇慢 SQL。  
**修复**：gh-ost；`ALTER` 前查 `metadata_locks`；kill 长查询。

### 案例 5：SKIP LOCKED 实现延迟队列

```sql
UPDATE async_task SET status = 'RUNNING', worker = ?
WHERE id = (
  SELECT id FROM (
    SELECT id FROM async_task WHERE status = 'PENDING'
    ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED
  ) t
);
```

## 十一、锁监控常用 SQL

```sql
-- 当前锁等待
SELECT r.trx_id waiting_trx, r.trx_mysql_thread_id waiting_pid,
       b.trx_id blocking_trx, b.trx_mysql_thread_id blocking_pid
FROM information_schema.innodb_lock_waits w
JOIN information_schema.innodb_trx b ON b.trx_id = w.blocking_trx_id
JOIN information_schema.innodb_trx r ON r.trx_id = w.requesting_trx_id;

-- 8.0 替代
SELECT * FROM performance_schema.data_lock_waits\G

-- 锁等待超时
SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';  -- 默认 50s
```

## 十二、面试 Q&A（20 题）

### Q1：Record、Gap、Next-Key 区别？

**A**：Record 锁存在记录；Gap 锁记录间空隙防 INSERT；Next-Key = Gap + Record，左开右闭，RR 默认。

### Q2：为什么 RR 要用间隙锁？

**A**：当前读需防幻读；仅 Record 无法阻止间隙 INSERT。

### Q3：两个 Gap Lock 会互斥吗？

**A**：不会。同一间隙可被多 trx 持 Gap（兼容），但 Insert Intention 与 Gap 冲突。

### Q4：FOR UPDATE 一定只锁一行吗？

**A**：不一定。范围扫描锁多 Next-Key；无索引可能锁全表。

### Q5：RC 有没有间隙锁？

**A**：一般 DML 无；外键插入检查、duplicate key 等例外仍有。

### Q6：死锁谁回滚？

**A**：InnoDB 选 undo 量较小的事务回滚；客户端收 1213。

### Q7：如何读死锁日志？

**A**：看 LATEST DETECTED DEADLOCK 两 trx 的 HOLDS / WAITING RECORD LOCKS。

### Q8：MySQL 会锁升级吗？

**A**：InnoDB 不会。全表锁效果来自无索引全表扫描加锁。

### Q9：MDL 和行锁关系？

**A**：独立。SELECT 持 MDL SR 不阻塞行 X；但 ALTER 要 MDL X 会堵 DML。

### Q10：意向锁干什么用？

**A**：表级 IS/IX，快速判断表锁与行锁冲突，无需扫表。

### Q11：FOR UPDATE 和 UPDATE 锁一样吗？

**A**：UPDATE/DELETE 是当前读，对扫描行加 X 锁，语义类似 FOR UPDATE。

### Q12：LOCK IN SHARE MODE 何时用？

**A**：需要稳定读且防他人改，如先读再决策是否更新；实际多用 FOR UPDATE 或 MVCC。

### Q13：innodb_lock_wait_timeout 与死锁？

**A**：超时是等锁太久抛错；死锁是检测环立即回滚一方。不同机制。

### Q14：唯一索引等值 FOR UPDATE 锁范围？

**A**：通常退化为 Record Lock，不加 gap（存在 `-next-key lock` 优化例外需查版本）。

### Q15：如何减少 gap 死锁？

**A**：改 RC、统一访问顺序、避免不必要的范围 FOR UPDATE、乐观锁。

### Q16：全局锁使用场景？

**A**：全库只读备份；InnoDB 热备优先 `--single-transaction` 快照。

### Q17：INSERT 会加什么锁？

**A**：插入意向锁 + 对新记录 Record X；唯一键冲突时可能锁冲突记录。

### Q18：Spring @Transactional 默认隔离级别？

**A**：跟随 DB 默认 RR；可 `@Transactional(isolation=READ_COMMITTED)`。

### Q19：主键 UPDATE 会改变行锁吗？

**A**：若改 PK，相当于删旧插新，锁旧记录+新间隙，易冲突。

### Q20：场景：并发扣同一行库存，选什么？

**A**：`UPDATE ... WHERE id=? AND stock>=1` 原子；或 FOR UPDATE；高并发用分桶+乐观或 Redis。
