# 02 · 索引原理与 B+ 树

> **目标读者**：7 年 Java 后端工程师，需能设计联合索引、读懂 EXPLAIN、解释慢 SQL 根因，并在面试中对比 B+ 树 / Hash / B 树选型。
> **预计阅读**：60 min · **难度**：★★★★

---

## 1. 为什么 InnoDB 用 B+ 树而不是 B 树或 Hash

### 1.1 三种结构对比

```
B 树（每个节点存 key+data）          B+ 树（叶子存 data，非叶只存 key）
        [10|20|30]                         [10|20|30]
       /    |    \                        /    |    \
  [5|8] [15] [25|28]              [5|10] [20] [30|...]
  数据在各层                         数据只在叶子，叶子双向链表 ──► 范围扫描
```

| 结构 | 等值查询 | 范围查询 | 排序 | 磁盘 IO | InnoDB 选择 |
|------|----------|----------|------|---------|-------------|
| Hash | O(1) 平均 | **不支持** | 不支持 | 低 | Memory 引擎 / 自适应哈希 |
| B 树 | O(log n) | 支持但效率一般 | 支持 | 中 | 未采用 |
| B+ 树 | O(log n) | **高效链表扫描** | 天然有序 | **低（高扇出）** | **默认** |

**选 B+ 树的核心原因**：

1. **扇出大**：非叶节点不存行数据，单页 16KB 可存数百指针，树高低（通常 3～4 层），单次查询 IO 少。
2. **范围查询**：叶子双向链表，`BETWEEN`、`ORDER BY`、`GROUP BY` 顺序扫描友好（OLTP + 报表都常见）。
3. **全表扫描**：沿叶子链表顺序读，预读（read-ahead）友好。
4. **聚簇索引**：B+ 树叶子即数据页，主键即物理顺序。

**Hash 在 InnoDB 中**：没有用户可见的 Hash 索引；AHI 是内部优化，不能替代 B+ 树做范围查询。

## 2. 页大小与扇出计算

**默认页大小**：16KB（`innodb_page_size=16384`）。

### 2.1 扇出估算

假设 secondary index 非叶节点：

- 页头、目录等开销约 128B。
- 指针 6B（page no）+ 主键 8B（BIGINT）≈ 14B/entry。
- 可用 ≈ 16384 - 128 ≈ 16256B → **约 1100+ 指针/页**。

```
树高 3 的 B+ 树（扇出 1000 保守估计）：
  根 ──► 1000 个中间页 ──► 1000×1000 = 100 万叶子页 ──► 约 1600 万行（视行宽）
```

**结论**：千万级单表，主键索引通常 **3～4 次 IO** 定位一行（含 Buffer Pool 命中则 0 IO）。

```sql
SHOW VARIABLES LIKE 'innodb_page_size';
-- 16384
```

## 3. 聚簇索引 vs 二级索引

### 3.1 聚簇索引（Clustered Index）

- 表数据**按主键顺序**存放在 B+ 树叶子页。
- **一张 InnoDB 表只有一个聚簇索引**；无显式 PK 时选第一个 UNIQUE NOT NULL，或隐式 row_id。

```
聚簇索引 B+ 树（叶子 = 完整行）
                    [PK=100]
                   /        \
           [PK=50]            [PK=150]
           /     \            /      \
    叶子: row(30) ...   叶子: row(100) row(120) ... ──► 链表
```

### 3.2 二级索引（Secondary Index）

- 叶子存 **(索引列, 主键值)**，不含完整行。
- 查非索引列需 **回表**：二级索引定位 PK → 再查聚簇索引取全行。

```
SELECT name, age FROM user WHERE email = 'a@b.com';

  email 二级索引                    聚簇索引
  找到 email='a@b.com' ──PK=42──►  取完整行 (name, age, ...)
         │
         └── 回表（一次或多次随机 IO）
```

### 3.3 对比表

| 维度 | 聚簇索引 | 二级索引 |
|------|----------|----------|
| 叶子内容 | 完整行 | 索引列 + PK |
| 数量 | 1 个 | 多个 |
| 插入 | 按 PK 顺序，可能页分裂 | 维护独立 B+ 树 |
| 覆盖索引 | 天然覆盖 PK 相关 | 需包含所需列才可避免回表 |

**设计原则**：主键尽量**短、有序、自增**（BIGINT 雪花 / AUTO_INCREMENT），避免 UUID 随机插入导致页分裂。

## 4. 覆盖索引（Covering Index）

索引已包含 SELECT / WHERE / ORDER BY 所需全部列，优化器直接从二级索引返回，**无需回表**。

```sql
-- 索引：KEY idx_user_email_name (email, name)
EXPLAIN SELECT name FROM user WHERE email = 'a@b.com';
-- Extra: Using index  ← 覆盖索引
```

**收益**：减少聚簇索引随机 IO，慢查询变快一个数量级常见。

**Java 场景**：列表页只查 id、title、status，建 `(status, created_at, id, title)` 覆盖常用查询。

## 5. ICP（Index Condition Pushdown，索引下推）

MySQL 5.6+：在 **存储引擎层** 用索引列先过滤，再回表，减少回表次数。

```sql
-- 索引：KEY idx (name, age)
EXPLAIN SELECT * FROM user WHERE name LIKE '张%' AND age = 25;
-- Extra: Using index condition
```

**无 ICP**：引擎只按 `name LIKE '张%'` 扫索引，每行回表后再在 Server 层判 `age=25`。

**有 ICP**：在索引层同时判 `age=25`，不满足则不回表。

**注意**：ICP 是 **Index Condition** Pushdown，与「索引下推」中文常混用；还有 **MRR**（Multi-Range Read）优化回表顺序，Extra 可见 `Using MRR`。

## 6. 最左前缀原则

联合索引 `(a, b, c)` 等价于有序字典：先按 a，再 b，再 c。

### 6.1 能用上索引的情况

```sql
-- 索引 KEY idx_abc (a, b, c)

WHERE a = 1                          -- ✓ 用 a
WHERE a = 1 AND b = 2                -- ✓ 用 a,b
WHERE a = 1 AND b = 2 AND c = 3      -- ✓ 全用
WHERE a = 1 AND c = 3                -- ✓ 用 a；c 仅 ICP 可能帮过滤，不算 range 索引
ORDER BY a, b                        -- ✓ 与 WHERE 组合时常见
```

### 6.2 不能用或部分用

```sql
WHERE b = 2                          -- ✗ 跳过 a
WHERE a = 1 OR b = 2                 -- ✗ 通常走 index_merge 或全表扫
WHERE a > 1 AND b = 2                -- ✓ a range；**b 往往用不上**（a 范围截断）
```

### 6.3 范围截断（高频面试）

```sql
-- idx(status, created_at)
WHERE status = 1 AND created_at > '2024-01-01' AND created_at < '2024-02-01'
-- status 等值 + created_at 范围 → 索引高效

WHERE status > 0 AND created_at = '2024-01-01'
-- status 范围后 created_at 无法走索引有序定位（只能 ICP）
```

**记忆**：遇到**范围条件**，该列及其**右侧列**通常无法用于 B+ 树定位（仍可能 ICP / 覆盖索引）。

## 7. Index Merge（索引合并）

优化器对多个二级索引分别扫描后 **交集/并集**。

```sql
-- KEY idx_a(a), KEY idx_b(b)
EXPLAIN SELECT * FROM t WHERE a = 1 OR b = 2;
-- type: index_merge
-- Extra: Using union(idx_a, idx_b); Using where
```

| 类型 | 场景 |
|------|------|
| intersection | AND 多条件各命中不同索引 |
| union | OR 多条件 |
| sort-union | OR + ORDER BY 优化 |

**生产**：index_merge 不一定是好事，常说明缺合适联合索引；高并发下多索引扫描 CPU 高。

## 8. 索引失效场景（优化器不走预期索引）

### 8.1 对列使用函数或运算

```sql
WHERE YEAR(create_time) = 2024        -- ✗ 应用 WHERE create_time >= '2024-01-01'
WHERE id + 1 = 100                     -- ✗ 改为 id = 99
```

### 8.2 隐式类型转换

```sql
-- phone 是 VARCHAR，索引 idx_phone
WHERE phone = 13800138000              -- ✗ 数字转字符串，可能全表扫
WHERE phone = '13800138000'            -- ✓
```

**规则**：字符串列与数字比较，列被 cast，索引失效。

### 8.3 LIKE 左模糊

```sql
WHERE name LIKE '%张%'                 -- ✗ 无法利用 B+ 树有序
WHERE name LIKE '张%'                  -- ✓ range
```

### 8.4 OR、NOT EQUAL、IS NOT NULL

```sql
WHERE status != 1                      -- 优化器可能判全表扫更优
WHERE a = 1 OR b = 2                   -- 见 index_merge 或全表
```

### 8.5 不等于与选择性

高选择性列 `=` 走索引；`!=` 或 `NOT IN` 返回行数过半时常选全表扫描（成本模型判断）。

### 8.6 联合索引列顺序错误

见 §6、§10。

## 9. 联合索引设计原则

### 9.1 等值在前，范围在后

```sql
-- 查询：WHERE tenant_id = ? AND user_id = ? AND created_at BETWEEN ? AND ?
-- 推荐：KEY idx (tenant_id, user_id, created_at)
-- 不推荐：(created_at, tenant_id) — 范围列打头截断
```

### 9.2 列顺序：区分度 + 查询模式

1. **WHERE 最常用且等值**的列放左。
2. **区分度高**的列优先（减少扫描行数）—— 但需结合最左前缀，不能单独把高区分度列放第二位而第一位 rarely 过滤。
3. **ORDER BY / GROUP BY** 列尽量纳入索引且顺序一致，避免 filesort。

```sql
-- 区分度：tenant_id(100) < user_id(100万) < gender(2)
-- 查询总是带 tenant_id=?
-- 索引 (tenant_id, user_id, ...) 而非 (gender, tenant_id)
```

### 9.3 避免冗余索引

```sql
KEY idx_a_b (a, b)
KEY idx_a (a)        -- 冗余，被 idx_a_b 最左覆盖
```

MySQL 8.0 可辅助检测：

```sql
SELECT * FROM sys.schema_redundant_indexes;
```

## 10. 选择性（Selectivity）与 Cardinality

**选择性** = 不重复值数 / 总行数，越接近 1 越好（如 PK）。

```sql
SHOW INDEX FROM user;
-- Cardinality 列：估算值，非精确，ANALYZE TABLE 后更新
```

| 列 |  distinct | 选择性 | 是否单独索引 |
|----|-----------|--------|--------------|
| gender | 2 | 低 | 通常不单独建 |
| mobile | 500万/500万 | 高 | 适合 |
| status | 5 | 低 | 放联合索引左侧需配合高过滤 |

**坑**：`Cardinality` 不更新导致优化器选错计划 → 定期 `ANALYZE TABLE` 或 InnoDB stats 持久化。

## 11. 索引维护成本与写放大

每次 INSERT/UPDATE/DELETE 可能：

1. 修改聚簇索引页（PK 变则移动行）。
2. 修改**每个**受影响二级索引 B+ 树。
3. 产生 Undo/Redo、Change Buffer merge。

```
写放大 ≈ 1（聚簇） + N（二级索引数） + 页分裂额外 IO
```

**真实场景**：表上 8 个二级索引，批量导入 QPS 只有 2 索引表的 1/4；治理方式：删冗余索引、批量写时暂禁非必要索引、用 LOAD DATA。

**页分裂 / 合并**：随机 PK（UUID）插入中间叶子 → 分裂；自增 ID 追加右侧 → 分裂少。

## 12. Online DDL 简述

MySQL 5.6+ InnoDB 支持在线加索引，减少锁表。

```sql
ALTER TABLE user ADD INDEX idx_x(a), ALGORITHM=INPLACE, LOCK=NONE;
-- 大表仍可能 IO 高，需在低峰执行
```

| 操作 | 典型算法 | 锁 |
|------|----------|-----|
| ADD INDEX | INPLACE | NONE / SHARED |
| OPTIMIZE | COPY | 可能阻塞 |
| 改列类型 | 常 COPY | 谨慎 |

**8.0 instant DDL**：加列末尾等操作可 instant，读 [`官方文档`](https://dev.mysql.com/doc/refman/8.0/en/innodb-online-ddl-operations.html) 确认。

## 13. EXPLAIN 精读与 12 条 SQL 示例

### 13.1 EXPLAIN 关键列

| 列 | 含义 |
|----|------|
| type | system > const > eq_ref > ref > range > index > ALL |
| key | 实际使用索引 |
| rows | 估算扫描行数 |
| Extra | Using index / Using where / Using filesort / Using temporary |

---

**示例 1：主键等值 — const**

```sql
EXPLAIN SELECT * FROM user WHERE id = 1;
-- type: const, key: PRIMARY, rows: 1
```

**示例 2：二级索引 + 回表 — ref**

```sql
EXPLAIN SELECT * FROM user WHERE email = 'a@b.com';
-- type: ref, key: idx_email, rows: 1, Extra: NULL 或 Using where
```

**示例 3：覆盖索引**

```sql
EXPLAIN SELECT id, email FROM user WHERE email = 'a@b.com';
-- Extra: Using index
```

**示例 4：范围 — range**

```sql
EXPLAIN SELECT * FROM user WHERE id BETWEEN 100 AND 200;
-- type: range, key: PRIMARY
```

**示例 5：最左前缀 — ref**

```sql
-- KEY(tenant_id, status, created_at)
EXPLAIN SELECT * FROM order_t WHERE tenant_id = 1 AND status = 2;
-- key: 联合索引, ref
```

**示例 6：范围截断**

```sql
EXPLAIN SELECT * FROM order_t
WHERE tenant_id = 1 AND status > 0 AND created_at = '2024-06-01';
-- key_len 可能只用到 tenant_id+status；created_at 靠 ICP/where
```

**示例 7：LIKE 左模糊 — ALL**

```sql
EXPLAIN SELECT * FROM user WHERE name LIKE '%明%';
-- type: ALL 或 index（全索引扫描），rows 很大
```

**示例 8：隐式转换**

```sql
EXPLAIN SELECT * FROM user WHERE phone = 13800138000;
-- type: ALL, key: NULL（phone 为 varchar 时）
```

**示例 9：函数导致失效**

```sql
EXPLAIN SELECT * FROM user WHERE DATE(create_time) = '2024-01-01';
-- type: ALL
-- 改写：create_time >= '2024-01-01' AND create_time < '2024-01-02'
```

**示例 10：ICP**

```sql
EXPLAIN SELECT * FROM user WHERE name LIKE '张%' AND age = 30;
-- Extra: Using index condition
```

**示例 11：filesort**

```sql
EXPLAIN SELECT * FROM user WHERE status = 1 ORDER BY created_at DESC;
-- 无 (status, created_at) 时 Extra: Using filesort
-- 建索引 KEY idx(status, created_at) 可消除
```

**示例 12：index_merge**

```sql
EXPLAIN SELECT * FROM t WHERE a = 1 OR b = 2;
-- type: index_merge, Extra: Using union(...)
```

## 14. 慢查询典型模式

| 模式 | 特征 | 治理 |
|------|------|------|
| 深分页 | `LIMIT 100000, 20` | 延迟关联 / 游标 / 覆盖索引 |
| 隐式转换 | 类型不匹配 | 统一类型、改 SQL |
| 索引列运算 | 函数包裹列 | 改写范围条件 |
| 回表过多 | 大 range + `SELECT *` | 覆盖索引、缩小列 |
| 冗余 OR | 多列 OR | UNION ALL 改写或联合索引 |
| 统计信息过期 | 好索引不用 | ANALYZE TABLE |
| 选错索引 | 多索引竞争 | optimizer hint / 删冗余索引 |
| 大 IN 列表 | `IN (数千 id)` | 临时表 JOIN、分批 |

**深分页改写**：

```sql
-- 慢
SELECT * FROM article ORDER BY id LIMIT 500000, 20;

-- 快：延迟关联
SELECT a.* FROM article a
INNER JOIN (SELECT id FROM article ORDER BY id LIMIT 500000, 20) t ON a.id = t.id;
```

## 15. 常见坑汇总

1. **以为建了联合索引就能用** —— 忽略最左前缀与范围截断。
2. **SELECT *** —— 错失覆盖索引，回表翻倍。
3. **UUID 主键** —— 页分裂、Buffer Pool 污染、索引体积大。
4. **低选择性列单独索引** —— 优化器不用，浪费写放大。
5. **只看 rows 不看 type** —— ref 扫 1 行 vs index 扫全索引长度不同。
6. **生产直接 ALTER 大表** —— 未评估 Online DDL IO 与 replication lag。

## 16. 面试 Q&A（18 题）

### Q1：B+ 树和 B 树区别？

**答**：B+ 树非叶只存 key，数据全在叶子且叶子链表相连；扇出更大、树更矮、范围查询更高效。InnoDB 叶子存整行（聚簇）或 PK（二级）。

### Q2：为什么主键推荐自增？

**答**：插入集中在 B+ 树右侧，减少页分裂与碎片；随机 PK 导致中间插入分裂频繁。

### Q3：什么是回表？如何避免？

**答**：二级索引查非索引列需再查聚簇索引。用覆盖索引（Extra: Using index）避免。

### Q4：覆盖索引是否包括主键？

**答**：二级索引叶子已含 PK，但 SELECT 列若不在索引定义中仍需回表取其他列。

### Q5：最左前缀是什么？

**答**：联合索引 (a,b,c) 匹配从 a 开始的连续前缀；跳过 a 则无法用该索引有序定位。

### Q6：a=1 AND b>2 AND c=3 能用 c 吗？

**答**：a 等值、b 范围，c **通常不能**用于 B+ 树定位；可能 ICP 在引擎层过滤 c。

### Q7：ICP 是什么？

**答**：Index Condition Pushdown，把 WHERE 中索引列条件下推到 InnoDB 层，在回表前过滤，减少回表。

### Q8：Hash 索引为什么 InnoDB 不支持用户创建？

**答**：Hash 不支持范围与排序；InnoDB 范围查询多，B+ 树通用。AHI 仅内部等值加速。

### Q9：index_merge 好吗？

**答**：能完成查询但不总是最优；常提示缺联合索引，OR 条件尤其明显。

### Q10：LIKE 'abc%' 能用索引吗？

**答**：能，range 扫描。`%abc` 不能。

### Q11：OR 为什么难走索引？

**答**：单列索引难以合并为一个有序扫描；可能 index_merge 或全表。改写 UNION 或联合索引。

### Q12：Cardinality 是什么？

**答**：索引列不重复值估算，供优化器选索引；非精确，需 ANALYZE 更新。

### Q13：一个表几个聚簇索引？

**答**：一个。二级索引多个，每个独立 B+ 树。

### Q14：写多读少还要很多索引吗？

**答**：每个索引增加写放大；应精简，只保留查询必需索引。

### Q15：EXPLAIN type=index 比 ALL 好吗？

**答**：index 是全索引扫描，比 ALL 扫表好，但仍可能很慢；目标 ref/range/const。

### Q16：联合索引 (a,b) 与 (b,a) 一样吗？

**答**：完全不同。查询 WHERE a=? 只能用 (a,b)，不能用 (b,a) 的最左 a。

### Q17：什么是索引下推和 MRR？

**答**：ICP 在索引层过滤；MRR 把回表 PK 排序后批量读聚簇，减随机 IO。Extra 分别显示。

### Q18：如何设计订单表索引？

**答**：按查询模板：`(tenant_id, user_id, created_at)` 等值+排序；列表覆盖 `(tenant_id, status, created_at, id)`；避免 status 单独低选择性索引；大表加索引用 Online DDL 低峰执行。

## 17. 生产案例

### 案例 A：Java 接口 P99 飙高

- **SQL**：`WHERE user_id=? ORDER BY create_time DESC LIMIT 20`
- **问题**：仅有 `idx_user_id`，Extra: Using filesort
- **修复**：`KEY idx_user_ct (user_id, create_time DESC)`，type ref，消除 filesort

### 案例 B：报表 COUNT 全表扫

- **SQL**：`WHERE DATE(dt)=?`  
- **修复**：`dt >= ? AND dt < ? + INTERVAL 1 DAY`，走 `idx_dt`

### 案例 C：分库分表后索引

- Sharding key 必须在查询条件中；二级索引设计需含 sharding key 前缀，否则跨片扫。
