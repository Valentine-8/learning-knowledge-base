## 一、AI 应用的分层架构

把 LLM 嵌入 Java 系统，推荐分层（和你熟悉的 Controller-Service-DAO 类比）：

```
┌─────────────────────────────────────────────┐
│  接入层    API/SSE、鉴权、限流、配额          │ ← [02][09]
├─────────────────────────────────────────────┤
│  编排层    Prompt管理、RAG、Agent、工作流      │ ← [01][05][06]
├─────────────────────────────────────────────┤
│  能力层    ChatClient抽象、多模型路由、工具/MCP │ ← [03][07]
├─────────────────────────────────────────────┤
│  模型层    云API / 本地模型(Ollama/vLLM)       │ ← [10]
├─────────────────────────────────────────────┤
│  数据层    向量库、缓存、会话、知识库           │ ← [04]
├─────────────────────────────────────────────┤
│  治理层    可观测、评估、成本、安全审计         │ ← [08][09]
└─────────────────────────────────────────────┘
```

**关键设计原则**：模型层要**可插拔**——业务代码依赖抽象（ChatClient），不绑定具体模型/厂商，这样能随时切换、降级、多路由。

## 二、技术选型决策树（核心能力）

面对一个 AI 需求，按这个顺序问：

```
需求来了
│
├─ 能不能不用 LLM？(规则/传统ML更简单？) ──是→ 别用 LLM
│
├─ 只是改行为/格式？ ──是→ Prompt 工程 [01]
│
├─ 需要私有/实时知识？ ──是→ RAG [05]
│
├─ 需要执行操作/多步任务？ ──是→ Function Calling/Agent [06]
│
├─ 要固化风格/领域能力且有数据？ ──是→ 微调 [11]
│
├─ 数据不能出内网？ ──是→ 本地部署 [10]
│
└─ 组合以上 + 治理(可观测/安全/成本)
```

**模型选型维度**：能力(benchmark) × 成本 × 延迟 × 上下文长度 × 中文 × 合规 × 可用性。**不追新、按场景和数据选**（呼应 [技能清单](../../01-Java/7年Java工程师技能清单.md) 技术选型）。

## 三、成本工程（AI 系统特有，面试高频）

LLM 是**按 token 付费的变动成本**，用不好账单会失控。要像做容量规划一样做成本规划。

### 3.1 成本构成
```
月成本 ≈ 请求数 × (平均输入token × 输入单价 + 平均输出token × 输出单价)
       + 向量库/存储 + (本地部署的)GPU + embedding 调用
```

### 3.2 降本手段（按性价比排序）

| 手段 | 说明 | 效果 |
|------|------|------|
| **缓存** | 相同/相似问题命中缓存不调模型 | ★★★ 最有效 |
| **模型分级路由** | 简单任务用便宜/小模型，难任务才用贵模型 | ★★★ |
| **控制上下文** | RAG 只给必要片段、多轮做窗口/摘要 | ★★ |
| **prompt 压缩** | 精简系统提示、few-shot 按需 | ★★ |
| **输出限制** | max_tokens 卡上限 | ★ |
| **批处理** | embedding/离线任务批量 | ★ |
| **本地模型** | 高频场景自建（要算 GPU） | 视规模 |

### 3.3 缓存的两种

```java
// 1. 精确缓存：同样的输入直接返回（Redis）
String cacheKey = hash(model + systemPrompt + userInput);
String cached = redis.get(cacheKey);
if (cached != null) return cached;   // 命中，0 成本

// 2. 语义缓存：相似问题命中（用 embedding，见 04）
//    "怎么退款" 和 "如何申请退款" 命中同一答案
List<Document> similar = vectorStore.similaritySearch(
    SearchRequest.query(question).withTopK(1).withSimilarityThreshold(0.95));
if (!similar.isEmpty()) return getCachedAnswer(similar.get(0));
```

### 3.4 配额与预算熔断
```java
// 按用户/租户/全局设 token 日预算，超了熔断或降级
if (costTracker.todayCost(tenantId).compareTo(dailyBudget) > 0) {
    return degradeResponse();   // 降级：用小模型/返回缓存/排队
}
```

## 四、可靠性设计：降级、限流、熔断

你在分布式系统学的这些（[技能清单](../../01-Java/7年Java工程师技能清单.md) 分布式章）**直接迁移**到 AI：

| 措施 | AI 场景应用 |
|------|-------------|
| 限流 | 保护模型服务和账户，客户端并发/QPS 限制 |
| 熔断 | 模型服务连续失败/超时则熔断，走降级 |
| 降级 | 主模型不可用→备用模型→缓存→兜底文案 |
| 超时 | LLM 慢，设合理超时 + 流式首 token 超时 |
| 重试 | 429/5xx 指数退避（[02](./02-LLM-API集成实战(Java).md)）|
| 多路由 | 多厂商/多模型，一个挂了切另一个 |
| 异步/队列 | 长任务（批量总结）异步化，别阻塞 |

```java
// 降级链示例
@CircuitBreaker(name = "llm", fallbackMethod = "fallback")
@RateLimiter(name = "llm")
public String chat(String q) { return primaryModel.chat(q); }

public String fallback(String q, Throwable t) {
    try { return backupModel.chat(q); }          // 备用模型
    catch (Exception e) { return semanticCache.getOrDefault(q, "系统繁忙，请稍后再试"); }
}
```

## 六、常见坑

| 坑 | 现象 | 解法 |
|----|------|------|
| 业务代码绑死某厂商 | 想换模型改一堆代码 | 依赖抽象层(ChatClient)，配置化 |
| 无缓存 | 重复问题重复烧钱 | 精确+语义缓存 |
| 一律用最贵模型 | 成本爆炸 | 分级路由 |
| 无预算熔断 | 被刷/bug 导致天价账单 | 配额+熔断+告警 |
| 没降级 | 模型挂全站崩 | 多路由+降级链+兜底 |
| 同步长任务 | 线程阻塞/超时 | 异步+队列+虚拟线程 |
| 上线才想安全/成本 | 返工/事故 | 用 checklist 前置 |

## 七、面试考点（架构级，含金量高）

- **Q：给你一个"智能客服"需求，怎么做技术选型？**
  A：按决策树——先看能否用规则；需要公司知识→RAG；要查订单/退款操作→Agent+工具(写操作人审)；模型按成本/中文/合规选，抽象层可切换；加缓存/路由控成本；加可观测/安全/降级；建评估集。分层讲清。
- **Q：AI 应用怎么控成本？**
  A：缓存(精确+语义)、模型分级路由、控上下文、prompt 压缩、输出限制、配额熔断、成本告警；高频可本地部署。给出成本公式。
- **Q：模型服务挂了怎么办？**
  A：多模型降级链（主→备→缓存→兜底文案）+ 熔断 + 超时 + 限流，业务依赖抽象层不绑厂商。
- **Q：怎么保证换模型/改 prompt 不出事？**
  A：版本化 + 评估集回归 + 灰度/A-B + 可回滚 + 可观测监控质量漂移。
- **Q：AI 系统架构和传统后端最大不同？**
  A：概率输出（需评估而非断言）、按 token 变动成本（需成本工程）、新安全面（prompt 注入）、质量会漂移（需持续评估）——但限流/熔断/降级/缓存等分布式经验可复用。
