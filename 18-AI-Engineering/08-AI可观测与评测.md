# 08 · AI 可观测与评测

> **能力层**：L4 架构者　**难度**：★★★　**预计工时**：10h
> **一句话**：LLM 应用是"概率系统"，不像传统代码非黑即白。没有可观测（看得见每次调用）和评测（量化质量），你就是在黑箱里裸奔。这是 AI 应用能不能上生产的关键。
> **前置**：[02-LLM-API集成实战](./02-LLM-API集成实战(Java).md)、[05-RAG](./05-RAG系统工程化实战.md)。

## 一、为什么 AI 应用必须做可观测和评测

传统后端：输入确定 → 输出确定，单测 assert 相等即可。
LLM 应用：**同样输入可能不同输出**，"对不对"是模糊的。带来三个新问题：

1. **看不见**：一次 RAG 问答内部经过 检索→rerank→prompt→生成 多步，出问题不知道哪一环
2. **测不准**：没法 `assertEquals`，得判断"答案质量好不好"
3. **会漂移**：模型升级、prompt 改动、数据变化都会让效果悄悄退化

对策：**可观测（Observability）** 解决"看得见"，**评测（Evaluation）** 解决"测得准"。

## 二、可观测：Trace 每一次调用

### 2.1 要采集什么

| 维度 | 具体指标 |
|------|----------|
| 输入输出 | prompt 全文、模型回复、检索到的文档 |
| 性能 | 首 token 延迟(TTFT)、总延迟、每步耗时 |
| 成本 | prompt/completion token 数、按模型单价算的费用 |
| 质量 | 用户反馈(赞/踩)、是否触发降级、解析失败率 |
| 链路 | 一次请求内多步（RAG检索、多次工具调用）的父子关系 |

关键概念 **Trace / Span**：一次用户请求 = 一个 Trace，内部每一步（embedding、检索、LLM调用、工具调用）= 一个 Span，形成树状调用链——和你熟悉的 SkyWalking/Jaeger 分布式追踪一模一样，只是内容换成 LLM。

### 2.2 Langfuse（LLM 可观测事实标准）

```yaml
# docker-compose 起 Langfuse（自托管，数据不出内网）
# 官方提供 compose，含 postgres + clickhouse
```

Spring AI 集成（通过 OpenTelemetry 或 Langfuse SDK）：
```java
// 方式1：Spring AI 内置 Micrometer/OTel observation
management:
  tracing:
    sampling:
      probability: 1.0
// LLM 调用自动生成 span，导出到 Langfuse/Jaeger

// 方式2：手动记录（更可控）
LangfuseTrace trace = langfuse.trace("rag-qa").userId(uid);
Span retrieval = trace.span("retrieval").input(question);
// ... 检索 ...
retrieval.output(docs).end();
Span gen = trace.span("generation").input(prompt);
// ... LLM 生成 ...
gen.output(answer).usage(promptTokens, completionTokens).end();
```

Langfuse 界面能看到：每次调用的完整 prompt/输出、token/成本、延迟、调用链树、用户反馈，还能收集数据集做评估。

### 2.3 与现有监控体系整合
你已会 Prometheus + Grafana（见 [技能清单](../../01-Java/7年Java工程师技能清单.md) DevOps 章）。LLM 指标同样可以：
- Micrometer 埋点 → Prometheus：QPS、延迟分布、token 速率、成本、错误率、降级次数
- Grafana 看板：AI 调用总览
- OpenTelemetry：LLM span 接入现有 Jaeger/SkyWalking 链路

**心智**：LLM 可观测 = 分布式追踪 + token/成本维度 + 输入输出留存。你的 APM 经验直接迁移。

## 三、评测：量化"答得好不好"

### 3.1 两种评测时机

| 类型 | 何时 | 用途 |
|------|------|------|
| **离线评估** | 上线前/改动后 | 用固定评估集回归，防止改坏 |
| **在线评估** | 生产实时 | 采样打分、用户反馈、监控质量漂移 |

### 3.2 评测方法

| 方法 | 说明 | 适用 |
|------|------|------|
| 精确匹配/规则 | 输出==标准答案，或正则/包含 | 分类、抽取、有唯一答案 |
| 相似度 | embedding 余弦、BLEU/ROUGE | 翻译、摘要 |
| **LLM-as-Judge** | 用强模型给答案打分 | 开放式问答、RAG（最常用）|
| 人工标注 | 人打分 | 金标准，贵，抽样做 |

### 3.3 LLM-as-Judge 实战

用一个强模型当"裁判"，按标准给答案打分：

```java
String JUDGE_PROMPT = """
你是严格的评审。根据【问题】【参考答案】【模型答案】，从以下维度打分(1-5)：
- 正确性：模型答案是否与参考答案一致、无事实错误
- 忠实度：是否只依据给定资料，无编造
- 完整性：是否回答了问题的所有方面
只输出 JSON：{"correctness":int,"faithfulness":int,"completeness":int,"reason":"..."}

【问题】%s
【参考答案】%s
【模型答案】%s
【检索资料】%s
""";

public JudgeScore judge(EvalCase c, String modelAnswer) {
    return chatClient.prompt()
        .user(JUDGE_PROMPT.formatted(c.question(), c.reference(), modelAnswer, c.context()))
        .options(ChatOptions.builder().temperature(0.0).build())
        .call().entity(JudgeScore.class);
}
```

**注意**：LLM-as-Judge 本身有偏差（偏爱长答案、位置偏好），要：用强模型当裁判、固定评分标准、必要时人工校准、对比多个裁判。

### 3.4 Spring AI 内置 Evaluator

```java
// RelevancyEvaluator：答案与检索内容是否相关（防幻觉）
var evaluator = new RelevancyEvaluator(chatClientBuilder);
EvaluationResponse resp = evaluator.evaluate(
    new EvaluationRequest(question, retrievedDocs, answer));
boolean pass = resp.isPass();
```

### 3.5 回归评估流程（工程化）

```
改了 prompt / 分块 / 换模型
   → 跑评估集(30~50条)
   → 计算指标(准确率/faithfulness/Recall@K)
   → 和上一版对比，涨了才发布
   → 结果存档（可进 CI）
```
这就是 LLM 应用的"单元测试 + 回归测试"。呼应 [05-RAG 评估](./05-RAG系统工程化实战.md)。

## 四、常见坑

| 坑 | 现象 | 解法 |
|----|------|------|
| 不留 prompt/输出 | 出问题无法复现 | 全量或采样留存输入输出（注意脱敏） |
| 只看总延迟 | 不知慢在哪 | 分 span：检索/生成/工具各自计时 |
| 无评估集就改 prompt | 改好一个坏三个 | 建评估集，改动必回归 |
| LLM-as-Judge 全信 | 裁判也会错/有偏 | 强模型+固定标准+人工抽检校准 |
| 留存 PII 违规 | 合规风险 | 日志脱敏、访问控制，见 [09](./09-LLM安全与合规.md) |
| 不监控成本 | 账单爆炸 | token/成本做成 Grafana 告警 |
| 忽略质量漂移 | 模型升级后悄悄变差 | 在线采样评估 + 定期跑离线集 |

## 五、面试考点

- **Q：LLM 应用为什么需要专门的可观测和评测？**
  A：输出非确定、质量模糊、易漂移；需要留存输入输出、追踪多步链路、量化质量，才能定位问题和防退化。
- **Q：Trace/Span 概念，和分布式追踪什么关系？**
  A：一次请求是 Trace，内部每步是 Span，形成调用树；与 Jaeger/SkyWalking 同源，只是内容是 LLM 调用+token+成本。
- **Q：怎么评估一个 RAG 系统？**
  A：离线评估集 + 检索指标(Recall@K/MRR)+ 生成指标(faithfulness/relevance)，方法用 LLM-as-Judge/规则/人工，改动做回归。
- **Q：LLM-as-Judge 是什么，有什么局限？**
  A：用强模型给答案打分。局限：有位置/长度偏好、裁判本身会错，需固定标准+人工校准。
- **Q：AI 应用怎么防止上线后质量退化？**
  A：在线采样评估 + 用户反馈 + 定期跑离线评估集 + 模型/prompt 变更走回归 + 成本质量告警。
