## 2. 手写 Redis 锁：SET NX EX

### 2.1 基本命令

```bash
# 加锁：key 不存在则设置，带过期
redis-cli SET order:lock:10001 "uuid-abc-123" NX EX 30
# OK  → 加锁成功
# (nil) → 已被占用

# 错误示范：SETNX + EXPIRE 分两步（非原子，宕机死锁）
```

| 参数 | 作用 |
|------|------|
| NX | Not eXists，仅不存在时设置 |
| EX 30 | 30 秒过期，防客户端 crash 死锁 |
| value | **唯一标识**（UUID），防误删他人锁 |

### 2.2 释放锁：Lua 脚本

删之前必须校验 value，且 **GET + DEL 必须原子**：

```lua
-- unlock.lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

```bash
redis-cli EVAL "if redis.call('GET',KEYS[1])==ARGV[1] then return redis.call('DEL',KEYS[1]) else return 0 end" 1 order:lock:10001 uuid-abc-123
```

**为何不用 GET 再 DEL 两条命令**：线程 A GET 校验通过 → 锁过期 → 线程 B 加锁 → A DEL 删掉 B 的锁。

### 2.3 Java 示例（Jedis/Lettuce）

```java
public boolean tryLock(String key, String token, long seconds) {
    String result = jedis.set(key, token, SetParams.setParams().nx().ex(seconds));
    return "OK".equals(result);
}

public void unlock(String key, String token) {
    String script =
        "if redis.call('GET', KEYS[1]) == ARGV[1] then " +
        "  return redis.call('DEL', KEYS[1]) else return 0 end";
    jedis.eval(script, Collections.singletonList(key),
               Collections.singletonList(token));
}
```

## 3. 常见问题与修复

### 3.1 锁过期但业务未完成

```
T0: 加锁 EX 30s
T25: 业务仍执行
T30: 锁自动释放 → 其他线程加锁成功
T35: 线程 A 完成 → 可能重复写 / 误删 B 的锁（若释放不校验）
```

| 方案 | 说明 |
|------|------|
| 合理评估 TTL | 业务 P99 × 2 |
| **看门狗续期** | Redisson 默认 |
| 业务幂等 | 锁外仍要保证 |

### 3.2 主从切换导致锁丢失

```
1. 客户端在 Master 加锁成功
2. Master 宕机，锁未同步到 Replica
3. Replica 晋升为新 Master，锁「消失」
4. 另一客户端加锁成功 → 双持锁
```

**Redis 单实例 / Sentinel 无法避免此极端情况**。金融级互斥用 **ZooKeeper / etcd**（CP 共识）。

### 3.3 时钟漂移

Redis 过期依赖系统时钟；极端漂移可能提前/延后过期。NTP 同步；RedLock 论文讨论 clock drift 需留 margin。

### 3.4 不可重入

同线程二次 `SET NX` 失败。需 Hash 结构 `HINCRBY lock_key threadId 1` + Lua 或 Redisson。

## 4. Redisson

### 4.1 特性

| 特性 | 实现 |
|------|------|
| 可重入 | Hash: field=UUID:threadId, value=重入次数 |
| 看门狗 | 默认 30s 锁，每 10s 续期到 30s |
| 红锁 | RLock 单 Redis；RedLock 多独立 Master |
| 读写锁 | RReadWriteLock |
| 联锁 | RMultiLock 多个资源 |

```java
RLock lock = redisson.getLock("order:lock:10001");
try {
    if (lock.tryLock(10, 30, TimeUnit.SECONDS)) {
        // waitTime=10s 等锁, leaseTime=30s 则不用看门狗
        // leaseTime 不传则看门狗自动续期
        deductStock();
    }
} finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

### 4.2 看门狗原理

```
加锁成功 → 启动 Watchdog 定时任务（默认 lockWatchdogTimeout/3）
         → 若仍持有则 EXPIRE 延长
业务完成 unlock → 取消续期
```

**注意**：`tryLock(wait, lease, unit)` 指定了 leaseTime 则**不**启用看门狗。

### 4.3 与手写锁对比

| 维度 | 手写 SET NX | Redisson |
|------|-------------|----------|
| 实现成本 | 低 | 依赖库 |
| 可重入 | 需自研 | 内置 |
| 续期 | 需自研 | 看门狗 |
| 生产推荐 | 简单场景 | **Java 主流** |

## 5. RedLock 与争议

### 5.1 算法（Redis 作者 Antirez）

```
对 N 个**独立** Redis Master（非主从复制关系）:
1. 依次 SET NX EX，记录加锁成功数
2. 总耗时 < 锁有效时间 - clock drift
3. 成功数 > N/2 → 认为加锁成功
4. 失败则向所有节点释放
```

```java
RedissonRedLock redLock = new RedissonRedLock(lock1, lock2, lock3);
redLock.lock();
```

### 5.2 争议（Martin Kleppmann 等）

| 批评点 | 说明 |
|--------|------|
| 非共识算法 | 多独立 Redis 仍非 CP |
| 主从 + 异步 | 单节点 RedLock 实例若用主从，仍有丢失问题 |
| 时钟依赖 | 多机时钟不同步破坏安全性 |
| GC 停顿 | 持锁线程 STW 超 TTL，锁过期后恢复仍以为持有 |

**社区共识**：

- RedLock **不能**把 Redis 变成 ZK 级强一致锁。
- 一般业务 **单 Redis + Redisson** 足够；配合**幂等**与**业务层去重**。
- 强一致互斥：**etcd / ZK**；或 DB `SELECT FOR UPDATE` / 唯一约束。

### 5.3 选型表

| 场景 | 推荐 |
|------|------|
| 电商库存（可超卖兜底） | Redisson 单集群 + DB 乐观锁 |
| 定时任务单跑 | SET NX EX 足够 |
| 支付幂等 | DB 唯一键 + 状态机 |
| 金融转账互斥 | ZK / etcd |
| 跨机房 | 谨慎 RedLock；优先 CP 组件 |

## 6. 与其他锁方案对比

| 方案 | 性能 | 一致性 | 复杂度 |
|------|------|--------|--------|
| Redis SET NX | 高 | 最终/极端丢失 | 低 |
| Redisson | 高 | 同 Redis | 中 |
| RedLock | 中 | 有争议 | 高 |
| ZooKeeper 临时顺序节点 | 中 | 强 | 高 |
| etcd Lease | 中 | 强 | 高 |
| MySQL `GET_LOCK` | 低 | 依赖 DB | 低 |
| 数据库唯一索引 | 中 | 强 | 低（幂等） |

```
ZK/etcd: 创建 ephemeral sequential 节点，最小序号获锁
         Watch 前一个节点释放
```

## 7. 并发场景实战

### 7.1 库存扣减

```java
// 锁 + DB 乐观锁双保险
@Transactional
public void deduct(Long skuId, int qty) {
    RLock lock = redisson.getLock("stock:" + skuId);
    lock.lock();
    try {
        int rows = stockMapper.deduct(skuId, qty); // WHERE stock >= qty
        if (rows == 0) throw new SoldOutException();
    } finally {
        lock.unlock();
    }
}
```

**Redis 锁防并发；DB 条件更新防超卖**——锁失效时仍安全。

### 7.2 定时任务防重复

```bash
# 每分钟任务
SET job:daily:report:20250701 host-1 NX EX 120
# 仅一台执行
```

配合 **ShedLock**（DB/Redis 存储）更规范。

### 7.3 接口幂等

```
SET idempotent:order:{requestId} 1 NX EX 86400
失败 → 重复请求直接返回上次结果
```

比「锁」更准确描述是 **去重键**。

### 7.4 缓存重建互斥

见第 03 章：`lock:product:{id}`，TTL 10s，防击穿。

## 8. 分布式锁设计 Checklist

| 项 | 要求 |
|----|------|
| 加锁 | SET key unique NX EX；或 Redisson |
| 解锁 | Lua 校验 value 再 DEL |
| 超时 | TTL 覆盖 P99；或看门狗 |
| 异常 | finally 释放；只释自己的锁 |
| 可重入 | 需则 Redisson |
| 降级 | 获锁失败快速失败，别无限 spin |
| 监控 | 锁等待时间、持有时间、失败率 |

## 9. 错误实现反例

```java
// ❌ 1. 无过期
jedis.setnx(key, "1");
jedis.expire(key, 30);  // 非原子

// ❌ 2. 释放不校验
jedis.del(key);

// ❌ 3. 锁 value 固定 "1"
// 线程 A 可能删 B 的锁

// ❌ 4. spin 无上限
while (!tryLock()) { }  // 打满 Redis

// ❌ 5. 锁粒度太大
lock("global:order");   // 串行化整个系统
```

## 10. 面试 Q&A

| 问 | 答 |
|----|-----|
| 如何实现 Redis 分布式锁？ | SET NX EX + 唯一 value；Lua 原子释放 |
| 为何要 unique value？ | 防误删其他客户端锁 |
| 看门狗作用？ | 业务未完成时自动续期，防锁过期 |
| RedLock 安全吗？ | 有争议；不能等价 ZK；一般业务不必 |
| 主从切换丢锁？ | 极端情况双持；强一致用 ZK/etcd |
| Redis 锁 vs ZK 锁？ | Redis 高性能 AP；ZK CP 临时节点顺序 |
| 可重入如何实现？ | Hash field=客户端+线程Id，count 加减 |
| 获锁失败策略？ | 快速失败、排队 MQ、重试带退避 |

## 11. 生产案例

**案例 1：未用 Lua 误删锁**

促销夜两实例交替 DEL，库存超卖。改 Lua + DB 乐观锁。

**案例 2：看门狗未开**

`tryLock(5, 60, SECONDS)` lease 60s，大报表 90s，锁过期双跑。改不传 lease 或加大 lease + 任务可重入检查。

**案例 3：锁粒度过细**

`lock:user:{id}` 每秒 10 万次，Redis CPU 高。改业务合并或本地 synchronized 分片 + 少量 Redis 锁。

**案例 4：Sentinel 切换双扣款**

主从切换窗口双持锁扣款两次。支付改 DB 唯一约束 `(user_id, biz_id)` 幂等 + 对账。

## 12. redis-cli 完整演练

```bash
# 1. 加锁
redis-cli SET demo:lock my-uuid-001 NX EX 30

# 2. 再次加锁失败
redis-cli SET demo:lock other-uuid NX EX 30
# (nil)

# 3. 正确释放
redis-cli EVAL "if redis.call('GET',KEYS[1])==ARGV[1] then return redis.call('DEL',KEYS[1]) else return 0 end" 1 demo:lock my-uuid-001

# 4. 错误 value 释放失败
redis-cli EVAL "if redis.call('GET',KEYS[1])==ARGV[1] then return redis.call('DEL',KEYS[1]) else return 0 end" 1 demo:lock wrong-uuid
# (integer) 0

# 5. 模拟可重入（Hash）
redis-cli HINCRBY reentrant:lock "client1:thread1" 1
redis-cli EXPIRE reentrant:lock 30
redis-cli HINCRBY reentrant:lock "client1:thread1" -1
```

## 14. 公平锁与读写锁（Redisson）

### 14.1 公平锁

```java
RLock fairLock = redisson.getFairLock("fair:order");
fairLock.lock();  // 按请求顺序获取，防饥饿
```

**代价**：维护队列，吞吐低于非公平锁。

### 14.2 读写锁

```java
RReadWriteLock rw = redisson.getReadWriteLock("config:rw");
RReadWriteLock.ReadLock readLock = rw.readLock();
RReadWriteLock.WriteLock writeLock = rw.writeLock();

readLock.lock();
try { return getConfig(); }
finally { readLock.unlock(); }

writeLock.lock();
try { updateConfig(); }
finally { writeLock.unlock(); }
```

| 锁 | 互斥 |
|----|------|
| 读 + 读 | 允许 |
| 读 + 写 | 互斥 |
| 写 + 写 | 互斥 |

**场景**：配置中心读多写少。

## 15. 锁监控与可观测性

```java
long start = System.currentTimeMillis();
if (lock.tryLock(5, TimeUnit.SECONDS)) {
    metrics.record("lock.wait", System.currentTimeMillis() - start);
    try {
        metrics.record("lock.hold", () -> doWork());
    } finally {
        lock.unlock();
    }
} else {
    metrics.increment("lock.fail");
}
```

| 指标 | 告警 |
|------|------|
| lock.wait P99 | > 1s 锁竞争严重 |
| lock.hold P99 | > TTL 需续期或优化业务 |
| lock.fail rate | > 5% 需扩容或降粒度 |
